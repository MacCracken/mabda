# Mabda Security Audit — 2026-04-30

**Scope**: P(-1) hardening pass against the Mabda v3 delta, targeting the
v3.0.0 release. Covers the new dual-backend abstraction
(`backend.cyr` / `backend_wgpu.cyr` / `backend_native.cyr` /
`backend_native_kms.cyr`), the new public surface dispatchers
(`surface_v3.cyr`), and the `GpuContext` 96 → 112-byte growth in
`context.cyr`. The v2 modules already audited 2026-04-19 (color,
profiler, capabilities, buffer/texture/sampler/depth/blend/vertex
/instancing, render_graph, the cache trio) are out of scope; flagged
only when the v3 work re-opened a prior class.
**Auditor**: internal.
**Target release**: 3.0.0 (post-fix).
**Method**: per-file code walk of the v3 delta (~5,800 new lines) +
DRM/KMS/AMDGPU CVE sweep (2026-04-19 .. 2026-04-30), with the
understanding that mabda's trust model remains "library called by
trusted consumer code." The native backend additionally runs as a
GPU client of the kernel — invalid ioctl payloads can crash the
kernel-side AMDGPU/DRM driver, so the same defensive posture
applies inward as well as outward.

## Summary

| Severity  | Count | Disposition                                |
|-----------|-------|--------------------------------------------|
| CRITICAL  | 0     | —                                          |
| HIGH      | 2     | Fix required before 3.0.0                  |
| MEDIUM    | 7     | Fix required before 3.0.0                  |
| LOW       | 6     | Schedule; defense-in-depth fixes           |
| Total     | 15    |                                            |

The v3 delta has the same structural posture as the v2.x core: no
memory-unsafe primitives, no libc, all ioctl / syscall args flow
through `syscall(SYS_IOCTL, ...)` or the wgpu C launcher, no direct
`fncall6` against wgpu-native. The new attack surface is the AMDGPU
/ DRM / KMS ioctl boundary — every ioctl payload struct is hand-laid
out by mabda in pure Cyrius, and consumer-supplied
`width`/`height`/`size` values flow into BO size math + page-flip
state.

The two HIGH findings are correctness defects in the surface API
that will surface (no pun intended) the moment a consumer wires
up a real present loop: `_backend_native_surface_configure` ignores
the consumer-requested `width` / `height` and silently substitutes
the EDID's preferred mode, and `gpu_surface_configure_native_logind`
leaks the logind-delegated master fd on every failure path between
"got fd from samvada" and "slot returned non-zero." Neither is
remote-reachable, but both are structural defects that must not
ship as a v3.0 first-party trusted dep.

The MEDIUM findings cluster around three patterns:
1. **Integer overflow on dimension math** in BO size + pitch
   computation (`width * height * 4`, `pitch * height`),
2. **Errno-vs-GpuErr code sign / shape inconsistencies** in the
   native surface present + ioctl wrappers, and
3. **Cross-handle / cross-fd leaks** on the modeset failure paths.

The LOW findings are documentation drift, stale stub bodies, and
defense-in-depth improvements to bounds-checks that today only
fail under contrived input.

---

## Methodology

1. **Attack-surface enumeration**. The v3 delta adds these
   external input boundaries on top of v2.x:
   - Consumer-supplied `width` / `height` / `card_fd` /
     `wgpu_surface` / `surface` to the new `gpu_surface_*` API.
   - Consumer-supplied PM4 dword counts and IB byte counts
     to `native_compute_dispatch_cached` /
     `native_render_dispatch_simple` (via the slot dispatchers,
     not directly).
   - `samvada_session_take_device` return value (sd-bus errno
     in the negative; valid fd in the positive). samvada itself
     is out of scope; the API boundary is in.
   - DRM / KMS / AMDGPU ioctl payloads — every offset hand-laid
     against `include/uapi/drm/{drm,drm_mode,amdgpu_drm,drm_fourcc}.h`.
     The kernel rejects malformed payloads with `-EINVAL`, but
     malformed payloads crafted to match the kernel struct layout
     can land in unintended driver paths.
   - DRM event-read (`syscall(0, fd, buf, n)`) on the master fd —
     consumer-supplied buf, kernel-supplied event payload.

2. **Code walk** per surface with checklist: input validation,
   buffer safety, integer overflow, divide-by-zero, syscall return
   handling, ioctl struct offset correctness, FFI shim avoidance,
   resource leak on failure paths.

3. **CVE sweep** of the 11 days since 2026-04-19 (the prior audit)
   in adjacent domains: linux-kernel DRM/KMS (especially amdgpu),
   drm-prime / drm-syncobj cross-fd handling, drm-event read paths,
   wgpu-native v29 patches.

4. **Findings triaged** with severity per the ladder in
   `CLAUDE.md`: CRITICAL (exploitable immediately) / HIGH (moderate
   effort) / MEDIUM (specific conditions) / LOW (defense-in-depth).

## Findings

### [HIGH-1] `_backend_native_surface_configure` ignores consumer-supplied `width` / `height`

- **File**: `src/backend_native.cyr`
- **Lines**: 2651–2698 (slot body), 2682 (substitution site)
- **Class**: CWE-841 (improper enforcement of behavioral workflow) /
  CWE-665 (improper initialization)
- **Phase introduced**: 7.7 (surface API public dispatchers + native
  slot wiring).

**Description**. The public dispatcher
`gpu_surface_configure_native_kiosk(ctx, card_fd, width, height)`
in `src/surface_v3.cyr:65` validates the consumer's
`width`/`height` (must be positive), stashes the card fd on
`ctx`, and dispatches `fncall3(slot, ctx, width, height)`.
The native slot at `src/backend_native.cyr:2651` validates
the same args (positive width / height) but then **never uses
them** — it pulls `fb_w` / `fb_h` from the connector's preferred
mode that `native_kms_modeset_first_connected` selected:

```cyrius
# src/backend_native.cyr:2671–2683
var rc = native_kms_modeset_first_connected(card_fd, render_fd,
                                            state,
                                            ns + NATIVE_SURFACE_SCANOUT);
if (rc != 0) { ... return 0; }
var fb_w = load32(ns + NATIVE_SURFACE_SCANOUT + NATIVE_KMS_SCANOUT_WIDTH);
var fb_h = load32(ns + NATIVE_SURFACE_SCANOUT + NATIVE_KMS_SCANOUT_HEIGHT);
rc = native_kms_alloc_fb(card_fd, render_fd, fb_w, fb_h,
                         ns + NATIVE_SURFACE_FB_B);
```

The `width` / `height` slot parameters are silently discarded.
The consumer asks for a 1280×720 surface; mabda configures
3840×2160 (or whatever the EDID prefers). The two FBs in the
swap chain match each other (both are `fb_w * fb_h`), so
double-buffered present works, but the consumer's
back-buffer-rendering code (compute / render PM4 streams,
texture writes, mmap'd CPU writes) targets the consumer's
expected dimensions — not the actual scanout dimensions.

**Impact**. Consumer renders an N-byte tile into a buffer that
`native_kms_alloc_fb` allocated as M-bytes (M typically larger,
since EDID preferred is usually the panel native). A mmap'd
write past the consumer's expected end can land in an unrelated
mapped page. Buffer-size mismatches between the render path
and the present path produce torn / partial frames; consumer
debugging will land in mabda's modeset code rather than their
own dimensioning. On the wgpu side this works correctly —
`_backend_wgpu_surface_configure` *does* pass `width`/`height`
into `surface_state_new` (`src/backend_wgpu.cyr:530`). The
behaviour gap between backends silently breaks portability.

**Mitigation**. Two options:
- (a) Honor the consumer's request: pick a mode whose
  `hdisplay` × `vdisplay` matches `width` × `height`, fail
  with a recognisable error code if no mode matches.
- (b) Document explicitly that the native path "ignores
  consumer-supplied dimensions and uses the EDID preferred mode
  always," and write back the actual `fb_w`/`fb_h` to the
  surface struct so the consumer can read them — and reject
  any consumer-supplied size that doesn't match a supported
  mode.

(a) is the wgpu-parity path and what consumers expect; (b) is
the smaller patch but breaks the cross-backend identity story
the v3.0 backend abstraction is selling. Either is fine for
3.0.0 — silently ignoring the args is not.

### [HIGH-2] `gpu_surface_configure_native_logind` leaks the master fd on every failure after `samvada_session_take_device`

- **File**: `src/surface_v3.cyr`
- **Lines**: 102–123
- **Class**: CWE-401 (missing release of resource), CWE-404
  (improper resource shutdown / release)
- **Phase introduced**: 7.7 (logind path; samvada v0.2.0 wiring).

**Description**. The dispatcher composes:

```cyrius
# src/surface_v3.cyr:111–123
var fd = samvada_session_take_device(_DRM_MAJOR, 0);
if (fd < 0) {
    fd = samvada_session_take_device(_DRM_MAJOR, 1);
}
if (fd < 0) { return 0; }   # samvada uninit'd OR no card available

var b = gpu_ctx_backend(ctx);
if (b == 0) { return 0; }
var slot = backend_get_slot(b, BACKEND_SLOT_SURFACE_CONFIGURE);
if (slot == 0) { return 0; }
gpu_ctx_set_native_card_fd(ctx, fd);
return fncall3(slot, ctx, width, height);
```

`samvada_session_take_device` succeeded and returned a
delegated DRM master fd. The dispatcher then:
1. `gpu_ctx_backend(ctx)` returns 0 → returns 0, fd leaks.
2. `backend_get_slot` returns 0 → returns 0, fd leaks.
3. `fncall3(slot, ctx, width, height)` returns 0 (slot's
   own failure path: discovery failed, modeset failed,
   second-FB alloc failed) → returns 0, fd leaks.

In each case the fd is now stashed on `ctx`, but the
dispatcher never calls `samvada_session_release_device`, never
calls `sys_close(fd)`, and the consumer has no signal that
they need to manually release it (the dispatcher returns 0,
which is "no surface; you didn't get a card" — same return
value as "samvada took your fd and gave it away").

This is the master-fd version of the v2.x compute-pipeline
leak class (LOW-5 in the prior audit). A consumer running
a fallback "try logind, then try kiosk" loop accumulates one
leaked master fd per attempt — and master fds on a logind
session may be capped by `RLIMIT_NOFILE`.

**Impact**. Resource leak. Each failed
`gpu_surface_configure_native_logind` call leaks one fd held
in master mode by the kernel. Other DRM clients that try to
`SET_MASTER` on this card will see `-EBUSY` until process
exit. On a desktop with hot-plug, this also means logind's
internal "session active device tracking" gets confused.
Not memory-corruption, but it can render the GPU
inoperable from this process for the rest of its lifetime.

**Mitigation**. After every `if (...) { return 0; }` between
`samvada_session_take_device` and the slot dispatch, release
the fd. Symmetrically, route the slot's failure path through
a closer instead of a bare `return 0`. The cleanest shape is:

```cyrius
fn gpu_surface_configure_native_logind(ctx, width, height) {
    if (ctx == 0)    { return 0; }
    if (width <= 0)  { return 0; }
    if (height <= 0) { return 0; }
    var fd = samvada_session_take_device(_DRM_MAJOR, 0);
    if (fd < 0) { fd = samvada_session_take_device(_DRM_MAJOR, 1); }
    if (fd < 0) { return 0; }
    var b = gpu_ctx_backend(ctx);
    if (b == 0) {
        samvada_session_release_device(_DRM_MAJOR, 0);  # or remember the minor
        sys_close(fd);
        return 0;
    }
    ...
    var surf = fncall3(slot, ctx, width, height);
    if (surf == 0) {
        # slot failed; return master to logind + close fd
        samvada_session_release_device(_DRM_MAJOR, ...);
        sys_close(fd);
        gpu_ctx_set_native_card_fd(ctx, 0);
    }
    return surf;
}
```

(The "remember which minor we got" detail needs a small extra
slot on the dispatcher's locals; trivial.)

### [MED-1] `_backend_native_surface_present` returns kernel-negative errno where slot ABI declares `GPU_ERR_*` (positive)

- **File**: `src/backend_native.cyr`
- **Lines**: 2719–2744 (slot body), in particular 2738
  (`if (rc != 0) { return rc; }`)
- **Class**: CWE-754 (improper check for unusual conditions),
  CWE-393 (return of wrong status code)
- **Phase introduced**: 7.7 (native surface slot).

**Description**. `gpu_surface_present` (in `surface_v3.cyr:148`)
documents its return as "0 on success, GPU_ERR_* on failure"
and the wgpu wrapper at `_backend_wgpu_surface_present`
returns `surface_state_submit_present(surface)` which is 0 or
a positive `GPU_ERR_*` per the v2.x convention. The native
slot `_backend_native_surface_present` instead does:

```cyrius
var rc = native_kms_present(card_fd, ..., back_fb_id, 0);
if (rc != 0) { return rc; }
```

`native_kms_present` returns `0` on success or **negative**
errnos (the page-flip ioctl rc, the `read(2)` rc, or `-1` /
`-2` / `-3` for caller-internal cases). So consumers checking
`if (gpu_surface_present(ctx, surf) != 0) { ... }` see a
negative rc on native and a positive `GPU_ERR_*` on wgpu —
diagnosable, but consumers that compare against specific
`GPU_ERR_*` codes hit a silent miss on native.

A particularly nasty case is `-EBUSY` (-16) coming back from
a too-fast second `present` call (kernel returns EBUSY if
the previous flip's vblank event hasn't fired yet). The
consumer's "if return is `GPU_ERR_BUFFER` (== 1) retry once"
logic reads -16 != 1 and either falls through or treats it
as success.

**Impact**. Consumer error-handling code paths diverge
between backends. The wgpu side gets the positive code that
the public API documents; the native side gets the negative
kernel errno. Compatible diagnostics fail; same code that
"works" on wgpu silently misbehaves on native.

**Mitigation**. Route through `_native_neg_rc_to_gpu_err`
the same way every other native slot does. Two-line patch:

```cyrius
var rc = native_kms_present(card_fd, ..., back_fb_id, 0);
if (rc != 0) { return _native_neg_rc_to_gpu_err(rc); }
```

(Also worth eyeballing every internal step-code in
`native_kms_present`'s tail: `-2` "short read" and `-3` "wrong
event type" are mabda-internal sentinels, not kernel errnos —
they should map to a fresh `GPU_ERR_SURFACE_*` code rather
than be passed through as-is.)

### [MED-2] `native_kms_alloc_fb` and `native_kms_modeset_first_connected` lack overflow guards on `pitch * height`

- **File**: `src/backend_native_kms.cyr`
- **Lines**: 1218–1220 (modeset_first_connected), 1480–1482
  (alloc_fb), 1496 (forwarded to `native_kms_add_fb_xrgb8888`)
- **Class**: CWE-190 (integer overflow) → CWE-787 (OOB write)
- **Phase introduced**: 7.2(d) + 7.5.

**Description**. Both fns compute scanout BO size as:

```cyrius
var pitch_raw = width * 4;
var pitch = ((pitch_raw + 255) / 256) * 256;
var bo_size = pitch * height;
```

`width` and `height` are `u32` from the kernel's
`drm_mode_modeinfo` (`hdisplay` / `vdisplay` fields,
loaded via `load16`) on the modeset path, and from
caller-supplied i64s on the alloc_fb path (with the
`width <= 0 / height <= 0` guards but no upper bound).
Three overflow surfaces:

- `width * 4`: well within i64 for any realistic display
  width; would need `width > 2^60`, not reachable in practice.
- `(pitch_raw + 255) / 256 * 256`: same, defense-in-depth.
- `pitch * height`: for caller-supplied `width = 65536,
  height = 65536` the size is 17.18 GiB — wrapping for
  `width = height = 2^32` is i64-safe (4.6e19 / 2^63 ≈
  large), but for `width = height = 2^31` the math is
  `pitch ≈ 8 GiB * 2^31 = 1.6e19` — within i64 range, just
  large. The deeper concern: `width * 4` then promotes
  `pitch` to a value passed as both the pitch ioctl arg
  (a u32, truncated) AND the BO-size ioctl arg (i64). If
  `pitch > 2^32` after rounding, the truncated u32 pitch
  on the AMDGPU FB ADD path doesn't match the BO size
  the kernel reserves — the kernel allocates
  `pitch_truncated * height` bytes of GTT and userspace
  thinks it has `pitch_full * height`. The next write into
  the mmap reaches past the BO end.

The `surface_v3.cyr` configure entries cap nothing on `width
/height`. A consumer passing 67108864 × 67108864 (legitimately
silly numbers, but mabda doesn't reject them) crashes at the
ioctl with `-ENOMEM` or worse, lands in the truncation case.

**Impact**. With caller-supplied width/height that wrap when
multiplied by 4 + cast to u32, the kernel's accepted
`drm_mode_fb_cmd2.pitches[0]` is smaller than the mmap stride
the BO actually has. A consumer write to the mmap goes into
unmapped memory or an adjacent BO. On the modeset path
(`native_kms_modeset_first_connected`) the dimensions come
from `drm_mode_modeinfo` and so are bounded by the kernel —
unreachable in practice. On `native_kms_alloc_fb` they come
from mabda's caller and can reach the overflow case for a
malformed (but well-typed) input.

**Mitigation**. Cap caller-supplied width/height. WebGPU's
limit is 16384 × 16384 (`MAX_TEXTURE_DIMENSION_2D`); KMS
scanout is realistically capped at the panel's native res.
Reject `width > 16384` / `height > 16384` and `pitch * height
> 2^31` (since the FB cmd's per-plane pitches[] is u32,
anything past 2^31 is asking for trouble). Add an overflow
guard:

```cyrius
if (width > 16384) { return -1; }
if (height > 16384) { return -1; }
var pitch_raw = width * 4;
if (pitch_raw < width) { return -1; }  # overflow guard, defensive
var pitch = ((pitch_raw + 255) / 256) * 256;
var bo_size = pitch * height;
if (bo_size / pitch != height) { return -1; }  # overflow guard
```

### [MED-3] `_backend_native_render_pass_target` divides by 2 with no even-dimension guard; viewport math wrong on odd RT sizes

- **File**: `src/backend_native.cyr`
- **Lines**: 1620–1657 (block 3 builder), in particular
  1639–1640 (`rt_width / 2`, `rt_height / 2`)
- **Class**: CWE-682 (incorrect calculation), defense-in-depth
- **Phase introduced**: 6.5(b).

**Description**. `native_pm4_build_render_pass_target` derives
viewport scale + offset from `rt_width / 2` and `rt_height / 2`
using integer division (Cyrius `/` is integer):

```cyrius
var w_half_f32 = native_int_to_f32_bits(rt_width / 2);
var h_half_f32 = native_int_to_f32_bits(rt_height / 2);
```

For odd `rt_width` / `rt_height` the loss of the half-pixel
shifts the viewport off by 0.5 px, distorting the rendered
output (the comment at line 1619 notes "must be even" but
nothing enforces it — the only guard is `rt_width <= 0`).
A consumer creating an odd-sized RT on the native backend
silently gets a misaligned scissor / viewport.

**Impact**. Visual: shadow-edge fringing, sub-pixel offset
artefacts. Not memory-corruption; the dispatch still completes.
But the silent failure makes "render the same triangle on
both backends, byte-compare" produce different bytes — the
v3.0 cross-backend identity story breaks.

The path-cited 6.5(b) header docstring (line 1619) says
"`rt_width` and `rt_height` are pixel counts (must be even
for the /2 viewport math to be exact)" — so the contract is
documented but not enforced. v3.0's
`_backend_native_render_target_create_2d_rgba8` doesn't reject
odd width/height either.

**Mitigation**. Either reject odd dimensions in the RT
allocator (cleanest), or compute viewport in IEEE-754 directly
using `f64_div(f64_from(rt_width), f64_from(2))` then
`f64_to_f32`. The latter is more flexible (consumers can use
1×1 textures for picking, etc.) but more code. Rejection is
fine for v3.0.

### [MED-4] Two-pass DRM ioctls have a TOCTOU window between count-pass and fill-pass

- **File**: `src/backend_native_kms.cyr`
- **Lines**: 291–363 (`native_kms_init`), 645–680
  (`native_kms_get_connector_modes`)
- **Class**: CWE-367 (Time-of-check / time-of-use), CWE-122
  (heap-based buffer overflow, mitigated)
- **Phase introduced**: 7.1(a) + 7.2(a).

**Description**. Both two-pass discovery flows do:
1. `ioctl(GETRESOURCES, count_*=0, *_ptr=0)` to learn counts.
2. `alloc(count_X * 4)` for each ID array.
3. `ioctl(GETRESOURCES, *_ptr=arrays, count_*=capacity)` to fill.

The kernel reserves the right to grow the underlying lists
between calls (e.g. hot-plug a connector). The post-fill
counts are the source of truth and the code does take them
as authoritative (lines 349–356 in init), but the array
*allocations* are sized off the count-pass values. If the
fill-pass returns a count *larger* than pass-1 reported (a
new connector arrived in the gap), the kernel writes more
IDs than the buffer holds — heap overflow.

In practice the kernel never grows the count between the two
calls in this direction; it can grow it before the second
call but the second call still treats the userspace
`count_*` as the buffer cap and writes only up to that many
IDs. From `drivers/gpu/drm/drm_mode_config.c:drm_mode_getresources`:

```c
if (card_res->count_fbs >= fb_count) {
    /* copy out */
    if (copy_to_user(fb_ptr, ..., fb_count * sizeof(u32)))
        ret = -EFAULT;
}
card_res->count_fbs = fb_count;  /* report actual */
```

The kernel respects userspace's cap. But mabda's code at
lines 658 in `native_kms_get_connector_modes` doesn't guard
against the inverse case: count-pass says N, alloc N, fill-
pass says N+1 (which the kernel won't write past the cap, but
the post-fill `count_modes` is now N+1 according to the
kernel even though only N modes were copied — and mabda
trusts `actual` and exposes it):

```cyrius
var actual = load32(&req + DRM_MODE_GET_CONNECTOR_COUNT_MODES);
store32(count_out, actual);
return modes;
```

A caller iterating `modes_ptr[0..actual]` reads past the
allocated buffer for the "extra" mode at index N.

**Impact**. With a hot-plug-during-discovery race, the caller
can read 68 bytes past the modes buffer. Bump-allocator
allocations in mabda are page-aligned and contiguous, so the
read lands in the next allocation (which on this code path
is whatever happened next — typically a request struct or
the FB struct). Read-only OOB; no overwrite.

Same shape applies to `native_kms_init`'s ID arrays: the
per-category counts are clamped at the cap by the kernel,
but mabda then trusts the post-fill count and downstream
loops walk that count.

**Mitigation**. Trust the *minimum* of "what we allocated for"
and "what the kernel wrote." After the fill-pass, clamp
`actual = min(actual, capacity)` before exposing it. Three-line
patch in each of the two callers.

### [MED-5] `native_drm_set_master` collapses `-EINVAL` to success with no probe

- **File**: `src/backend_native_kms.cyr`
- **Lines**: 62–67
- **Class**: CWE-755 (improper handling of exceptional condition)
- **Phase introduced**: 7.1.

**Description**.

```cyrius
fn native_drm_set_master(fd) {
    var rc = syscall(SYS_IOCTL, fd, DRM_IOCTL_SET_MASTER, 0);
    if (rc == 0)         { return 0; }
    if (rc == 0 - 22)    { return 0; }   # -EINVAL → already master
    return rc;
}
```

The comment claims `-EINVAL` means "already master, kernel
doesn't differentiate." This is true for *some* kernels and
*some* configurations (e.g., a freshly-opened render-fd-then-
SET_MASTER race on certain pre-6.x kernels). It is not the
authoritative kernel docs — `drivers/gpu/drm/drm_auth.c`
returns `-EINVAL` from `drm_setmaster_ioctl` for several
distinct cases including "fd opened with O_WRONLY" and
"DRM driver doesn't support master/auth (rare but legal for
software-render-only drivers)."

Treating `-EINVAL` as success and returning 0 means the
caller proceeds as if it has master. The follow-up SETCRTC
or AddFB2 ioctl will actually fail with `-EACCES` or
`-EPERM`, but by then the consumer has done discovery,
mode pick, BO alloc, PRIME bridge — wasted work, and the
error path lands at SETCRTC instead of at the master grab.

**Impact**. Diagnostic confusion: errors land further
downstream than they should. No memory-corruption, but
on the small subset of kernels / drivers where `-EINVAL`
genuinely means "operation not supported" (not "already
master"), the consumer never gets a clean signal that
master wasn't available.

**Mitigation**. Probe master with a cheap ioctl after the
SET_MASTER. The cleanest is `DRM_IOCTL_AUTH_MAGIC` (which
requires master) or just a `SET_MASTER` retry that the
kernel resolves to one of {success, -EACCES, -EBUSY,
-ENOSYS}. Alternatively just accept that `-EINVAL` is
ambiguous and pass it through — caller can decide based
on subsequent ioctl results.

### [MED-6] `native_kms_present` accepts arbitrary buffer length but writes only into `buf[0..32]`

- **File**: `src/backend_native_kms.cyr`
- **Lines**: 1561–1596, in particular 1579–1583
- **Class**: CWE-200 (information exposure through stack
  reuse), CWE-457 (use of uninitialized variable, mitigated)
- **Phase introduced**: 7.5.

**Description**.

```cyrius
var buf[64];
memset(&buf, 0, 64);
var n = native_drm_read_event(card_fd, &buf, 64);
if (n < 0) { return n; }
if (n < DRM_EVENT_VBLANK_SIZE) { return -2; }
var ev_type = drm_event_type(&buf);
if (ev_type != DRM_EVENT_FLIP_COMPLETE) { return -3; }
```

The fn requests up to 64 bytes from the DRM fd. The
kernel may queue *multiple* events on the fd (vblank +
flip-complete, or a stale vblank from a prior flip), and
`read(2)` returns all of them in the one call. Mabda only
inspects the first event header; if it's `FLIP_COMPLETE`,
it returns 0 — leaving the second + later events
*unread* on the fd. The next time mabda reads (next
present), the stale `vblank` lands at offset 0 instead
of the new flip-complete, and the `if (ev_type !=
DRM_EVENT_FLIP_COMPLETE)` rejects it as `-3`.

Worse: the comment at line 1583–1586 says "the event we
drained wasn't FLIP_COMPLETE [...] could happen if some
other queued event lives in the read queue." This is
*deterministically* the case after the first present — the
present-pacing kernel queues both `DRM_EVENT_VBLANK` and
`DRM_EVENT_FLIP_COMPLETE` for every flip, and userspace
must drain both.

**Impact**. The first `gpu_surface_present` succeeds. The
second returns `-3` (mabda's "wrong event type" sentinel).
Subsequent presents may alternate. The visual result is
present pacing breakage — frames present but the syncobj
loop reports stutter, and the consumer's "present
returned non-zero, retry" loop spins.

The `programs/native_present_e2e.cyr` 120-frame test (per
the punchlist) presumably has run successfully on real
hardware, which suggests either the kernel-version-on-the-
test-box only emits FLIP_COMPLETE (kernel >= 6.10 with
`drm.timeline = 0`) or the alternate-event case fires
silently. Worth verifying.

**Mitigation**. Loop the read until either the queue
drains or a `FLIP_COMPLETE` event lands:

```cyrius
var found = 0;
while (found == 0) {
    var n = native_drm_read_event(card_fd, &buf, 64);
    if (n < DRM_EVENT_VBLANK_SIZE) { return -2; }
    # walk multiple events in the buffer if any
    var off = 0;
    while (off < n) {
        var ev_len = drm_event_length(&buf + off);
        var ev_type = drm_event_type(&buf + off);
        if (ev_type == DRM_EVENT_FLIP_COMPLETE) { ... drain ...; found = 1; }
        off = off + ev_len;
    }
}
```

(Use the `length` field on the event header — already
exposed at line 1423 — to walk multiple events in one buffer.)

### [MED-7] `_backend_native_render_pass_draw` allocs a 1024-byte PM4 scratch on every draw call (per-frame leak in long-running consumers)

- **File**: `src/backend_native.cyr`
- **Lines**: 2535–2595 (slot body), in particular 2557–2558
- **Class**: CWE-401 (missing release of resource — bump
  allocator), CWE-770 (allocation without limits)
- **Phase introduced**: 6.8(c).

**Description**. Every `render_pass_draw` slot call:

```cyrius
var pm4 = alloc(1024);
memset(pm4, 0, 1024);
...
return native_render_dispatch_simple(ctx, pm4, pos, &triple, deadline);
```

The bump allocator never reclaims this 1024-byte buffer.
For a consumer rendering at 60 FPS for a 60 s scene, that's
3,600 draw calls × 1024 bytes = 3.5 MB of leaked PM4
scratches per minute of operation. For a soorat-style
desktop compositor running continuously, this exhausts
the bump-allocator slab in hours.

The compute side has the same issue at line 2374 (`alloc(256)`
in `_backend_native_compute_dispatch`) and at lines 2103, 2220
(`alloc(8)` for the syncobj handle ptr).

The bump allocator is `process-lifetime, never freed` — that
contract is fine for one-shot programs (every test program in
`programs/`), but the moment a consumer integrates this slot
into a frame loop, the leak is real.

**Impact**. Bump allocator OOM in long-running consumers.
Process aborts via `alloc()` returning 0; subsequent code
that expects non-null fails with a segfault on the first
`store64` to the result. Not exploitable, just a UX cliff.

**Mitigation**. Cache the PM4 scratch on the `GpuContext` (or
on the `NativePass` struct, since pass_begin already allocs).
The PM4 stream is composed each draw, but the buffer can be
reused. The compute path already does this for the IB BO via
`gpu_context_new_native`'s `_NATIVE_IB_VA` cache — extend the
same pattern to `pm4` scratches.

### [LOW-1] `native_drm_set_master` doesn't check `fd > 0` like its KMS siblings

- **File**: `src/backend_native_kms.cyr:62`
- **Class**: CWE-754 (improper check for unusual conditions),
  defense-in-depth.

**Description**. Every other ioctl wrapper in the file
(`native_drm_mode_set_crtc`, `native_kms_page_flip`, etc.)
guards `if (fd <= 0) { return -1; }` before issuing the
ioctl. `native_drm_set_master` and `native_drm_drop_master`
go straight to the syscall. With fd=0 (a passed-in zero from
a caller mistake), the syscall fires against stdin's fd.
On a normal program stdin isn't a DRM fd, so the kernel
returns `-ENOTTY`; harmless. But the guard is cheap and
matches the rest of the file's style.

**Mitigation**. Add `if (fd <= 0) { return -1; }` at the
top of both fns.

### [LOW-2] `native_kms_summary` infinite-loop bound is `j < 32` for hex32 printer; loops without bound on `_kms_summary_print_u32`

- **File**: `src/backend_native_kms.cyr:584` (u32 printer)
- **Class**: defense-in-depth — buffer-write OOB if `fmt_int_buf`
  ever returns > 16.

**Description**.

```cyrius
fn _kms_summary_print_u32(v) {
    var buf[16];
    memset(&buf, 0, 16);
    var n = fmt_int_buf(v, &buf);
    syscall(1, 1, &buf, n);
    return 0;
}
```

`fmt_int_buf` is in `lib/fmt.cyr`; for unsigned i64 (Cyrius
ints are i64), the worst case is `9223372036854775807` =
19 digits. The 16-byte buffer overflows for any value >
9999999999999999. mabda's CRTC IDs and connector IDs are
u32 in practice, so 10 digits max — the 16-byte buf is fine
for everything *currently* passed in. But the type signature
doesn't say "u32 only" — a future caller using this for a
larger value silently overruns.

**Mitigation**. Either size the buf at 24 bytes, or rename
the helper to `_kms_summary_print_u32` (already done — name
is fine) and add an internal assert that `n <= 16`.

### [LOW-3] `_backend_native_buffer_create / _write / _read / _release` and `_shader_module_*` slots are still stubs

- **File**: `src/backend_native.cyr:2334–2358`
- **Class**: CWE-440 (expected behaviour violation),
  documentation drift.

**Description**. The native backend's `buffer_create` slot
at line 2334 returns `0`; `_write` and `_read` return
`GPU_ERR_OTHER`; `_shader_module_create` returns `0`. These
are the v3 Step 4c stubs that the punchlist marked as
"deferred to Step 4d+ work" in 2026-04-28.

Three reachable consequences in v3.0:
- A consumer calling `gpu_buffer_create` against a native
  backend gets `0` (interpreted as alloc failure). This is
  the documented behaviour — the public API surface
  routes through the slot — but the failure mode is
  indistinguishable from "GPU OOM."
- `gpu_shader_module_create` returns 0 → consumer's later
  `gpu_compute_dispatch` call gets a 0 shader module ptr,
  and the slot's null-check rejects it as `GPU_ERR_OTHER`.
- The consumer has to know that "native backend doesn't
  support `gpu_buffer_*` yet, you must use the
  `native_buf_pair_write` private convention" — which is
  documented in the slot header comment at line 2266 but
  not in any public-facing doc.

**Impact**. None today (programs that drive the native
path use the private buf-pair convention). But as soon as
a soorat / rasa / etc. tries to compile against the dual
backend, the discrepancy surfaces.

**Mitigation**. Either land the real impls for v3.0 (which
the punchlist defers), or return a more diagnostic error
code (e.g. add `GPU_ERR_NOT_IMPLEMENTED` to the enum so
consumers can pattern-match cleanly). Adding the enum value
is a tiny, ABI-stable extension — the existing
`GPU_ERR_OTHER` paths still work, and consumers that want to
disambiguate get a hook.

### [LOW-4] `_backend_native_render_pass_draw` ignores `vc` and `ic` (caller-supplied vertex / instance counts)

- **File**: `src/backend_native.cyr:2535`
- **Class**: CWE-440 (expected behaviour violation).

**Description**. The slot signature takes
`(ctx, pass, pipe, vc, ic)` for parity with wgpu's
`render_pass_encoder_draw(vertex_count, instance_count, ...)`
but the body uses fixed `GFX9_FULLSCREEN_TRI_VCOUNT` (=3) and
`GFX9_VGT_NUM_INSTANCES_ONE` (=1) regardless. Documented at
line 2533 ("v2-native: single-draw-per-pass — vc/ic are
accepted for ABI parity but the FS+VS pair is fixed-shape").

Cross-backend identity is broken for any draw count != 3 or
instance count != 1. A consumer that draws a 6-vertex quad on
both backends gets a 3-vertex triangle on native.

**Impact**. Same shape as HIGH-1 but a smaller blast radius —
v2-native only ships a single fixed shader pair, so any 3-
vertex full-screen-triangle draw works regardless. But the
silent-drop is the same class of issue.

**Mitigation**. Either return `GPU_ERR_OTHER` on
`vc != 3 || ic != 1` to surface the limitation, or honour the
caller's `vc` / `ic` in the PM4 stream (single-line change in
`native_pm4_build_render_draw_tail` to take the count as an
arg).

### [LOW-5] `_backend_native_compute_dispatch` allocates `pm4 = alloc(256)` on every dispatch

- **File**: `src/backend_native.cyr:2374`
- **Class**: CWE-770 (allocation without limits).

Same pattern as MED-7 but on the compute side. The PM4
scratch is 256 bytes per dispatch, leaked to the bump
allocator. For a consumer running a compute shader at
"once per frame," 256 bytes / frame × 60 FPS = ~900 KB / hour.
Slower leak than the render path's 1024 bytes / draw, but
same class.

**Mitigation**. Cache on the GpuContext alongside the cached
IB BO. (The cached IB BO is at `_NATIVE_IB_VA` already;
the staging copy on the host side is what
`alloc(256)` gives us. Reuse a heap-allocated 1024-byte
scratch on the ctx — the compute and render paths share
the same buffer at different offsets.)

### [LOW-6] `gpu_surface_release` doesn't zero `gpu_ctx_native_card_fd` / `gpu_ctx_wgpu_surface_handle` on the ctx after release

- **File**: `src/surface_v3.cyr:161–169`
- **Class**: CWE-672 (use after release), defense-in-depth.

**Description**. `gpu_surface_release(ctx, surface)` calls
the slot's release fn, which zeros the surface struct itself
— but the consumer-stash fields on the ctx
(`+96` `wgpu_surface_handle`, `+104` `native_card_fd`)
remain set. A subsequent `gpu_surface_configure_*` on the
same ctx skips the "stash on ctx" step but the slot still
reads the stashed value, which is now stale (pointing at a
released surface or a closed fd).

The configure dispatchers do call `gpu_ctx_set_*_handle`
before the slot dispatch, so on the happy path the new value
overwrites the stale one. The bug only surfaces when the
new configure fails *before* the stash (i.e. width/height
validation fails) — then the next `gpu_surface_acquire`
call routes through the stash and may read a stale fd /
handle.

**Impact**. Stale-pointer read into a slot that was just
released. Defense-in-depth.

**Mitigation**. Add `gpu_ctx_set_native_card_fd(ctx, 0)` and
`gpu_ctx_set_wgpu_surface_handle(ctx, 0)` to the release
dispatcher, after the slot's release fn returns.

## Disposition for v3.0 ship

**Ship-blocking** (must land before tag):
1. **HIGH-1** — `_backend_native_surface_configure` must either honour
   the consumer's width/height or fail loudly when ignoring them.
   Cross-backend identity is the load-bearing v3.0 architectural
   sell; silent dimension substitution breaks it.
2. **HIGH-2** — master fd leak on logind-path failure. Once a
   consumer wires up "try logind, fall back to kiosk," the leak
   accumulates until process exit and bricks DRM master for the
   process.
3. **MED-1** — native present return-code shape. Cheap fix, blocks
   any consumer with cross-backend error-handling logic.
4. **MED-3** — odd RT dimension viewport silent miscalc. Two-line
   fix in `native_rt_create_2d_rgba8` (reject odd `width` /
   `height`); guards against the cross-backend-identity drift.
5. **MED-6** — page-flip event-read short-drain. Blocks any
   long-running present loop. The 120-frame e2e program may have
   run by luck on the dev box; this is not a property to ship.

**Defer to v3.x** (file as backlog, not blockers):
- **MED-2** — overflow guards on caller-supplied dimensions. The
  3.0 attack surface for this is "consumer with malformed input"
  and most consumers cap dimensions themselves; defense-in-depth
  worth scheduling but not blocking.
- **MED-4** — TOCTOU clamping on two-pass discovery. Hot-plug
  during init is a corner case; the post-fill count is already
  treated as truth, the missing piece is just the min(actual, cap)
  clamp.
- **MED-5** — `set_master` `-EINVAL` ambiguity. Behavioural quirk,
  not a security issue.
- **MED-7** + **LOW-5** — bump-allocator leaks on per-dispatch PM4
  scratches. Real bug, but only surfaces on long-running consumers
  (compositor / game engine), which are a v3.x consumer-cutover
  effort anyway.
- **LOW-1, LOW-2** — defense-in-depth nits.
- **LOW-3** — native backend stubs. Either fold into the next
  Phase-B follow-up or document the public API limitation
  prominently in the README.
- **LOW-4** — `vc`/`ic` ignored in native render. Cross-backend
  parity issue, but in scope of the existing "v2-native fixed
  shader" v3.x backlog item.
- **LOW-6** — surface release stale-stash. Fixable in two lines;
  bundle with the HIGH-2 cleanup.

## Non-findings (verified clean)

- **No `unsafe` / memory-unsafe primitives** — Cyrius has none;
  every struct access via `load64`/`load32`/`load16`/`store*`
  with named offset constants. Spot-checked all `+offset`
  arithmetic in `backend_native.cyr` against the comment-block
  layouts and `backend_native_kms.cyr` against the kernel uapi
  headers (`linux/drm.h`, `drm/drm_mode.h`, `drm/amdgpu_drm.h`).
- **No `fncall6` direct calls into wgpu-native or kernel
  syscalls** — verified. The native path uses `syscall(SYS_IOCTL,
  fd, num, ptr)` (4 args, well within `fncall*` limits) for every
  ioctl. The wgpu path's 6+arg calls still go through
  `deps/wgpu_main.c` shims as before.
- **No raw pointer arithmetic outside documented struct
  accessors** — verified across the v3 delta. Every
  `load*(ptr + offset)` cites a named constant from the module's
  layout comment block (e.g.
  `KMS_STATE_FIELD_*` / `NATIVE_KMS_SCANOUT_*` /
  `DRM_MODE_FB_CMD2_*`). No string-tab access into kernel
  payloads without an offset constant.
- **No path writes to `/etc`, `/bin`, `/sbin`** — verified;
  mabda still never touches the filesystem outside
  `/dev/dri/render*` and `/dev/dri/cardN`.
- **PM4 dword math** — verified. `native_pm4_pkt3_header`'s
  count field is masked to 14 bits (`0x3FFF`). The PM4 buffer
  size in `native_pm4_build_render_clear_triangle` and
  `_compute_store_deadbeef` is bounded by the 1024 / 256-byte
  scratches respectively, both larger than the maximum PM4 a
  single dispatch ever produces (verified by counting dwords
  in the composers).
- **DRM ioctl numbers** — every `DRM_IOCTL_*` constant in the
  v3 delta cross-checked against `_IOC(dir, type, nr, size)`
  encoding via `native_ioc_encode`. The CPU asserts in
  `tests/tcyr/mabda_v3.tcyr` and `mabda_v3_phase_d.tcyr`
  cover every constant.
- **Backend slot indexing** — verified. `BACKEND_SIZE = 208`
  matches the sum of `+0..+200` slot offsets + 8-byte slot
  size; `BACKEND_FNPTR_SLOTS_END = 80`,
  `BACKEND_TEXTURE_SLOTS_END = 120`,
  `BACKEND_RENDER_SLOTS_END = 176`,
  `BACKEND_SURFACE_SLOTS_END = 208` — all aligned, no
  off-by-one. `backend_get_slot(b, off)` with off ≥ 208 reads
  past the struct, but no caller passes an unbounded value;
  every call site uses one of the named constants.
- **GpuContext 96 → 112-byte growth** — verified. The new
  slots at +96 / +104 are written only by the new
  `gpu_ctx_set_*_handle` setters, which include null-ctx
  guards. The growth doesn't shift any prior offset.
- **PRIME cross-fd dmabuf fd leak** — verified clean.
  `native_kms_import_bo` closes the transient `dmabuf_fd` on
  both success and failure branches (`sys_close(dmabuf_fd)`
  unconditionally before the final return), so the
  intermediate fd never leaks.
- **drm_event_vblank header parsing** — `drm_event_type` /
  `drm_event_length` use the documented 8-byte header; the
  vblank payload extends to 32 bytes total, well within the
  64-byte read buffer. (The MED-6 finding is about *which
  events* mabda drains, not the parsing itself.)
- **Layout comment vs alloc** — every `var X[N]` /
  `alloc(N)` in the v3 delta cross-checked against its
  module-header comment block. KmsState comment says 96 B,
  alloc is 96 B. NativeSurface says 120 B, alloc is 120 B.
  NativeRenderPipeline says 320 B, alloc is 320 B. NativePass
  says 32 B, alloc is 32 B. NativeTexture says 32 B, alloc
  is 32 B. NativeRenderTarget says 40 B, alloc is 40 B.
  NativeKmsScanout says 40 B, alloc is 40 B. NativeKmsFb
  says 32 B, alloc is 32 B. (The v2.x LOW-1 from the prior
  audit — `capabilities.cyr` 128 vs 120 — does *not*
  recur in any v3 module.)
- **Backend kind value is at +80 in the layout but
  treated as a value, not a fnptr** — verified.
  `backend_is_complete` skips the +80 slot by walking
  `0..80` then `88..120` then `120..176` then `176..208`.
  Every other slot reads a fnptr via `backend_get_slot`.
- **No `cyrius lint` warnings on the v3 delta** — verified
  with per-file invocations across all six modules in scope.
