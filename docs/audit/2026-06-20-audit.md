# Mabda Security Audit — 2026-06-20 (3.4.4 P(-1) scaffold-hardening)

Scope: the v3.4.x code since the last full audit (2026-06-14) — 3.4.0 array
textures + cubemaps (AA), 3.4.1 BC tiled arrays + the `MABDA_F64_*` collision
fix, 3.4.2 render-target allocator (64 KiB `va_map` align + per-context RT VA
bump), and 3.4.3 (the `va_map` 64 KiB sweep across every native create path +
the render-graph changes: out-of-order toposort, `rg_to_dot`, debug wrapping,
aliasing-planner activation). Tree at VERSION 3.4.3, toolchain 6.2.30.

Methodology: regression-check the prior ship-blockers + deferrals against the
current tree; two external CVE sweeps (amdgpu/DRM + wgpu/WebGPU, 2026-04-30 →
window); four dimension-focused security finders over the untrusted-input
parsers and the native memory paths; every candidate finding adversarially
re-verified against the actual source before disposition.

## Candidate findings — all FALSE POSITIVE (verified against source)

1. **DDS mipped-level `off` accumulation OOB (claimed CRITICAL).** FALSE. `off`
   is the parser-set constant `data_off` (128 legacy / 148 DX10,
   `asset_load.cyr:134`), **not** an attacker-controlled u64 header field. The
   level loop runs `mipc ≤ mip_level_count(w,h)` (~14) iterations, each guarded
   by `off + n > len` before the read (`:218`); for a real buffer `off ≤ len`
   holds and the sum cannot overflow i64.
2. **DDS/KTX2 `total = layers * faces` multiplication overflow (claimed
   CRITICAL).** FALSE. `arraysize` is clamped to `[1, MABDA_MAX_TEXTURE_ARRAY_
   LAYERS]` (256) at `asset_load.cyr:124-125` and `faces ∈ {1,6}`, so `total ≤
   1536` — no i64 overflow is reachable. The layered load bounds the span with
   the overflow-safe `total > (len - data_off) / per_image` (`:174`), computing
   no `total*per_image` product.
3. **SPIR-V `id_bound * SPIRV_TYPE_REC` memset OOB / i64 overflow (claimed
   HIGH).** FALSE. The cap check `id_bound > cap` (`spirv_parse.cyr:289`)
   precedes the `memset(out, 0, id_bound * SPIRV_TYPE_REC)` (`:290`), so memset
   runs only for `id_bound ≤ cap` (within the caller's `cap`-sized buffer). And
   `0x3FFFFFFF * 24 ≈ 2.5e10 ≪ i64_max` — the product cannot overflow i64.
4. **KTX2 `_asset_per_image_size` modulo on untrusted total (claimed MEDIUM).**
   FALSE. `total_images <= 0` is rejected (`:48`) before the modulo (`:50`), so
   the `%` never sees a non-positive divisor.
5. **PNG `w*h*4` unvalidated before multiply (claimed MEDIUM, ×2).** FALSE. The
   multiply at `asset_load.cyr:413` / `:439` runs only after
   `gpu_texture_create_2d_sampleable` / `_rgba8_mipped` succeed, and both
   validate `validate_dimensions(w, h, MABDA_MAX_TEXTURE_DIM_2D)` (≤ 8192) at the
   public dispatcher **and** the native slot — so at the multiply `w,h ≤ 8192`
   ⇒ `w*h*4 ≤ 256 MiB`, no overflow.

### Documented defense-in-depth (not defects)

- **PNG decoder output trust (chitra).** mabda trusts `chitra` (a fuzz-hardened
  pure-Cyrius PNG decoder, the sibling AGNOS package) to return a buffer sized
  to its reported `w×h`. The dimension cap above bounds the write size; a
  chitra-internal under-allocation would be a chitra defect, not mabda's.
- **`_native_align_up(desc_off + 64, …)` on sampleable descriptors.** `desc_off`
  derives from `w*h*element_bytes` under the 8192 dim cap (≤ ~1 GiB), so
  `desc_off + 64` cannot approach i64 limits — safe by construction.
- **Per-context VA bump-leak.** The texture/RT VA regions never reclaim on
  steady-state release (mabda's documented bump-leak allocator model); a
  churn-heavy consumer exhausts the region. A free-list is a tracked future
  concern, not a memory-safety defect.

## External CVE sweep (2026-04-30 → window)

### wgpu / WebGPU — clean
No applicable CVE. mabda links the wgpu-native v29.0.0.0 binary and forces the
Vulkan backend on Linux (`deps/wgpu_main.c`), so the in-window wgpu point-release
fixes (DX12/Metal/GLES backend-internal) are unreachable, and the headline
WebGPU CVEs are in Dawn (Chrome) and the PowerVR GLES driver — separate stacks
mabda does not embed. wgpu-native has zero published security advisories.

### amdgpu / DRM — kernel-side exposure, no mabda defect
Several in-window amdgpu kernel CVEs touch ioctls mabda drives, but **all are
kernel bugs**: mabda submits well-formed payloads and cannot patch them in-tree.
The mitigation is a **patched amdgpu kernel** at the deployment.

- **CVE-2026-43237** (CVSS 7.8, GEM_VA stale/freed `dma_fence` use on map/unmap
  last-fence timeline update). APPLICABLE — mabda issues `DRM_IOCTL_AMDGPU_GEM_VA`
  MAP/UNMAP on every BO. Strongest hit; kernel-side only.
- **CVE-2026-23468** (BO-list unbounded growth; fix adds a 128k cap). APPLICABLE
  path (BO_LIST_CREATE per submit) but mabda's lists are tiny + short-lived.
- **CVE-2026-46220** (SDMA4 `BUG_ON(addr & 0x3)` fence-writeback panic).
  CLASS_APPLICABLE — mabda drives the SDMA/CS rings, but the mis-aligned address
  is kernel-computed, not userspace-supplied, so a well-formed CS won't trip it.
- **CVE-2026-46209** (ADDFB2 plane-dimension check bypass on subsampled formats).
  CLASS_APPLICABLE — mabda uses `ADDFB2` but only with non-subsampled
  ABGR8888/ARGB8888/XBGR/XRGB over its own render-target dims.
- NOT_APPLICABLE: CVE-2026-43318 (cross-GPU dma-buf; mabda is single-Cezanne),
  CVE-2026-46197 (amdkfd/SVM; mabda uses no `/dev/kfd`), CVE-2026-46199 +
  cluster (VCN video parser; mabda submits no VCN IBs).
- **CVE-2026-46006** (nouveau 32-bit `base+offset` overflow) — NOT mabda's
  driver, flagged only as a **code-pattern** to audit (32-bit `pitch`/`offset`/
  `width*height` products wrapping before a bounds use). Swept: mabda uses 64-bit
  `store64` for VAs/sizes; the KMS 32-bit FB fields are bounded by the 16384 FB
  dim cap (`bo_size ≤ 1 GiB`, fits u32). No wrap found.

**Deployment advisory:** consumers running mabda's native AMD path should run an
amdgpu kernel patched for the above (notably CVE-2026-43237). Documented here so
the kernel-side exposure is visible; no mabda code change closes it.
