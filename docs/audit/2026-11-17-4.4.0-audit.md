# Mabda Security Audit — 2026-11-17 (4.4.0, compilers + NVIDIA)

**Scope.** The 4.4.0 diff against the `4.3.1` tag (about 5,600 source lines), weighted toward
what crosses a trust boundary:

- **consumer SPIR-V into the native compilers:** `spirv_parse`, `spirv_lower`, `mir`,
  `gfx9_*` (the 1024-id MIR space, the scratch-buffer contract, the control-flow fixes) and the
  new SM75 back end (`sm75_encode`, `sm75_isel`, `sm75_regalloc`, `sm75_compile`);
- **the kernel boundary on the display path:**
  - `backend_native_kms`: ADDFB2's struct, the poll-then-read flip wait, the console save and
    restore;
  - the AMD native surface (its 232-byte record, the double buffer, the recorded refusals);
  - NVIDIA block-linear scanout (tiled BOs, the VM_BIND kind, the copy-engine method, the CPU
    swizzle, the 296-byte `NvSurface`);
  - the logind fd's ownership on NVIDIA;
- **the wgpu surface-acquire leak fix** (`surface.cyr`, `backend_wgpu.cyr`,
  `backend_wgpu_surface.cyr`);
- **the dependency moves**, samvada 1.0.1 → 1.1.2 and chitra 1.0.3 → 1.4.1.

**Method.**
- Three reviewers read the diff against the CLAUDE.md security checklist (input validation,
  buffer safety, integer overflow, divide-by-zero, syscall returns, pointer validation, FFI
  layouts, shim correctness). They were split by trust boundary (compilers, kernel, wgpu), wrote
  nothing, and ran nothing on a GPU.
- Each finding was then traced again in the code before it was fixed.
- A regression check of both 2026-11-16 audits (4.3.0 and 4.3.1).
- An external CVE sweep for what changed since that sweep: Mesa 26.2.6 → 26.2.7 and Linux 7.2.14
  → 7.3.4 on the Cezanne this morning.

## Verdict

**In mabda's own code: 0 CRITICAL / 1 HIGH / 2 MEDIUM / 9 LOW, all fixed in 4.4.0.** The HIGH
and both MEDIUMs are silent miscompiles in the native compilers. Plus **one HIGH in a
dependency**: samvada's `TakeDevice` descriptor confusion (its 1.1.2 P1-1), fixed by the samvada
1.1.2 move.

### HIGH-1 — GFX9 waits were placed as if the program had no branches

`gfx9_waitcnt` walked the selected instructions in order. Before the first use of an
outstanding load it emitted `s_waitcnt vmcnt(0)`, and from then on treated every load as
arrived. But the program branches. When the use sat in a block a branch can skip at run time
(a uniform `s_cbranch_scc0`, a divergent if's `s_cbranch_execz`, a loop exit), the path that
skipped the block also skipped the wait, and the code after the merge still believed nothing
was in flight. Two consequences:
- **A later use read a load before it arrived.** A second load used only after the merge got
  no wait.
- **A register was recycled under a load still in flight.** Regalloc frees a load's VGPR after
  its last use, relying on "its first use waits". When that use was in the skipped block, a
  value computed after the merge could take the VGPR, and the load overwrote it when it landed.

Valid kernels silently got wrong data. A stale address or index could also send a store outside
its binding, anywhere in the process's GPU VM within the 32-bit offset range. SM75 was not
affected: its scheduler waits on every scoreboard at a `BRA`.

**Fix:** before every branch record (`s_branch`, `s_cbranch_scc0/1`, `s_cbranch_execz`),
anything outstanding is waited for, so every branch target is reached with nothing in flight
(SM75's rule). A fall-through keeps the linear state, which is exact for it.

Tests:
- `test_gfx9_waitcnt_waits_before_branches` (`compiler_backend.tcyr`), covering every branch
  kind;
- `test_cf_audit_fixes_isa` (`compiler_compile.tcyr`): the wait lands right before the
  `s_cbranch_scc0`;
- two hardware kernels, `wait_skipped_uniform_use` and `wait_skipped_only_use`
  (`tests/spirv/control_flow/`), lane-checked by `test-native-spirv-control-flow-e2e` and the
  NVIDIA gate. **Run on the Cezanne without the fix**
  (`build/logs/cut-440-cf-without-waitfix-*.log`), `wait_skipped_only_use` was wrong on 63 of 64
  lanes. Each read 63 (`a[63 - i] + i`): the late load had landed in the recycled register,
  exactly as predicted.

Both CPU tests fail with the fix removed (mutation-checked).

### MED-1 — an equal-target loop latch lost its phi copies on GFX9

`OpBranchConditional %c %H %H` is legal before SPIR-V 1.6. When both targets are a loop
header, `_spirv_lower_cond_branch` treated it as a back-edge and put the header's phi copies
after the COND_BRANCH, flagged on it. GFX9 isel turns an equal-target COND_BRANCH into
`s_branch` and advanced by one record, so the copies were selected after the unconditional
branch and never ran: the loop counter never advanced, and the GPU hung. SM75 already placed the
copies first.

**Fix:** the lowering turns an equal-target conditional branch into an unconditional one, with
its copies first, exactly as OpBranch is lowered. That covers both back ends.

`test_cf_audit_fixes_isa` checks that `loop_latch_same_targets` compiles to exactly the bytes of
its OpBranch twin, `loop_latch_branch`. That was checked on the CPU before the kernel ran on
hardware. Both kernels run lane-checked on the Cezanne and the TU116. Mutation-checked.

### MED-2 — SM75 emitted records whose operands were error codes

The SM75 f64 divide allocates about 140 synth ids, and several helper results were not
checked. Once the 1024-id space ran out, `mir_alloc_synth_id`'s error (-25) travelled through
the helpers as an operand <id>. `_s75_put` emitted it, regalloc read an id ≤ 0 as RZ, and the
compile returned success. An attacker can pick `id_bound` so the last division of about six runs
out just past its last checked allocation; a benign kernel near the limit hits it about 9 times
in 140. The division then returns 0.0, or NaN for a NaN input. The result is wrong, but no memory
is corrupted.

**Fix:** `_s75_put`, the one place SM75 emits records, refuses a negative dst or a negative
register operand with that operand's own code. Flagged immediates are raw bits and stay
allowed. `test_sm75_put_refuses_error_operands`.

### DEP-1 — samvada's `TakeDevice` returned a descriptor a local user could choose

samvada ≤ 1.1.1 attributed received descriptors to messages by each message's own `UNIX_FDS`
header field. A message whose header it could not walk (any big-endian message, or an unknown
field type ahead of `UNIX_FDS`) counted as carrying none. So a descriptor a local user attached to
a directed signal stayed queued, and the next `take_device` returned it with success. Through
`gpu_surface_configure_native_logind`, mabda would then modeset and scan out onto that fd. This
is samvada's 1.1.2 P1-1 (HIGH, the bug class of CVE-2022-42012). mabda 4.4.0 pins samvada 1.1.2.
The public surface mabda calls is unchanged (`samvada_native_init`, `samvada_session_take_device`,
`samvada_session_release_device`, `samvada_release`), and 1.1.2's stricter init errors are all
negative while mabda branches on non-zero. It was checked against the live system bus on the
Cezanne: `samvada_native_init()` returns 0, and `samvada_version()` reports 1.1.2. The logind seat
gate on both boxes is part of the seat closeout (below).

### LOW-1 — the flip wait could fall one flip behind for good

`native_kms_wait_flip_complete` returned on the first `DRM_EVENT_FLIP_COMPLETE` it read, from any
flip, and `native_drm_wait_event` restarted its full 1 s timeout after every EINTR (four of them:
4 s). If a wait timed out on a flip the kernel went on to complete (a vblank stall over 1 s), that
flip's event stayed queued. The next present's wait consumed it at once, and so did every wait
after: each present returned before its own flip landed, so the consumer drew into the buffer
being scanned out. A second CRTC on the same fd could also satisfy the wait.

**Fix:**
- The presents wait through `native_kms_wait_flip_for(card_fd, crtc_id, user_data, seq_out)`.
  It takes only the FLIP_COMPLETE whose `user_data` is the FB id the flip was given, and whose
  CRTC is the surface's when the event carries one; anything else is skipped.
- NVIDIA now passes its FB id as `user_data`, as AMD already did. A stale event is skipped, so
  the drift heals within one flip.
- `native_drm_wait_event`'s timeout is a deadline: an EINTR polls again for the time that is
  left and doesn't count as a spurious wakeup.

Tests (`kms.tcyr`, `test_kms_wait_flip_for_skips_stale_events`):
- a stale flip ahead of this one, in one read;
- another CRTC's event, and an event with no CRTC id;
- the any-flip drain unchanged;
- only stale events → -ETIME within the deadline;
- a 30 ms wait takes about 30 ms;
- a negative timeout is refused.

### LOW-2 — NVIDIA present reported a lost surface as "no adapter"

The drain's own -2 (no flip-complete in 16 reads, or a short read) and -3 (a malformed event) are
not errnos. AMD maps them to `GPU_ERR_SURFACE_LOST`. The NVIDIA present, new to the drain in
4.4.0, passed them through the errno map, which read -2 as ENOENT, `GPU_ERR_ADAPTER_NOT_FOUND`.
**Fix:** one map for both, `_native_present_rc_to_gpu_err`; `test_kms_present_rc_mapping`.

### LOW-3 — the console restore could put another monitor's config on this connector

Both modesets picked the lowest CRTC in the encoder's `possible_crtcs`. amdgpu DC lists every
CRTC there, so with two heads the pick could be the CRTC driving the other monitor. The 4.4.0
console save then recorded that monitor's config, and the restore put it onto this connector.
**Fix:** `native_kms_pick_crtc` keeps the CRTC already driving the connector (the encoder's
`crtc_id`) when the card lists it, and falls back to the mask's lowest otherwise. On a
single-head box the choice is the same as before. `test_kms_pick_crtc`.

### LOW-4 — releasing a non-current older-path wgpu surface leaked its frame

`_backend_wgpu_surface_release` returns early for a record that is no longer the context's
current surface: two `gpu_surface_configure_wgpu` calls, then a release of the first. That path
skipped `surface_state_release`, which is where an older-path record drops an unpresented frame.
It leaked one texture reference per such release. **Fix:** the frame is dropped first, on either
kind of record. Test in `target_tier.tcyr`.

### LOW-5 — an older-path present with no frame acquired called `wgpuSurfacePresent`

This covers no acquire, a failed acquire, or a resize since the acquire. wgpu-core answers with
an error that wgpu-native treats as fatal. The MB5 path already refused this. **Fix:** the slot
returns `GPU_ERR_SURFACE_CONFIG` and doesn't call wgpu. `surface_state_submit_present` itself is
unchanged for direct callers. The test that pinned the old 0 now pins the refusal, and that
nothing is presented.

### LOW-6 — a failed older-path acquire allocated on every call

`surface_state_acquire` built its failure Result with `gpu_err_new` (16 bytes of bump
allocation), and the slot discarded it. A consumer retrying a failing acquire every frame (an
occluded window) grew the heap by 16 bytes a frame. The 4.4.0 leak fix's 1,000-frame check
covered only success. **Fix:** `_surface_state_acquire_raw` allocates on no path; the slot
records the reason on the error channel. `surface_state_acquire` keeps its Result form. Test:
1,000 failed acquires allocate 0 bytes.

### LOW-7 — a uniform branch on a 0/-1 mask read whatever SCC held

`_gisel_cond_flag` puts a MIR_T_BOOL condition (a 0/-1 mask) into VCC, but the uniform
COND_BRANCH path branches on SCC. A mask legitimately comes only from a float compare, which is
always divergent. A uniform one comes from a malformed module, such as a bool-typed
`OpConvertUToF`, and it compiled to a branch on a stale SCC instead of failing. **Fix:** the
uniform path refuses it with `GISEL_ERR_COND_NOT_COMPARE`.
`test_gfx9_isel_uniform_mask_condition_refused`.

### LOW-8 — compile time grew with branches × stream length

`_spirv_find_label` scanned the whole stream, and an OpBranchConditional made up to five such
calls. Near `MABDA_MAX_SPIRV_WORDS` with about 1,000 branches, that is about 10^10 steps inside
`gpu_shader_module_create_spirv` (estimated, not measured). **Fix:** `spirv_lower_module`
builds a label → offset table once (the first OpLabel of each id, the scan's own answer) and
drops it when it returns. Outside a lowering, or past `MIR_MAX_CAP_IDS` ids, the scan runs as
before. `test_cf_label_table_matches_scan` checks that the table and the scan agree for every
label id of every corpus kernel, and that no table outlives the compile.

### LOW-9 — documentation

- `backend_wgpu_surface.cyr` called the surface record 80 bytes (it is 88).
- `NvSurface`'s header said 288 (it is 296; every write fits).
- `native_kms_add_fb2`'s comment said 100 bytes (104 since the ADDFB2 fix).
- `NV_SASS_MAX_BYTES`' comment said the selector holds 512 records (1024 since the id space
  widened).
- `gpu_surface_acquire` now says that on wgpu the returned texture belongs to the surface: don't
  release it, and don't use it after the present. No consumer in the tree releases it.

## Reviewed and found sound

- **ADDFB2 / GETCRTC / SETCRTC:**
  - `drm_mode_fb_cmd2` is 104 B with `modifier[]` at +72, ioctl 0xC06864B8,
    `DRM_MODE_FB_MODIFIERS` = 2;
  - GETCRTC is 0xC06864A1 (104 B);
  - the packers validate their arguments;
  - the save is zeroed on failure, and the restore falls back to disabling the CRTC.
- **Block-linear:**
  - `native_nv_bl_modifier` matches `DRM_FORMAT_MOD_NVIDIA_BLOCK_LINEAR_2D(0,1,2,0x06,h)` bit
    for bit;
  - `drm_nouveau_gem_new`'s tile mode and flags are at +32 / +36, and the VM_BIND op is 40 B
    with the kind in the flags' low byte;
  - pitch, size and block height mirror the kernel's `nouveau_check_bl_size`, on u16 mode
    dimensions, so they cannot overflow;
  - the swizzle reads stay under `height × lin_pitch`, and its writes total exactly the BO size;
  - the copy-engine method writes the 80 bytes it declares;
  - every failure path in the tiled-FB setup unwinds once.
- **The surfaces:**
  - the AMD 232-byte and NVIDIA 296-byte records fit their offsets, and the 104-byte saves
    fit;
  - the double buffer releases each FB once;
  - the recorded refusal messages are bounded (worst case about 176 of 192 bytes);
  - the logind fd is released and closed exactly once, after the KMS teardown.
- **wgpu surface:**
  - a second acquire returns the held texture without asking wgpu again;
  - a null success texture is refused;
  - a failed acquire releases what came back with it;
  - the frame drop is idempotent;
  - the MB5 and older records are told apart by +56;
  - no write reaches past +87 of 88;
  - every new wgpu call takes scalar or pointer arguments only, so no shim is needed.
- **The include chain and manifest:** `src/lib.cyr` and `cyrius.cyml [lib].modules` list the same
  modules, the four `sm75_*` included.

- **The compilers:**
  - the table builders take their capacity from their lengths and reject `id_bound` past it
    before any memset, and every lookup is bounded by `id_bound`;
  - labels must be `0 < id < id_bound`;
  - phi copies are bounded (64 per edge, under `MIR_CB_MOVES_MAX`);
  - `mir_mod_init`'s 1024 clamp matches `vals` / `instrs` in both compile frames;
  - `gfx9_isel`'s region depth is checked before each push, and every emit checks its cap;
  - `gfx9_emit_program` checks label ids where they are recorded and where they are patched,
    with 32 bytes of room per record;
  - the regalloc tables stay below their caps;
  - SM75 rejects `id_bound` > 256, bounds its label tables, predicates (P0–P6), barriers (16)
    and bindings (16), and checks the SASS size before any write;
  - every compile frame is under Cyrius's stack-array budget.

## External CVE sweep

Since the 2026-11-16 sweep:
- **Mesa 26.2.7** is a bug-fix release: crash, corruption and leak fixes, no new features, and
  no security fix named.
- **Linux 7.3.4.** The recent amdgpu CVEs are in the user-queue (`userq`) and amdkfd ioctls,
  which mabda does not call; it submits through `AMDGPU_CS`. The nouveau item is a leak on a
  failed device init. AMD's November 2026 graphics bulletin (AMD-SB-6028) is a driver and
  firmware matter outside mabda's code. The box runs the updated kernel.
- **wgpu-native / wgpu-core / naga:** no new advisory. wgpu-native is still v29.0.1.1.
- **samvada:** DEP-1 above.
