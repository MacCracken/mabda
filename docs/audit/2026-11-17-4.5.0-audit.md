# Mabda Security Audit — 2026-11-17 (4.5.0, textures + language)

**Scope.** The 4.5.0 diff against the `4.4.0` tag (about 4,300 source lines added), weighted
toward what crosses a trust boundary:

- **untrusted asset input:**
  - KTX2 Zstandard / ZLIB supercompression, decoded through consumer-registered decoders
    (`src/asset_load.cyr`);
  - the KTX2 / DDS sRGB container mapping (`src/asset_format.cyr`) and the eight new format ids
    (`src/texture_format.cyr`);
  - the BC7 encoder and decoder (`src/texture_bc7.cyr`, new);
- **native AMD GPU memory and the kernel:**
  - the render graph's native backing (`rg_build_ctx`: one GTT allocation, transients as views)
    and the executor's waits (`src/render_graph.cyr`);
  - multi-slot pending waits and the multi-entry TIMELINE_WAIT chunk (`src/queue.cyr`,
    `src/backend_native_amdgpu.cyr`, the four submit sites in `src/backend_native.cyr`);
  - the sRGB number format in the T# (`src/backend_native_shaders.cyr`);
- **the cyrius 6.7 language sweep**, for behaviour changes: 2,126 constants as `const`, 34
  predicates as `bool`, 66 if-expression sites, plus the new wgpu sRGB format values.

**Method.**
- Three reviewers read the diff against the CLAUDE.md security checklist, split by trust
  boundary (assets, native memory and kernel, the language sweep). They wrote nothing and ran
  nothing on a GPU.
- Each finding was then traced again in the code before it was fixed, and each fix landed with
  a test that fails without it.
- A regression check of the 4.4.0 audit (`2026-11-17-4.4.0-audit.md`): the eleven tests it
  added still exist and pass, the hardware control-flow gate included.
- An external CVE sweep for what changed since this morning's 4.4.0 sweep.

## Verdict

**0 CRITICAL / 1 HIGH / 4 MEDIUM / 11 LOW, all fixed in 4.5.0** (LOW-10 by documenting the
contract mabda's other CPU state already has). Four of the five worst are in the native render
graph's new backing reuse; MED-4 is older (3.2.14) and the new waits made it likelier.

Two notes needed no change. A copy between compressed twins (BC7 ↔ BC7 sRGB) now passes the
format check and is refused one check later, with the same `GPU_ERR_TEXTURE` and a clearer
message. Masking the C `WGPUBool` to 32 bits in `wgpu_*_has_feature` is defense in depth.

### HIGH-1 — a node id indexed the sorted list after the build

`rg_build` sorts the graph's node vec in place. Every accessor that takes a node id
(`rg_node_set_pass`, `rg_node_queue_get`, `rg_node_batch_idx`, and `rg_node_reads` / `_writes` /
`_queue`) indexed that vec, so after the build an id named whichever node landed at that sorted
position. 4.5.0's own guide says to call `rg_node_set_pass` after the build, with the id
`rg_add_render` returned.

Take A writing X, B reading X, and an independent C. Kahn's order is A, C, B, so
`rg_node_set_pass(g, B, pB)` set C's pass. C then drew into B's target at C's place in the
order, without B's waits. With aliasing on, that write could hit bytes a previous occupant was
still using.

**Fix.** The graph keeps its nodes in insertion order too (`by_id`, RenderGraph +72), and every
id-taking accessor resolves through `_rg_node_by_id`. The test builds exactly that graph,
checks that the sorted order really is A, C, B, and sets both passes.

### MED-1 — supercompressed KTX2 was a decompression bomb

A stored level must be in the file, so a stored file bounds its own size. A supercompressed
level's size comes only from the header (`uncompressedByteLength`, which must equal the
format's level size). sankoch's zstd honours an RLE block, so about 4 input bytes become
128 KiB. A file of about 256 KiB could declare an 8192 × 8192 RGBA16F array with 16 layers. It
would then take an 8 GiB anonymous mapping and seconds of CPU, and load successfully as an
8 GiB texture, which is system RAM on an APU.

**Fix.**
- A supercompressed file whose levels decode past a budget is refused with
  `GPU_ERR_OUT_OF_MEMORY` before anything is created, and the reason goes on the error channel.
- The budget defaults to 1 GiB (`KTX2_MAX_DECODED_DEFAULT`). That holds every 2D texture of up
  to 8192² in any mabda format with a full mip chain (RGBA16F's is about 683 MiB).
- `gpu_ktx2_set_max_decoded_bytes(n)` sets it (`n <= 0` restores the default), and
  `gpu_ktx2_max_decoded_bytes()` reads it. Stored files are not limited.
- The test pins the boundary: one byte past the budget is refused before any texture is
  created, exactly the budget loads, and a stored file loads under a 1-byte budget.

### MED-2 — only the first user of a reused slot waited

The executor added the previous occupant's waits before the first user of the transient that
took over its slot. A later user with no edge to that first user got none.

For example: n0 on GRAPHICS reads x (its last use); n1 on COMPUTE writes y, which takes x's
bytes, and waits; n2 on GRAPHICS also writes y, waits for nothing, and could overlap n0 still
reading x. 4.5.0's own premise is that same-ring submits may overlap, and different rings
certainly do.

**Fix.** Every node that reads or writes a transient with an `alias_of` waits for every queue
that used the previous occupant (`_rg_alias_waits`). The test is that graph: two barriers, one
before each writer.

### MED-3 — inputs and outputs could share bytes

The planner gave each transient the interval from its first to its last user. Two failures
followed:
- An INPUT, read by its first user and filled by the CPU after the build as the guide says,
  could take over the slot of a transient that an earlier node writes. That node then
  overwrote the fill before the input's reader ran.
- An OUTPUT, written by its last user and read after the graph, could hand its slot to a later
  transient.

**Fix.** A transient whose first user reads it is planned from node 0. One whose last user writes
it is planned to the last node (`plan_first` / `plan_last`, TransientResource +112 / +120).
Scratch that is written and then read still reuses. The test checks both rules and that
scratch still reuses.

### MED-4 — IB slices reused without a wait (since 3.2.14)

The native executor stages each node's command stream into the next of 16 IB slices. Past 16
nodes, node k + 16 overwrote node k's slice while node k's submit could still be pending, and
the GPU would then run a half-overwritten stream. The code's own comment said the executor
"must have retired" those submits, and it did not. 4.5.0's new waits keep more submits pending,
which made this likelier.

**Fix.** When the cursor wraps to slice 0, the executor waits for every queue it uses to go idle.
- The CPU test: 17 nodes give one drain after the sixteenth dispatch, then the final one.
- The hardware gate's new phase D: a 20-node chain over 21 aliased buffers in two slots, every
  element right. It exercises the path, but cannot provoke the race reliably.

### The LOWs
- **LOW-1, the BC7 API's buffers.** `mabda_bc7_encode` read `(height - 1) × pitch + width × 4`
  bytes, and `mabda_bc7_decode` wrote them, with no length for that buffer. Fix:
  - they take `src_len` / `dst_len`, a change to an API that was not yet released;
  - they check the pitch divide-first, `pitch ≤ (len − width × 4) / (height − 1)`, so a huge
    pitch cannot overflow.
- **LOW-2.** A 104-byte header made a full-size GPU allocation before its first bad level entry
  was found. A pre-pass (`_ktx2_check_levels`) checks every entry, and the budget, first.
- **LOW-3.**
  - The decoder is read once.
  - A decoded level now ends exactly where a `PROT_NONE` page begins, so a decoder that writes
    past its buffer faults instead of silently corrupting the next mapping.
- **LOW-4.** `_ktx2_unmap` checks `cyr_munmap` and records a failure.
- **LOW-5.**
  - `rg_release` now unbuilds the graph. Execute refuses it, and a rebuild works.
  - It zeroes every view a consumer payload may still hold, so one names handle 0 / VA 0, which
    every native path refuses, not a freed BO.
  - Views are registered, and the native buffer / texture / target release slots refuse one.
    Releasing a view would GEM_CLOSE the shared handle, and `rg_release` would then close it a
    second time, by then perhaps another BO's.
- **LOW-6.** `rg_execute_mq` refuses a null graph (`rg_is_built` and the counts are null-safe).
  It refuses with `GPU_ERR_OTHER` a graph `rg_build_ctx` built on another context, whose views
  name that context's memory.
- **LOW-7.**
  - The executor stops at the first failed wait or dispatch, since later nodes read what that
    node would have written, and still drains its queues.
  - `rg_node_reads` / `_writes` / `_queue` return 1, changing nothing, after the build or for a
    bad id. The first two returned 0 for both.
- **LOW-8.** A timeline submit the kernel refused never signals the point it reserved. Every
  later wait on that queue then timed out, and the next submit lost the dependency.
  `_native_submit_undo` gives the point back and restores the waits, at all four submit sites.
- **LOW-9.** The backing checks `native_tex_view_init` and releases everything on a refusal.
- **LOW-10.** The BC7 search keeps its state in module globals. mabda treats its CPU state as
  single-threaded (the error slots say so), and `mabda_bc7_encode` now says it too.
- **LOW-11.**
  - The DDS and KTX2 parse buffers are 64 bytes, as every caller already allocated.
  - `texture_format.cyr`'s overflow note names RGBA16F (512 MiB) as the largest size.
  - `_asset_per_image_size` and its test are removed: nothing in `src/` has called it since 4.5.0
    sized layered KTX2 levels from the format.

## Regression check (2026-11-17, 4.4.0)
All eleven tests the 4.4.0 audit added are present and pass:
- the waitcnt-before-branch and control-flow ISA tests;
- the label table;
- the uniform-mask refusal;
- the CRTC pick, flip wait and present-rc mapping;
- the SM75 error-operand refusal;
- the hardware `test-native-spirv-control-flow-e2e` (`wait_skipped_only_use`).

## External CVE sweep

Since this morning's 4.4.0 sweep, the box is unchanged: Mesa 26.2.7, Linux 7.3.4.
- **CVE-2026-68111** (drm/amdgpu gfx9) is a kernel hardening fix: `BUG_ON` → `WARN_ON` in
  `gfx_v9_0.c`, announced in August. It was fixed in 6.6.148 / 6.12.101 / 6.18.42 / 7.1.6 /
  7.2-rc2, so 7.3.4 has it. mabda has no code on that path.
- The other recent amdgpu items stay in the user-queue and amdkfd ioctls mabda does not call, or
  in AMD's driver-and-firmware bulletin (AMD-SB-6028), both covered this morning.
- **Mesa 26.2.x:** no new RADV security fix.
- **wgpu:** CVE-2026-6773 (buffer bounds via integer overflow in wgpu-core) was assessed in the
  2026-11-16 audit. mabda's wgpu path validates its own sizes before calling. No new wgpu-native
  advisory.
- **samvada 1.1.2 and chitra 1.4.1** are still their latest releases.
