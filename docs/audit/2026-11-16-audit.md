# Mabda Security Audit — 2026-11-16 (4.3.0, render tier MB1 + the 2026-11 repairs)

**Scope.** The 4.3.0 diff, weighted toward what crosses a trust or ABI boundary:

- the launcher revision (`deps/wgpu_main.c`, 67 → 81 slots): the uncaptured-error callback and
  record, the error-scope shim, the finish shim's own scope, the submit shim's release, the
  viewport / Wayland-surface / surface-capabilities / debug-group shims, the slot-count handshake
  and the table-size guard;
- the Cyrius wrappers for slots 67–80 (`src/wgpu_ffi.cyr`) and the old-launcher gate;
- every new descriptor writer (`src/backend_wgpu_rtier.cyr`): bind group layouts, bind groups,
  sampler objects, pipeline layouts, render pipelines, the per-context scratch block, and the
  rewritten pass begin and textured draw (`src/backend_wgpu.cyr`);
- the public builders that take consumer data (`src/gpu_bind.cyr`, `src/gpu_pipeline.cyr`,
  `src/gpu_draw.cyr`, `src/error_scope.cyr`);
- the repairs: `gpu_copy_bytes` / `gpu_buffer_map`, the NVIDIA binding array and shader-kind gate,
  the profiler's pass list and exports, the wgpu texture readback's row padding, the native
  render-tier subset, the five appended format ids.

**Method.** One reviewer reading the diff against the CLAUDE.md security checklist (input
validation, buffer safety, integer overflow, divide-by-zero, syscall returns, pointer validation,
FFI descriptor offsets, shim correctness), plus a regression check of the prior audit and an
external CVE sweep. Every v29 struct offset the diff writes was taken from the compiler with
`offsetof` against `deps/wgpu-native/include/webgpu/webgpu.h` (v29.0.1.1), not from comments; the
offsets are cited in the module headers and pinned byte for byte by `tests/tcyr/render_tier.tcyr`.

## Verdict

**0 CRITICAL / 0 HIGH / 2 MEDIUM / 2 LOW — all fixed in 4.3.0.** Two of them are pre-existing
descriptor-layout defects this release's offset check exposed; one is a wrong success code; one
is a hardening of a margin that held.

| ID | Severity | Where | Status |
|---|---|---|---|
| MED-1 | Medium | `src/vertex.cyr`, `src/instancing.cyr` — pre-v29 `WGPUVertexAttribute` layout and `Float32x*` values | **Fixed**, test |
| MED-2 | Medium | `src/bind_group.cyr` — `bglb_texture_2d` / `bglb_sampler` / `bglb_comparison_sampler` wrote into the sub-structs' `nextInChain` | **Fixed**, test |
| LOW-1 | Low | `src/backend_wgpu.cyr` — `_backend_wgpu_buffer_write` checked nothing and returned 0 for writes WebGPU rejects | **Fixed**, CPU + HW test |
| LOW-2 | Low | `src/profiler.cyr` — export buffers sized below the formatter's documented bound | **Hardened**, test |

### MED-1 — the vertex attribute layout was pre-v29

`WGPUVertexAttribute` is 32 bytes in webgpu.h v29 (`nextInChain` +0, `format` +8, `offset` +16,
`shaderLocation` +24). `_vertex_attr` wrote a 24-byte record with the format at +0, and
`WGPU_VERTEX_FORMAT_FLOAT32X2/X3/X4` were 21/22/23 — in v29, 21 is `Unorm16x4` and Float32x2–x4
are 0x1D–0x1F. A consumer handing `vertex2d_attributes()` / `vertex3d_attributes()` /
`instance_data_attributes()` to wgpu would have passed its format word as a `nextInChain`
pointer: wgpu dereferences a chain pointer, so a non-null garbage value is a wild read. Nothing
reached this before 4.3.0 only because the old builder ignored vertex layouts (`rpb_build`).
**Fix:** the v29 layout and values; `tests/tcyr/graphics.tcyr` pins them.

### MED-2 — the legacy bind-group-layout builders wrote into `nextInChain`

In v29 `WGPUBindGroupLayoutEntry` carries `bindingArraySize` at +24, so its `texture` sub-struct
starts at +72 with its own `nextInChain`, and `sampleType` / `viewDimension` are at +80 / +84; the
`sampler` sub-struct starts at +56, its `type` at +64. `bglb_texture_2d` wrote sample type 1
(v29: Undefined) at +72 and the dimension at +76; `bglb_sampler` / `bglb_comparison_sampler`
wrote 1 / 3 (v29: Undefined / NonFiltering) at +56 — non-null values in two `nextInChain`
pointers, the same wild-read class as MED-1. The `wgpu_bgl_entry_*` helpers in
`src/wgpu_descriptors.cyr` were already correct; the `bglb_*` builders had not been routed
through them. **Fix:** routed through the helpers / the v29 offsets and values;
`test_legacy_bglb_v29` pins the bytes.

### LOW-1 — the wgpu buffer write returned success for writes WebGPU rejects

`_backend_wgpu_buffer_write` called `wgpuQueueWriteBuffer` with no checks. A write WebGPU
rejects (offset or size not a multiple of 4, past the end, a null buffer or source) returned 0;
the rejection went to the uncaptured-error callback (before this release's error channel,
wgpu-native's default handler: an abort). Hardware probe on the Cezanne, before the fix: a 6-byte
write returned 0 and the process continued. **Fix:** the WebGPU rules checked before the call,
`GPU_ERR_BUFFER` returned; `test_wgpu_buffer_write_guards` (CPU) and `error_channel_e2e` case 7
(HW). The native backends already bounds-checked their writes and take any byte size.

### LOW-2 — the profiler exports' buffers relied on the precision

`profiler_export_json` reserved 64 bytes per pass and `profiler_export_history_csv` 48 per line.
At the exports' 3 decimals a float prints in at most 24 bytes, so the worst case fit (52 of 64,
46 of 48), but only by that precision; `fmt_float_buf` documents a 43-byte bound. **Hardened:** the
reservations now follow the formatter's bound (256 + 96 + 2 x label length per pass; 72 per CSV
line); `test_profiler_l24_export_worst_case_fits` checks the string and its NUL fit.

## Reviewed and found sound

- **Launcher.** `copy_string_view` clamps to `cap - 1` and NUL-terminates (`WGPU_STRLEN` handled);
  `wgpu_shim_take_uncaptured_error` copies at most `cap - 1`; `wgpu_shim_pop_error_scope` tolerates
  a NULL buffer and returns -100 if the callback never fires (bounded poll, 64 iterations); the
  finish shim's message buffer is a fixed 2 KiB stack array copied whole into the record; the
  surface-capabilities shim zeroes its output and copies at most 16 / 8 / 8 entries, reporting
  true counts; the debug-op shim refuses a NULL encoder and unknown target / op; the submit shim
  skips NULL. `build_fn_table` aborts at start-up if the table and `FN_COUNT` disagree. The
  uncaptured-error record is process-global and not synchronized: wgpu-native reports errors on
  the calling thread, and mabda's error API is documented single-slot like the shader-error slot.
- **Old launchers.** Every wrapper for slots 67–80 checks `_wgpu_has_slot`; without the
  handshake mabda assumes 67 slots, so a consumer on an old launcher gets `GPU_ERR_FFI_SYMBOL`
  (or the documented null result) instead of a call through memory past the table.
- **Scratch block.** `_WGPU_RS_*` offsets checked against their contents: 16 x 120 B layout
  entries, 16 x 56 B group entries, a 64 B descriptor slot (the largest user is the 64 B sampler
  descriptor), 8 x 40 B vertex buffer layouts, 8 x 16 x 32 B attributes, 8 x 32 B targets, 8 x 24 B
  blends, and the 48 B pass record within its 64 B slot; the last field ends at 8392 of 8448. The
  builders cap what feeds them (16 layout / group entries, 8 vertex buffers, 16 attributes in
  total, 8 targets, 4 groups) before the scratch is written. wgpu copies descriptors during the
  create call, so reuse is safe; the pass record is reused only when free, else allocated.
- **Consumer data.** Bindings < 1000, stage bits within `GPU_STAGE_*`, duplicate bindings and
  locations refused, strides ≤ 2048 and 4-aligned, attributes inside the stride, dynamic offsets
  ≤ 12 and 256-aligned, index offsets aligned to the index size, `base_vertex` within i32, scissor
  within u32, viewport positive with depth in [0, 1]. Entry-point and label strings go through
  `wgpu_string_view` (length capped by `_wgpu_strnlen`).
- **Integer math.** `_backend_wgpu_texture_read`: width and height are ≤ 8192, so the padded row is
  ≤ 32 KiB and the staging size ≤ ~256 MiB, far inside i64. The NVIDIA param writes stop at
  `0x160 + 16 x 8 = 0x1E0`, inside the 0x200 bank. The profiler's pass buffer doubles from 8.
  No new divisor that can be zero (`GPU_DYNAMIC_OFFSET_ALIGN` and the index size are constants).
- **Context layout.** `GPU_CONTEXT_SIZE` grew 184 → 208 (+184 scope depth, +192 pending table,
  +200 render state); no backend's own fields reach 184 (NVIDIA's end at +120, AMD's at +176). Every
  test that sized a stack context by literal was moved to 208; `check-stack-array-sizing` reports
  0 out-of-bounds writes over 12,525 checked.
- **`gpu_copy_bytes`.** Wide moves only when both pointers share 8-byte (or 4-byte) alignment;
  checked equal to `memcpy` for every length 0..96 x every source and destination alignment 0..7,
  with nothing written past `n`.
- **NVIDIA.** A binding array whose count is not the module's declared count is refused before
  any write or ioctl (CPU-tested with a stack context that has no fd); non-SASS modules are
  refused before any BO is allocated.

## Regression check — prior findings

The 2026-09-16 findings (MED-1 SPIR-V `<id>` bound check, LOW-1 cached-dispatch trust, LOW-2 loader
leak) sit in code this release did not touch. The KTX2 CRITICAL-1 (2026-06-19) is untouched.

## External CVE sweep (since 2026-09-16)

- **wgpu / wgpu-native:** no advisory against wgpu-native found. Two Firefox CVEs cite wgpu-core:
  CVE-2026-12293 (a stale object reaching `RenderBundle::execute` on the **Metal** backend) and
  CVE-2026-6773 (fix in draft upstream). mabda uses no render bundles and runs Vulkan only;
  wgpu-native stays at v29.0.1.1 — re-check when it moves.
- **Mesa:** CVE-2026-40393 (out-of-bounds write via WebGPU shader input) is fixed in 25.3.6 / 26.0.1;
  both test boxes run Mesa 26.2.6. No RADV / NVK CVE found for September–November 2026.
- **Kernel amdgpu:** CVE-2026-68105 (panic on a failed driver load, August) and CVE-2026-43195
  (user queue sizes) are kernel-side; mabda's native path creates no user queues.
