# Mabda Security Audit — 2026-06-14

**Scope**: P(-1) scaffold-hardening pass against the **post-GA tree**
(tip of `main`, version 3.0.3). Full-surface re-audit of all 38
`src/*.cyr` modules (~12,500 lines) — not just a delta — covering the
dual backend (wgpu + native AMD), the v3 public dispatchers, the cache
trio, the FFI descriptor layer, and the native DRM/KMS/PM4 paths. This
is the first audit since 3.0.0 GA shipped (2026-06-02) and the first
since the cyrius 6.0 → 6.2 toolchain jump and the samvada 0.2.2 → 0.4.1
dependency bump.

**Auditor**: internal (multi-agent fan-out: 10 dimension-focused
finders + 2-lens adversarial verification per candidate + 2 regression
agents + 2 external CVE-sweep agents; 60 agents total).
**Audited revision**: `main` @ 3.0.3, 2026-06-14.
**Method**: per-dimension code walk of the full source against the
`CLAUDE.md` security-hardening checklist (input validation, buffer
safety, integer overflow, divide-by-zero, syscall-return handling,
pointer validation, FFI offset review, fncall6 avoidance), with every
candidate finding adversarially re-verified by two independent skeptics
(a correctness/reachability lens and a false-positive-hunt lens) before
inclusion. Trust model unchanged: **library called by trusted consumer
code**, but the native AMD backend is a GPU client of the kernel —
malformed ioctl/PM4 payloads can fault the amdgpu/DRM driver, so the
defensive posture applies **inward** (toward the kernel) as well as
outward. Plus an amdgpu/DRM + wgpu/WebGPU CVE sweep for
2026-04-30 .. 2026-06-14.

### The systemic theme

The dominant new pattern is a **validation regression introduced by the
v3 backend-abstraction layer**: several public v3 dispatchers
(`gpu_texture_create_2d_rgba8`, `gpu_compute_dispatch`) were added as
thin `ctx->backend->slot` pass-throughs and **dropped the input
validation their v2 siblings (`texture_create_rgba8`,
`compute_dispatch`) still enforce in the same file**. The gap is
sharpest on the native AMD path, where unvalidated dimensions/counts
reach kernel GEM_CREATE ioctls and PM4 command submission with no
clamp. [HIGH-1], [MED-3], and the two native-overflow MEDIUMs are all
instances of this one architectural slip. The fix is uniform: make the
v3 dispatchers validate like their v2 siblings, and add the matching
guard at the native size/dispatch math.

The external CVE sweep independently corroborates this theme: the
in-window Dawn WebGPU integer-overflow CVEs (CVE-2026-4453,
CVE-2026-7973, CVE-2026-11077) and the amdgpu CVE-2026-23468 (BO-list
entry-count) are all the same "unvalidated user dimension/count feeding
allocation/ioctl" class.

## Findings

### [HIGH-1] `gpu_texture_create_2d_rgba8` validates neither upper dimension bound nor `width*height*4` overflow

- **File**: `src/texture.cyr:224-229` (+ native `backend_native.cyr:435-443`, `native_texture_size_2d_rgba8`)
- **Class**: CWE-1284 (Improper Validation of Specified Quantity) / CWE-190 (Integer Overflow)
- **Confidence**: 0.82

The v3 public dispatcher only guards `ctx == 0` and forwards
consumer-supplied `width`/`height` straight to `ctx->backend->slot`.
The v2 sibling `texture_create_rgba8` (lines 61-69) **in the same file**
enforces `width <= 0` / `height <= 0` and `validate_dimensions(...,
MABDA_MAX_TEXTURE_DIM_2D = 8192)`. The v3 entry omits all of it. On the
native backend the forwarded values flow through
`native_texture_size_2d_rgba8` (`return width * height * 4;`, no guard)
→ `native_bo_create_gtt` → `native_gem_create`, so an oversized or
overflowed size reaches a kernel `GEM_CREATE` ioctl + `mmap`.

**Impact**: missing validation on consumer-controlled texture dimensions
feeding a kernel ioctl; cross-backend behavior diverges from the 8192
cap honored elsewhere in the file.

**Fix**: add the v2 guards (positivity + upper bound + `width*height*4`
overflow guard) to `gpu_texture_create_2d_rgba8`, and a matching guard
in `native_texture_size_2d_rgba8`.

### [HIGH-2 NEW] logind-acquired DRM master fd leaked on the success-then-release lifecycle

- **File**: `src/surface_v3.cyr:184-197` (`gpu_surface_release`)
- **Class**: CWE-772 (Missing Release of Resource) / CWE-404
- **Confidence**: 0.85

Distinct from prior HIGH-2 (which fixed the *configure failure* paths).
On the **success** path, `gpu_surface_configure_native_logind` acquires
a master fd via `samvada_session_take_device` that **mabda owns**, and
stashes it only on the ctx (`ctx+104`). The release lifecycle never
gives it back: the native SURFACE_RELEASE slot tears down FBs/CRTC/BOs
but never `sys_close`s `card_fd` nor calls
`samvada_session_release_device`; then `gpu_surface_release`
unconditionally zeros the stash (line 195). The fd is now leaked **and
unrecoverable** by the consumer. The release comment ("Does NOT close
consumer-supplied fds … those stay with the caller") is correct for the
kiosk path but is the reasoning error for the logind path, where the fd
is *not* consumer-supplied.

**Impact**: every successful `configure_native_logind` → `release` cycle
leaks one fd **and** holds DRM master for the process lifetime. A
long-running compositor (aethersafta) that reconfigures on
mode-change/hotplug accumulates leaked master fds (RLIMIT_NOFILE) and
blocks every later `SET_MASTER` (`-EBUSY`/`-EACCES`) — degrading the
whole display stack, not just this process.

**Fix**: track fd provenance on the ctx (an "owned-by-mabda" flag +
the minor used). In the release path, if the fd was logind-acquired,
`samvada_session_release_device(major, minor)` + `sys_close(fd)` before
zeroing the stash. Kiosk fds stay untouched.

### [HIGH-3] WGSL shader source silently truncated at 4096 bytes

- **File**: `src/wgpu_descriptors.cyr:176-182` (root) + `src/backend_wgpu.cyr:154-162` (actionable call site) + `src/compute.cyr:56` (legacy path)
- **Class**: CWE-130 (Improper Handling of Length Parameter) / CWE-241
- **Confidence**: 0.85

`wgpu_shader_source_wgsl` builds the `WGPUShaderSourceWGSL.code`
StringView via `wgpu_string_view`, which derives length from
`_wgpu_strnlen(cstr, WGPU_LABEL_MAX_BYTES)` where `WGPU_LABEL_MAX_BYTES
= 4096`. That ceiling is meant for debug **labels** but is applied to
the shader **source**. The public entry
`gpu_shader_module_create(ctx, bytes_ptr, n)` carries the correct byte
length `n` all the way to `_backend_wgpu_shader_module_create` — which
even guards `n <= 0` — then **discards `n`** and re-derives a 4096-capped
length. wgpu-native reads exactly `StringView.length` bytes, so any WGSL
≥ 4 KiB is handed to the compiler truncated mid-token. The code comment
at `backend_wgpu.cyr:148-152` flags this as a known "Step-3 follow-up"
— it shipped anyway.

**Impact**: any non-trivial WGSL shader (common in rasa/bijli/soorat) is
silently truncated → either shader-create fails (dispatch silently
no-ops) or, if the truncation lands on a complete prefix, a *different*
shader compiles → wrong GPU results with no error. Breaks cross-backend
identity (native reads `bytes_ptr`/`n` as raw ISA with no cap).

**Fix**: add `wgpu_shader_source_wgsl_len(bytes_ptr, n)` using the
existing `wgpu_string_view_len`, and call it from
`_backend_wgpu_shader_module_create` with the `n` already in scope. Keep
the 4 KiB strnlen cap for labels only. Repair the `compute.cyr` legacy
path too.

### [HIGH-4] Caller-supplied cache keys `0` and `0xFFFFFFFFFFFFFFFF` collide with `map_u64` reserved sentinels

- **File**: `src/pipeline_cache.cyr:13-23`, `src/bind_group_cache.cyr:13-23`
- **Class**: CWE-697 (Incorrect Comparison) / CWE-457
- **Confidence**: 0.85

Both caches are thin pass-throughs to the stdlib `map_u64_*` API with a
**caller-supplied u64 key**. `lib/hashmap.cyr` reserves two key values
in-band: `MAP_U64_EMPTY = 0` and `MAP_U64_TOMB = 0xFFFFFFFFFFFFFFFF`,
and its header explicitly warns consumers to pre-shift keys that could
be 0 or u64::MAX. Neither mabda cache pre-shifts. A stored key of
`0xFFFF…F` reads back as TOMB and is never matched (set "succeeds", all
gets miss → cached handle silently lost). A stored key of `0` reads back
as EMPTY → also always misses, **and** `map_u64_set_a`'s `was_new`
logic treats the slot as empty on every overwrite, inflating the size
counter and corrupting load-factor/grow timing (confirmed by reading
`map_u64_set_a`). Keys are u64 hashes the caller folds from descriptor
fields, so an XOR-cancelling descriptor or all-ones fold readily yields
a sentinel. The existing `test_pipeline_cache_large_key` uses
`0x7FFFFFFFFFFFFFFF` (max i64, **not** the u64 sentinel), so neither
case is exercised.

**Impact**: silent cache corruption for two key values — get/has always
miss, defeating dedup (per-frame resource re-creation) and, for key=0,
corrupting the map's accounting.

**Fix**: remap caller keys out of the reserved range at the cache
boundary (e.g. XOR a fixed nonzero constant, applied symmetrically in
set/get/has) in both `pipeline_cache` and `bind_group_cache`. Add
round-trip assertions for both sentinel key values.

### [MED-1] Native texture create has no upper-dimension cap; `width*height*4` can overflow before GEM_CREATE + mmap

- **File**: `src/backend_native.cyr:435-443`, `native_texture_size_2d_rgba8` (`:955-957`)
- **Class**: CWE-190. **Confidence**: 0.6

`_backend_native_texture_create_2d_rgba8` validates only `<= 0`. The
native-side companion to [HIGH-1]: a wrapped size flows into
`native_gem_create` + `cyr_mmap`. Wrap-to-small under-allocates a BO
relative to the consumer's pixel dimensions (the size is reused
consistently for create/map/write, so it's a wrong-size allocation
rather than a heap overflow). **Fix**: cap dims + overflow-guard
`width*height*4` before `native_bo_create_gtt`. (Folds into the [HIGH-1]
fix.)

### [MED-2] Native render-target create has no upper-dimension cap; same overflow before GEM_CREATE + mmap

- **File**: `src/backend_native.cyr:1046-1048, 1054-1064`, `native_rt_size_2d_rgba8`
- **Class**: CWE-190. **Confidence**: 0.6

`native_rt_create_2d_rgba8` rejects `<= 0` and odd dims (the MED-3 fix)
but applies no upper bound; `native_rt_size_2d_rgba8 = width*height*4`
can overflow. The RT struct stores width/height as u32 while size is
computed from full i64 dims, so a `> u32` dimension would disagree with
the allocated size. **Fix**: cap dims (`MABDA_KMS_MAX_FB_DIM` /
`MABDA_MAX_TEXTURE_DIM_2D`), overflow-guard the multiply, validate the
computed size fits the u32 fields. Resolves [LOW-5] too.

### [MED-3] `gpu_compute_dispatch` performs no x/y/z workgroup-count validation

- **File**: `src/compute.cyr:229-234` (+ native `backend_native.cyr:390-405`)
- **Class**: CWE-1284. **Confidence**: 0.78

Same regression as [HIGH-1] on the compute path. The v3 entry guards
only `ctx == 0` then `fncall6`s x/y/z into the slot; the v2 sibling
`compute_dispatch` (lines 107-114) validates `<= 0` and
`validate_dispatch(..., MABDA_MAX_DISPATCH_DIM = 65535)`. The native
slot doesn't validate either, so out-of-range counts reach PM4 dispatch
construction + CS submit. **Fix**: validate `<= 0` +
`validate_dispatch` in `gpu_compute_dispatch`; replicate the guard in
`_backend_native_compute_dispatch`.

### [MED-4] wgpu shader-module slot discards the explicit length `n` it is given

- **File**: `src/backend_wgpu.cyr:154-162`
- **Class**: CWE-130. **Confidence**: 0.85

The actionable call site for [HIGH-3] — `n` is validated then dropped.
Fixed together with [HIGH-3].

### [MED-5] `gpu_timestamps_new` stores buffer handles without null-checking `wgpu_device_create_buffer`

- **File**: `src/gpu_timestamps.cyr:72-94`
- **Class**: CWE-252 (Unchecked Return Value). **Confidence**: 0.8

The query-set create is null-checked (line 65) but the two
`wgpu_device_create_buffer` returns are stored into the wrapper (ts+8 /
ts+16) and `gpu_ok(ts)` returned without a check. On VRAM exhaustion /
oversized `max_passes` the caller gets `Ok(ts)` holding null handles;
`gpu_timestamps_resolve` / `_map` then deref a null buffer inside
wgpu-native. No CPU test coverage for `gpu_timestamps_*`. **Fix**:
null-check each create, releasing prior resources and returning
`Err(GPU_ERR_OTHER)`; add an Err-on-null-buffer assertion.

### [MED-6] Test redefines production `present_mode_to_wgpu` — validates a stale local copy

- **File**: `tests/tcyr/mabda.tcyr:1065-1071`
- **Class**: CWE-1059 (Insufficient Test Validation) / CWE-561. **Confidence**: 0.95

`mabda.tcyr` includes `src/lib.cyr` (→ `surface.cyr`, defining
`present_mode_to_wgpu` at :37) and then re-defines a byte-identical copy
at :1065. The build prints `warning: duplicate fn 'present_mode_to_wgpu'
(last definition wins)`, so `test_present_mode_mapping` binds to the
**test's** copy, not production. The suite passes only because the
bodies are currently identical — a future change to the real mapping
would pass silently. Also the only duplicate-fn warning in the test
build (noise against the zero-warning gate). **Fix**: delete the
duplicate fn + the redundant `WGPU_PRESENT_MODE_*` var decls from the
test so it exercises the real symbol.

### [LOW-1] `NativeRenderPipeline` header comment states wrong struct size (320 B) vs the real 644 B

- **File**: `src/backend_native.cyr:1124-1141`
- **Class**: CWE-805 / documentation drift. **Confidence**: 0.9

The comment says "320 bytes" with SH_BLOCK 48 B @ +32 and CTX_BLOCK
292 B @ +80; the constants say SH_BLOCK 56 B @ +32, CTX_BLOCK 556 B @
+88, `NATIVE_PIPE_STRUCT_SIZE = 644`. Runtime is **safe** (alloc uses
644; composers assert their emitted sizes), but the comment is the
canonical reference — following it would mis-size the alloc by ~324 B.
**Fix**: correct the comment block to the real layout.

### [LOW-2] `RenderTarget` header comment states "48 bytes" but `RENDER_TARGET_SIZE` is 64

- **File**: `src/render_target.cyr:5-15`
- **Class**: CWE-805 / documentation drift. **Confidence**: 0.85

Field map lists msaa_view @ +48 and depth @ +56 (through byte 64);
`RENDER_TARGET_SIZE = 64` and `rtb_build` allocs 64. Runtime safe;
comment total is stale. **Fix**: "(48 bytes)" → "(64 bytes)".

### [LOW-3] `surface_state_resize` accepts negative dimensions (v2 path)

- **File**: `src/surface.cyr:88-95`
- **Class**: CWE-1284. **Confidence**: 0.55

Guards `width == 0` / `height == 0` but not negatives; a negative i64
truncates to a huge u32 surface extent at the wgpu boundary.
`surface_state_new` validates nothing. The v3 dispatcher
(`gpu_surface_configure_wgpu`) is correctly guarded, so this is the
older v2 lifecycle only. **Fix**: `== 0` → `<= 0` in `surface_state_resize`;
add `<= 0` guards to `surface_state_new`.

### [LOW-4] `clock_gettime` return discarded; uninitialized `t_now` read regardless → garbage syncobj deadline

- **File**: `src/backend_native.cyr:407-410` and `:650-653`
- **Class**: CWE-252 / CWE-457. **Confidence**: 0.7

`var t_now[16];` (uninitialized), `syscall(228, 1, &t_now)` return
discarded, both halves read unconditionally to compute `deadline`. On a
(practically never) clock_gettime failure the deadline is computed from
uninitialized stack → spurious immediate timeout or near-unbounded
wait. Only place in the native files where a syscall return is discarded
**and** its output buffer is read regardless. **Fix**: `memset` +
check the return at both sites (factor a `mono_ns()` helper).

### [LOW-5] RT extent silently masked to 14/16 bits in CB_COLOR0_ATTRIB2 / MRT0_EPITCH with no upstream max-dim bound

- **File**: `src/backend_native_pm4.cyr:900-924` (prior_ref MED-2)
- **Class**: CWE-190 / CWE-682. **Confidence**: 0.55

The render-path twin of the (otherwise FIXED) prior MED-2:
`native_pm4_build_render_pass_target` masks `(rt_width-1)` to 14 bits
(ATTRIB2) / 16 bits (EPITCH); `native_rt_create_2d_rgba8` bounds neither
the max dim nor `width*height*4`. A width ≥ 16385 yields a BO sized from
the true width but a wrapped CB extent → GPU-visible surface metadata
disagrees with the BO (cross-backend pixel-identity break; no kernel-side
OOB since the BO is correctly sized). **Fix**: subsumed by the [MED-2]
dimension cap.

### [LOW-6] `gpu_timestamps_resolve`/`_map` clamp `query_count` above but not below zero

- **File**: `src/gpu_timestamps.cyr:116-143`
- **Class**: CWE-20 / CWE-191. **Confidence**: 0.7

`if (count > max) { count = max; }` with no lower bound; a negative
`query_count` survives and feeds `count * 8` as a huge unsigned size
into wgpu map/copy calls. **Fix**: add `if (count < 0) { count = 0; }`
(or error) before `count * 8` in both fns.

## Considered but not confirmed (dropped by adversarial verification)

These candidate findings were raised by a finder and **refuted** on
re-review — recorded for transparency and to mark the boundary of the
trusted-caller model.

| Candidate | Why dropped |
|-----------|-------------|
| `texture_upload_rgba8` overflow (texture.cyr) | upload validates `n == size` against the already-validated BO; the FP-hunt lens refuted reachability (0.78) |
| `gpu_render_target_create_2d_rgba8` no dim validation | correctness lens refuted (0.78) — the create path it forwards to is guarded; remaining concern is the native-size overflow, already captured as [MED-2] |
| `gpu_buffer_write` no off+n bounds vs buffer size | refuted (0.8) — wgpu validates the write extent; asymmetry with `gpu_buffer_read` is stylistic, not a defect |
| `gpu_buffer_create` no size bound | refuted both lenses — `wgpu_device_create_buffer` rejects oversized; trusted-caller |
| `_shader_hash` FNV output hitting a map sentinel | refuted (0.93) — probability-bounded ~2⁻⁶⁴ for a hash output (vs [HIGH-4], where the key is caller-supplied and trivially 0) |
| `bind_group_cache_clear` returns a fresh map | split verdict; the bump-allocator-GC comment is accurate for the documented reset model — behavior is intended, not a leak |
| profiler/instancing depend on `color_init()` | refuted both lenses — `color_init()` is a documented init-order prerequisite the consumer template calls |

The sharp `_shader_hash` (refuted) vs `pipeline_cache` (confirmed)
distinction is the verification working as intended: the shader cache
key is an FNV **hash** (astronomically unlikely to equal a sentinel),
whereas pipeline/bind-group keys are **caller-supplied** and a sentinel
value is readily produced.

## Disposition for the 3.0.4 hardening patch

**Fix in this pass** (each HIGH/MED lands with a regression assertion
per P(-1) step 7):

1. [HIGH-1] + [MED-1] — texture dim validation (v3 dispatcher + native size guard)
2. [HIGH-2 NEW] — logind master-fd release (provenance tracking)
3. [HIGH-3] + [MED-4] — WGSL explicit-length threading
4. [HIGH-4] — cache sentinel-key remap (pipeline + bind_group)
5. [MED-2] + [LOW-5] — native RT dim cap + overflow guard
