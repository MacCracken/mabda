# Mabda Security Audit — 2026-04-19

**Scope**: full P(-1) scaffold-hardening pass against Mabda 2.2.0, targeting
the 2.3.0 release — the last audit-gated stdlib-candidate release before
mabda is promoted to first-party trusted status.
**Auditor**: internal.
**Target release**: 2.3.0 (post-fix).
**Method**: code walk of every `src/*.cyr` module + wgpu-native / GPU-driver
CVE sweep (2024–2026), with the understanding that mabda's trust model is
"library called by trusted consumer code" rather than "parser of network
input" — the attack surface is narrower than yukti's.

## Summary

| Severity  | Count | Disposition                               |
|-----------|-------|-------------------------------------------|
| CRITICAL  | 0     | —                                         |
| HIGH      | 2     | Fix required before 2.3.0                 |
| MEDIUM    | 6     | Fix required before 2.3.0                 |
| LOW       | 6     | Schedule; defense-in-depth fixes          |
| Total     | 14    |                                           |

Mabda has **no memory-unsafe language primitives** (no raw pointer
arithmetic in user code; struct access is `load64`/`store64` with named
offset constants) and **no libc**. The FFI to wgpu-native is wrapped in
a C launcher (`deps/wgpu_main.c`) so all integer-sized args flow
through `fncall2`/`fncall5` shims — not directly through `fncall6`
which has a known ABI crash with wgpu-native (see
`feedback_fncall6_wgpu` memory).

The two HIGH findings are both latent bugs that test coverage never
reached: a duplicate-function-name shadow in the surface path
(SurfaceState presentation is structurally wrong — `_configure` calls
the presentation function by mistake) and a 4-byte heap overflow in the
legacy render-pipeline builder's label setter. Neither is
remote-reachable (the library runs in the consumer's process), but
both are structural correctness defects that must not ship as a
first-party trusted dep.

The MEDIUM findings cluster around two patterns: **integer arithmetic
without overflow guards** (texture / storage-buffer size math,
growable-buffer doubling) and **missing zero / divisor checks** in
workgroup math. Consumers passing attacker-influenced dimensions (a
textured image from an unvalidated PNG, a workgroup size from a shader
config file) are the threat model.

---

## Methodology

1. **Attack-surface enumeration**. Mabda's external input boundaries
   are:
   - Consumer-provided WGSL shader source (passed to wgpu-native
     shader compiler; mabda does not parse)
   - Consumer-provided texture pixel buffers (`texture_from_rgba`,
     `texture_upload_rgba8`) — width / height / data pointer / size
   - Consumer-provided buffer sizes (`create_*_buffer`,
     `storage_buffer_*`, `growable_buffer_update`)
   - Consumer-provided descriptor fields (bind groups, render passes,
     compute dispatches)
   - Consumer-provided labels (passed through to wgpu-native as
     `WGPUStringView`)
   - The wgpu-native function table (populated by the launcher —
     trusted, written by the consumer)
   - `syscall(228, …)` for `clock_gettime` in the profiler (kernel
     boundary)

2. **Code walk** per surface with checklist: input validation, buffer
   safety, pointer arithmetic, integer overflow, descriptor-struct
   offset correctness, FFI return-value handling, resource leak on
   error paths.

3. **CVE sweep** of the last 24 months in adjacent domains:
   wgpu-native, WebGPU spec, Vulkan / Metal / DX12 driver bugs, image
   decoder and shader compiler classes. Cross-referenced each
   applicable class against mabda.

4. **Findings triaged** with severity per the ladder in
   `CLAUDE.md`: CRITICAL (exploitable immediately) / HIGH (moderate
   effort) / MEDIUM (specific conditions) / LOW (defense-in-depth).

## Findings

### [HIGH-1] `surface_state_present` name collision → `_configure` calls the wrong function

- **File**: `src/surface.cyr`
- **Lines**: 53 (accessor), 80 (caller), 123 (mutating function)
- **Class**: CWE-694 (use of multiple resources with duplicate identifier)

**Description**. Two functions share the name `surface_state_present`:

```cyrius
# Line 53 — intended as an accessor
fn surface_state_present(ss) { return load32(ss + 40); }

...

# Line 123 — surface present action
fn surface_state_present(ss) {
    wgpu_surface_present(surface_state_handle(ss));
    return 0;
}
```

Cyrius resolves duplicate function names by taking the last definition
parsed, so the accessor at line 53 is silently replaced by the
mutating function at line 123 throughout the module. The internal
`_surface_state_configure` helper does:

```cyrius
var cfg = wgpu_surface_configuration(surface_state_device(ss),
                                     surface_state_format(ss),
                                     surface_state_width(ss),
                                     surface_state_height(ss),
                                     usage,
                                     surface_state_present(ss));   # ← line 80
```

At runtime, `surface_state_present(ss)` **presents the surface** and
returns 0 (instead of reading the present-mode field). The
configuration therefore goes out with `present_mode = 0` — which in
v29 WebGPU is "Undefined" — and the surface is *presented before it
is configured*, which in wgpu-native is either a no-op or a
null-dereference depending on backend state.

**Impact**. First `surface_state_new` call creates a surface,
(mistakenly) tries to present the still-unconfigured texture, and
configures it with present_mode = 0. Subsequent `acquire` calls are
undefined behaviour — in practice either a black frame or a segfault
in wgpu-native depending on the backend. Not reachable from an
external attacker (the library caller is in-process), but the library
is structurally broken along the entire surface path.

**Mitigation**. Rename the mutating function to
`surface_state_submit_present(ss)` (or `_do_present`). Keep the
accessor named as-is. Update the one internal caller that invokes the
present helper.

### [HIGH-2] `rpb_label` 4-byte heap overflow

- **File**: `src/render_pipeline.cyr`
- **Lines**: 228 (`alloc(80)`), 251 (`store64(b + 76, label)`)
- **Class**: CWE-787 (out-of-bounds write)

**Description**. `rpb_new` allocates an 80-byte builder struct:

```cyrius
fn rpb_new(...) {
    var b = alloc(80);
    ...
}
```

`rpb_label` writes 8 bytes at offset 76:

```cyrius
fn rpb_label(b, label) { store64(b + 76, label); return b; }
```

Offsets 76, 77, 78, 79 are inside the allocation; offsets 80, 81, 82,
83 are **past the end** — 4 bytes into whatever bump-allocator slab
follows the builder struct. The next allocation after a builder (in
the same `cyrius build` process) typically has its first field
clobbered.

**Impact**. Latent heap corruption whenever a consumer ever calls
`rpb_label` on the legacy `rpb_new` builder. The entire `rpb_*`
builder is marked "legacy kept for API compatibility" and
`rpb_build` delegates to `render_pipeline_create_simple` (which
doesn't consult the label), so today nothing in the phase0 test path
hits this. But the `rpb_*` entry points are `@public` and any
consumer who sets a label will corrupt heap.

**Mitigation**. The builder struct header comment says the label lives
at +76, but the layout is underspecified: the `bind_groups` vec at
+60 and `vertex_layouts` vec at +68 leave the last usable 8-byte slot
at +72 (ends at +79). Either:
(a) bump the allocation to `alloc(88)` and keep the label at +76, or
(b) move the label to +72 (shifting the vecs back one slot).

Option (a) is safer — it doesn't reshuffle existing field offsets —
and adds only 8 bytes per builder.

### [MED-1] `workgroups_1d` / `workgroups_2d` divide by zero

- **File**: `src/buffer.cyr`
- **Lines**: 176–178 (`workgroups_1d`), 182–186 (`workgroups_2d`)
- **Class**: CWE-369 (divide by zero)

**Description**. The workgroup helpers compute
`ceil(total / workgroup_size)` without checking `workgroup_size > 0`:

```cyrius
fn workgroups_1d(total, workgroup_size) {
    return (total + workgroup_size - 1) / workgroup_size;   # SIGFPE if wg_size == 0
}

fn workgroups_2d(dst, width, height, wg_x, wg_y) {
    store64(dst, (width + wg_x - 1) / wg_x);                # SIGFPE if wg_x == 0
    store64(dst + 8, (height + wg_y - 1) / wg_y);           # SIGFPE if wg_y == 0
    return 0;
}
```

Workgroup sizes are often pulled from a shader config JSON file or
computed from capability reports; a zero is plausible and the process
dies via SIGFPE rather than returning a recoverable error.

**Impact**. Denial-of-service of the consumer process. Integer divide
by zero on x86-64 raises SIGFPE with no handler; Cyrius programs have
no default signal handler.

**Mitigation**. Return 0 (or a `GpuResult::Err`) on `workgroup_size ==
0`. Caller must already treat 0 workgroups as a no-op, so the
ambiguity is safe.

### [MED-2] `growable_buffer_update` unchecked `cap * 2` overflow

- **File**: `src/buffer.cyr`
- **Lines**: 147–168
- **Class**: CWE-190 (integer overflow) → CWE-787 (OOB write)

**Description**.

```cyrius
fn growable_buffer_update(gb, device, queue, data, size) {
    var cap = load64(gb + 8);
    ...
    if (size > cap) {
        var new_cap = cap * 2;
        if (size > new_cap) { new_cap = size; }
        ...
        wgpu_queue_write_buffer(queue, load64(gb), 0, data, size);
    }
}
```

`cap` is a signed i64; `cap * 2` overflows to negative when `cap >=
2^62`. The `size > new_cap` branch then takes `new_cap = size`, which
sounds like a save — but if `size` is a legitimate large upload (< 2^62)
and `cap` is already somewhere near the overflow boundary (unlikely in
practice, but representable), the math can land at a `new_cap`
smaller than `size` silently.

**Impact**. A buffer allocated smaller than `size` followed by a
`wgpu_queue_write_buffer` of `size` bytes — a GPU-side OOB write
(wgpu-native validates against the descriptor size but the descriptor
is the small one).

**Mitigation**. Guard the doubling:

```cyrius
var new_cap = cap * 2;
if (new_cap < cap) { new_cap = size; }      # overflow guard
if (new_cap < size) { new_cap = size; }
```

### [MED-3] `texture_upload_rgba8` unchecked dimension multiplication

- **File**: `src/texture.cyr`
- **Lines**: 77–84
- **Class**: CWE-190 (integer overflow) / CWE-20 (missing input validation)

**Description**.

```cyrius
fn texture_upload_rgba8(queue, texture, data, width, height) {
    var dest = wgpu_texel_copy_texture_info(texture, 0);
    var layout = wgpu_texel_copy_buffer_layout(0, width * 4, height);
    var size = wgpu_extent_3d(width, height, 1);
    var data_size = width * height * 4;
    wgpu_queue_write_texture(queue, dest, data, data_size, layout, size);
    return 0;
}
```

- `width * 4`: if width exceeds `i64_max / 4 ≈ 2.3e18`, overflows.
  Unreachable in practice but no bound.
- `width * height * 4`: for width = height = 65536 (the max that fits
  in u32 as WGPU expects), `65536 * 65536 * 4 = 17.18e9` — fine in
  i64. For width = height = 2^32, overflow. u32 truncation on the
  descriptor path means WGPU rejects anyway, but mabda should not rely
  on the FFI to validate — defence in depth.
- No zero-dimension check. `texture_upload_rgba8(queue, tex, data, 0,
  0)` issues a `wgpu_queue_write_texture` with `size = (0, 0, 1)` and
  `data_size = 0` — wgpu-native accepts this, but the caller's
  intent was probably "nothing happened" and the silent no-op can
  mask real bugs.

**Impact**. At realistic texture dimensions, no overflow. But the
`texture_from_rgba` caller passes consumer-supplied width / height
directly with no device-limit check (`gpu_caps_max_texture_2d`). A
malicious image decoder upstream could drive width past the GPU's
advertised limit and either crash wgpu-native or — on backends with
weak validation — corrupt GPU memory.

**Mitigation**. Cast operands to i64 before multiplying (Cyrius's i64
arithmetic is already i64, but the pattern is explicit). Add a
zero-dimension short-circuit. Expose `texture_from_rgba_checked` that
takes a caps pointer and validates against `gpu_caps_max_texture_2d`.

### [MED-4] `storage_buffer_write` unchecked `write_count * element_size`

- **File**: `src/typed_buffer.cyr`
- **Lines**: 126–135
- **Class**: CWE-190 (integer overflow)

**Description**.

```cyrius
fn storage_buffer_write(queue, sb, data, write_count) {
    var capacity_count = load64(sb + 16);
    if (write_count > capacity_count) { ... }
    var element_size = load64(sb + 24);
    var write_bytes = write_count * element_size;
    wgpu_queue_write_buffer(queue, load64(sb), 0, data, write_bytes);
    ...
}
```

`write_count * element_size` has no overflow guard. The
`capacity_count` check above enforces `write_count <= stored count`,
but if `element_size` was set to something large at `storage_buffer_wrap`
time (nothing checks it), the product can still wrap.

**Impact**. Wraps to a small `write_bytes`, wgpu-native writes that
many bytes (short write) while the caller believes
`write_count × element_size` were transferred. Silent data truncation
in the consumer's GPU buffers.

**Mitigation**. Compute `write_bytes` with an overflow-checked helper:

```cyrius
if (element_size != 0 && write_count > i64_max / element_size) {
    return gpu_err_result_msg(GPU_ERR_BUFFER, "write size overflow");
}
```

### [MED-5] `storage_buffer_wrap` trusts caller on capacity consistency

- **File**: `src/typed_buffer.cyr`
- **Lines**: 92–101
- **Class**: CWE-20 (improper input validation)

**Description**. The wrapper stores `capacity`, `count`, and
`element_size` verbatim with no check that `capacity >= count ×
element_size`:

```cyrius
# Wrap a raw buffer handle with element-count metadata. Caller is responsible
# for ensuring `capacity == count * element_size` (no runtime validation).
fn storage_buffer_wrap(handle, capacity, count, element_size) { ... }
```

The header comment is explicit that this is a trust boundary the
caller owns. It is still a real footgun — a typo in the caller
(`storage_buffer_wrap(h, 64, 16, 8)` when the buffer was `alloc(64)`
of 8-byte elements → 8 elements, not 16) makes downstream
`storage_buffer_write` accept writes past the buffer.

**Impact**. Depends on the downstream: `storage_buffer_write` will
happily issue a `wgpu_queue_write_buffer` with 128 bytes targeting a
64-byte GPU buffer. wgpu-native rejects in validation, so the practical
impact is a runtime error rather than a GPU OOB write — but the
error is emitted by the FFI layer, not by mabda's own validation,
which makes the failure mode diagnostically opaque.

**Mitigation**. Assert `capacity >= count * element_size` at wrap
time, returning a `GpuResult` if violated. Callers who *want* the
looser contract (e.g. byte-oriented writes on top of an element-typed
handle) can opt in via a separate `storage_buffer_wrap_raw`.

### [MED-6] `_time_now_ns` doesn't check `clock_gettime` return value

- **File**: `src/profiler.cyr`
- **Lines**: 29–36
- **Class**: CWE-252 (unchecked return value)

**Description**.

```cyrius
fn _time_now_ns() {
    var ts[16];
    syscall(228, 1, &ts);            # return value discarded
    var sec = load64(&ts);
    var nsec = load64(&ts + 8);
    return sec * 1000000000 + nsec;
}
```

`clock_gettime(2)` returns -EINVAL for invalid clock IDs and -EFAULT
for bad buffer pointers. On failure, `ts` contains whatever was on
the stack — i.e. garbage. The caller computes "timing" from garbage
and feeds it into the EMA, the FPS calculation, and the history ring
buffer.

**Impact**. Low. CLOCK_MONOTONIC (clock_id = 1) is always available
on Linux kernels mabda targets; the buffer is always a stack var, so
-EFAULT is structurally impossible. But the pattern is fragile: any
future edit that parameterises the clock ID or passes a heap pointer
inherits the missing check. Observability defect — garbage frame
times would propagate silently.

**Mitigation**. Check the return value; on non-zero, zero `ts` before
reading. Adds two instructions to a hot path but the branch predicts
well.

### [LOW-1] `capabilities.cyr` struct-layout comment says 128 bytes, alloc is 120

- **File**: `src/capabilities.cyr`
- **Lines**: 5–20 (comment), 23 (`alloc(120)`)
- **Class**: documentation drift (not a security bug per se)

**Description**. The layout comment at the top of the module says the
`GpuCapabilities` struct is 128 bytes. The actual allocation is 120
bytes. Every field offset in the comment is correct — the last field
(`multi_draw_indirect`) is at `+112` and occupies 8 bytes, so the
struct runs from 0 to 119 inclusive. 120 is correct; 128 in the
comment is wrong.

**Impact**. A future edit that adds a field based on the 128-byte
claim (say, at `+120` for a new 8-byte capability bool) would write
past the actual 120-byte allocation.

**Mitigation**. One-character fix: change `128` to `120`.

### [LOW-2] `read_buffer` allocates `size` without upper bound

- **File**: `src/buffer.cyr`
- **Lines**: 87–119
- **Class**: CWE-789 (memory allocation without size limit), defence-in-depth

**Description**. `read_buffer(device, queue, buffer, size)` calls
`alloc(size)` and `memcpy(result, mapped, size)` with no upper bound
on `size`. A consumer passing `size = i64_max / 2` as a typo drives
the bump allocator into exhaustion.

**Impact**. Process OOM — recoverable in Cyrius's bump allocator
(returns 0 on exhaustion, then `memcpy(0, …, huge)` segfaults). No
memory-safety violation, just a poor UX.

**Mitigation**. Cap `size` at a reasonable maximum (e.g. 1 GiB) and
return 0 beyond; or check the device's
`gpu_caps_max_buffer_size()` against `size` if a context is available.

### [LOW-3] `validate_dispatch` and `validate_dimensions` declared but never called internally

- **Files**: `src/buffer.cyr:190–195`, `src/texture.cyr:132–136`
- **Class**: CWE-252 (designed-in validator that the library never invokes)

**Description**. Both validators exist in the public API but no
internal caller invokes them before handing dimensions to the FFI.
Consumers who don't read the source miss them.

**Mitigation**. Call them from `texture_create_rgba8` /
`texture_upload_rgba8` / `compute_dispatch` with the device's
`gpu_caps_*` limits. Return an error instead of silently passing an
oversized dispatch to wgpu-native.

### [LOW-4] `wgpu_string_view` calls `strlen` on caller-controlled pointer

- **File**: `src/wgpu_descriptors.cyr`
- **Lines**: 15–19
- **Class**: defence-in-depth (implicit caller trust)

**Description**.

```cyrius
fn wgpu_string_view(dst, cstr) {
    store64(dst, cstr);
    store64(dst + 8, strlen(cstr));
    return 0;
}
```

`strlen` reads until it finds a NUL. If a caller hands in a non-NUL-
terminated pointer (a slice into a larger buffer), `strlen` walks off
the end and either reads the NUL from adjacent memory (producing a
garbage length) or eventually hits an unmapped page and segfaults.

**Impact**. Segfault on non-NUL-terminated input. Caller-trust
boundary — mabda documents label arguments as "cstr" — so not a
findings against mabda's own code, but a defence-in-depth improvement
would bound the scan.

**Mitigation**. Expose `wgpu_string_view_len(dst, data, len)` (already
present) and migrate internal callers that have a known length.

### [LOW-5] `compute_pipeline_new` leaks intermediate GPU handles on failure

- **File**: `src/compute.cyr`
- **Lines**: 16–65
- **Class**: CWE-401 (missing release of resource)

**Description**. When `wgpu_device_create_bind_group_layout` succeeds
but `wgpu_device_create_pipeline_layout` fails, the BGL handle and
the `entries` heap allocation are never released. Same chain for
shader module failure.

**Impact**. Resource leak on failure paths. Bump-allocator memory is
reclaimed at scope exit, but GPU handles outlive the Cyrius bump
arena.

**Mitigation**. Add explicit `wgpu_*_release` calls on each failure
branch, or restructure to early-return after cleanup.

### [LOW-6] `texture_from_color` relies on caller's color components being in [0, 1]

- **File**: `src/texture.cyr`
- **Lines**: 106–113
- **Class**: defence-in-depth (out-of-range float → byte conversion)

**Description**.

```cyrius
store8(&rgba, f64_to(f64_mul(color_r(color), f64_from(255))));
```

If `color_r` is outside [0, 1] (nothing in the color module enforces
this), `f64_mul(c, 255)` may exceed 255 or go negative. `f64_to` is
implementation-defined for out-of-range values.

**Impact**. Garbage byte stored in the 1×1 texture. Cosmetic.

**Mitigation**. Clamp each component to `[F64_0, F64_1]` before the
multiplication. Two calls to `f64_lt` / `f64_gt` per component.

## Remediation Plan

Fix order (dependencies and what each unlocks):

1. **HIGH-1** — rename `surface_state_present` (line 123) to
   `surface_state_submit_present`. Verify the one internal caller
   updates. Add a test that `surface_state_new` produces a
   surface where `surface_state_present(ss)` returns the configured
   mode (not 0). Unblocks any consumer building a real surface path.

2. **HIGH-2** — bump `rpb_new`'s allocation from 80 to 88 bytes. Add
   an assertion that writing a label back-reads it intact. Fixes the
   legacy builder without breaking offset compatibility.

3. **MED-1** — guard `workgroups_1d` / `workgroups_2d` against zero
   workgroup sizes. Return 0 / leave `dst` zeroed. Adds two tests.

4. **MED-2** — guard `growable_buffer_update`'s `cap * 2` against
   overflow. Add a test with a synthetic cap near the i64 boundary.

5. **MED-3** — cast dimension products to i64 explicitly in
   `texture_upload_rgba8`; add zero-dim short-circuit. Expose a
   `_checked` variant that takes a caps pointer. Integrate
   `validate_dimensions` (LOW-3) into `texture_create_rgba8`.

6. **MED-4** — overflow-guard `write_count * element_size` in
   `storage_buffer_write`. Add a test that hits the guard.

7. **MED-5** — consistency-check `capacity >= count * element_size`
   in `storage_buffer_wrap`. Split into `storage_buffer_wrap` (checked)
   and `storage_buffer_wrap_raw` (unchecked) to preserve the existing
   byte-oriented convenience path.

8. **MED-6** — check `syscall(228, …)` return in `_time_now_ns`;
   zero `ts` before reading on non-zero. Trivial.

9. **LOW-1 … LOW-6** — schedule individually; none block 2.3.0. LOW-1
   is a one-character fix and should ship alongside the HIGH fixes.
   LOW-3 folds naturally into the MED-3 work.

**Gates added to CI as part of this audit** (already landed in 2.2.0
workflow rewrite):

- `cyrius lint` fails build on any warning.
- `cyrius fmt --check` diff-clean required.
- `cyrius vet` on `programs/smoke.cyr` must be clean.
- Dist-sync: `cyrius distlib` regenerated and diff-checked.
- Security scan: raw `execve`/`fork`/`sys_system` in `src/` are
  failure conditions (not present today).

## Non-findings (verified clean)

- **No `unsafe` / memory-unsafe primitives** — Cyrius has none; struct
  access is via `load64`/`store64` with named offset constants.
- **No libc** — all syscalls direct, arity-checked by the compiler.
  The single `syscall(228)` in the profiler is the only kernel
  boundary.
- **No `sys_system()` in `src/`** — verified by grep.
- **No raw `execve(59)` or `fork(57)` in `src/`** — verified.
- **No path writes to `/etc`, `/bin`, `/sbin`** — verified; mabda
  never touches the filesystem.
- **No raw pointer arithmetic outside documented struct accessors** —
  verified. Every `load64(ptr + offset)` uses a named constant from
  the module's layout comment.
