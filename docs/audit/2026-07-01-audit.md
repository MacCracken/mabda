# Mabda Security Audit — 2026-07-01 (v4.0.0 release)

**Scope.** P(-1)/closeout audit for the v4.0.0 cut. Primary focus: the six
NVIDIA backend modules newly bundled into `dist/mabda.cyr` this release
(`backend_nvidia_nouveau.cyr`, `backend_nvidia_sass.cyr`,
`backend_nvidia_push.cyr`, `backend_nvidia_qmd.cyr`, `backend_nvidia_tex.cyr`,
`backend_nvidia.cyr`) plus the `gpu_context_from_preinit` NVIDIA routing branch
in `src/context.cyr`. These modules went from source-only to consumer-reachable
via the dist bundle at this cut, so this is their first formal audit. A full
10-dimension sweep of `src/*.cyr` ran alongside, with adversarial verification
(2 skeptics per candidate) and a CVE sweep for the 2026-04-30 → window across
amdgpu/DRM, wgpu/WebGPU, and nouveau/GSP-RM.

**Method.** Regression-check of every prior ship-blocker + deferral against the
current tree; 10 dimension-focused finders over `src/*.cyr`; each candidate
finding verified by two independent adversarial skeptics (correctness lens +
false-positive-hunt lens); external CVE research via web search/fetch against
NVD, GHSA, RustSec, amd-gfx/LKML, and gfx-rs trackers.

## Verdict

**Ship-clean for v4.0.0.** 0 CRITICAL, 0 HIGH. The NVIDIA backend surface — the
release's headline new-to-dist code — produced **zero confirmed findings**. All
9 confirmed findings are in the pre-existing AMD-native / wgpu / core tree
(none v4.0-introduced) and are LOW doc-staleness or bounded-MEDIUM
resource-hygiene issues on trusted-caller / retiring-wgpu paths. All prior
ship-blockers and deferrals regression-confirmed still FIXED. No in-window CVE
is fixable in mabda's tree; the two APPLICABLE amdgpu CVEs are kernel-side and
mabda is already defensive against both.

## Regression check — prior findings

All five 2026-06-14 ship-blockers (HIGH-1, HIGH-2, MED-1, MED-3, MED-6) and all
ten deferrals (MED-2/4/5/7, LOW-1..6) **regression-confirmed still FIXED**
against the current tree. Highlights:

- **HIGH-1** (surface configure ignored consumer w/h) — now reads back the
  chosen mode dims and fails loudly on mismatch (`backend_native.cyr:2397-2416`).
- **HIGH-2** (logind master fd leak on failure) — every failure path between a
  successful `take_device` and slot dispatch now releases master + closes the fd,
  plus success-path ownership provenance (`surface_v3.cyr:120-158`).
- **MED-6** (present drained only the first DRM event) — present now walks every
  event per read buffer and re-reads until FLIP_COMPLETE, capped at 16 reads
  (`backend_native_kms.cyr:1688-1713`).
- **MED-2/4/5/7 + LOW-1..6** — FB overflow guards, two-pass TOCTOU clamps,
  `set_master` raw-return, cached PM4 scratch, fd guards, widened summary buf,
  implemented buffer/shader slots, threaded `vc`, cached compute scratch, and
  ctx-stash zeroing on release — all present.

## CVE sweep (2026-04-30 → window)

### amdgpu / DRM — 2 APPLICABLE (both kernel-side, mabda defensive), rest N/A

- **CVE-2026-46220** (SDMA4 `sdma_v4_0_ring_emit_fence` `BUG_ON(addr & 0x3)`
  reachable via `DRM_IOCTL_AMDGPU_CS`, local kernel-panic DoS on GFX9) —
  **APPLICABLE** path (mabda submits SDMA CS on GFX9/Cezanne). mabda already
  only emits DWORD-aligned fence writeback addresses and documents this at
  `backend_native_amdgpu.cyr:836`; will not trip the panic. **Recommendation:**
  promote that comment into a hard CPU assertion so a future misaligned-fence
  regression is caught in tests, not as a HW panic.
- **CVE-2026-43237** (`amdgpu_gem_va_ioctl` stale-fence UAF → panic) —
  **APPLICABLE** ioctl (`GEM_VA`, every BO VA map), but the defect is
  kernel-internal fence bookkeeping, not payload-shaped; **no mabda mitigation
  possible**. Deployment advisory: run mabda's native AMD path on a patched
  amdgpu kernel. (Carried from the 2026-06-20 audit.)
- **CVE-2026-43318** (dma-buf `move_notify` TLB race) / **CVE-2026-46209**
  (GEM FB size-validation truncation) / **CVE-2026-23468** (unbounded BO-list) —
  **CLASS-APPLICABLE** only: mabda's scanout BOs are VRAM-pinned, it computes its
  own ADDFB2 pitch/size, and its BO-lists are small/fixed. Class reminders to
  keep mabda's own FB-size round-up and BO-list counts overflow-guarded.
- **NOT_APPLICABLE:** CVE-2026-43398 (userq wait — RDNA3+ submission model unused),
  CVE-2026-31566 / CVE-2026-46197 (amdkfd/KFD/SVM — mabda issues no KFD ioctls),
  CVE-2026-46204 / -46199 / -46218 / -46230 (VCN/UVD/VCE video engines — mabda
  instantiates none).

### wgpu / WebGPU — no wgpu-native/naga CVE in window

gfx-rs/wgpu-native's security tab shows no published advisories; no RUSTSEC/NVD
entry names wgpu or naga in 2026. The wgpu 29.0.1 core fixes (PR-9302 texture
height, PR-8808 mip/layer overflow, PR-9264 limit compare; all dated 2026-03-26,
rolled into wgpu-native v29.0.1.1 on 2026-06-23) straddle the window and are
**CLASS reminders** — mabda hand-lays descriptors and does its own texture-dim
math, so the overflow class matters (see MEDIUM below) — but none is a live
exploit against mabda's Vulkan-forced + native-DRM configuration.
**NOT_APPLICABLE:** CVE-2026-5281 (Dawn/Chromium), CVE-2026-22166 (PowerVR/GLES)
— other WebGPU implementations mabda does not use.
**Recommendation:** if convenient, bump the consumer wgpu-native pin to
v29.0.1.1 to pick up the 29.0.1 core fixes for free (the AMD wgpu path retires at
4.0.1 regardless).

### nouveau / GSP-RM (NVIDIA backend)

- **CVE-2026-46006** (nouveau legacy `nouveau_gem_pushbuf` reloc 32-bit integer
  overflow, ~2026-05-28) — **NOT_APPLICABLE.** mabda's nouveau path uses modern
  explicit-VA push submission (`backend_nvidia_push.cyr`), not the legacy
  relocation pushbuf ioctl. Confirmed against the NVIDIA push encoder.
- No in-window GSP-RM Xid / nouveau CVE maps onto mabda's ioctl surface. The
  ~30¾h soak burn-in (see CHANGELOG 4.0.0) observed dmesg Δ=0 (no Xid) across
  ~8.69M dispatches.
- **Out of window (fold into next sweep):** CVE-2026-53313 / CVE-2026-53135
  (drm/amd/display NULL-deref DoS, ~2026-06-26) — class-relevant to the KMS path,
  kernel-internal, mabda cannot control.

## Confirmed findings

> Dedup: the two GpuContext-header findings (`doc-gpuctx-168-vs-176`,
> `ctx-hdr-bytecount-stale`) are the same defect from two finders; the two
> texture-overflow findings (`ovf-tex-upload-datasize` MEDIUM,
> `texture-upload-product-overflow` LOW) are the same code. Six distinct issues.

### MEDIUM

**M1 — `texture_upload_rgba8` product overflow** — `src/texture.cyr:105-114`
(CWE-190). The @public `texture_upload_rgba8` validates each dimension only
against `0x7FFFFFFF` individually, then computes `data_size = width * height * 4`.
Both dims near the ceiling overflow i64 and wrap to a small/negative
`data_size` passed to `wgpu_queue_write_texture`; separately `width * 4` (up to
~2^33) truncates into the u32 `bytes_per_row`. The creation paths all cap at
`MABDA_MAX_TEXTURE_DIM_2D` (8192) — this v2 upload helper's `0x7FFFFFFF` ceiling
is the inconsistent one. Bounded: trusted caller, retiring wgpu path.
**Fix:** reject `width/height > MABDA_MAX_TEXTURE_DIM_2D`, or guard
`width*height*4` before the multiply. Aligning to 8192 also restores the
cross-backend dimension contract.

**M2 — VA leak on native buffer-create failure** — `src/backend_native.cyr:843-851`
(CWE-401). `_backend_native_buffer_create` reserves from the per-context
forward-only texture VA region via `native_ctx_alloc_texture_va(ctx, bo_size)`,
then on BO-create failure returns 0 **without** `native_ctx_free_texture_va`,
and on va-map failure releases the BO but still omits the VA reclaim — unlike the
sibling `_native_shader_compile_spirv` which does the LIFO rollback
(`backend_native.cyr:1035-1047`, where the omission was previously filed HIGH in
the N.6r review). Each transient failure permanently consumes `bo_size` of the
shared 2 GiB VA region. **Fix:** call `native_ctx_free_texture_va(ctx, bo_size)`
before both 0-returns.

**M3 — VA leak on native texture-create failure** — `src/backend_native.cyr:1543-1552`
(CWE-401). Same error-path VA-reclaim omission across the native texture create
slots (`_backend_native_texture_create_2d_sampleable`,
`_native_create_layered_sampleable` at 1628-1637, and the size-helper paths at
1373-1378). **Fix:** add `native_ctx_free_texture_va(ctx, bo_size)` before every
0-return that follows a successful VA reserve but a failed BO-create/va-map.

### LOW

**L1 — GpuContext header byte count stale** — `src/context.cyr:5-9`. Header
summary + growth chain say `168 bytes` but `GPU_CONTEXT_SIZE = 176` (the
`rt_va_next` field at +168, v3.4.2, extends to 176). `alloc(176)`/`memset(176)`
cover every accessor, so **no memory-safety impact** — one-directional-safe — but
the comment violates the "header byte count must equal the alloc" invariant.
**Fix:** update the summary to 176 and append `→ 176 (rt_va_next, v3.4.2)`.

**L2 — `native_render_handles_write` doc says 24, writes 32** —
`src/backend_native.cyr:432-442`. Comment states a "24-byte block" / `var
triple[24]`, but the body writes four u64 fields (the +24 `tex_h` added at v3.2
TS.5) needing 32 bytes. All in-tree callers correctly use `var triple[32]`
(no live overrun), but a future caller heeding the comment gets an 8-byte stack
overwrite. **Fix:** update the comment to 32 bytes; optionally add a
`NATIVE_RENDER_HANDLES_SIZE = 32` constant shared by writer + callers.

**L3 — `shader_cache` feeds raw FNV hashes without the HIGH-4 sentinel remap** —
`src/shader_cache.cyr:46,51,79,83`. Unlike the caches hardened after HIGH-4,
`shader_cache` passes raw FNV hashes into `map_u64_*` without the
`_cache_safe_key` sentinel remap. Low impact (u64 keyspace, collision-only), but
inconsistent with the sibling caches. **Fix (optional):** route through
`_cache_safe_key` for consistency.

**L4 — `profiler_new` / `instance_data_identity` degrade if `color_init()`
hasn't run** — `src/profiler.cyr:76-79`. @public helpers have a runtime
cross-module init coupling on `color_init()`. Low impact (degrade, not crash).
**Fix (optional):** document the init-order requirement or make it defensive.

## Dropped by adversarial verification (9)

Each refuted by ≥1 skeptic lens as false-positive or non-defect:
`dz-block256-alignup-zero` (guarded upstream), `rt-create-no-dim-validation`
(backend slot validates), `buffer-copy-negative-bytes` (bytes&3 + downstream
guards), `buffer-create-no-size-validation` (allocator rejects), `compute-
pipeline-storage-count-overflow` (bounded before alloc), `prime-fd-zeroext-
deadcheck` (check reachable), `vport-odd-dim-trunc` (odd dims rejected at RT
allocator — the MED-3 fix), `cb-color0-base-align` (composer contract holds),
`bind-group-clear-returns-new-map` (callers use the return).

## Recommendations

1. **Pre-tag fixes — DONE (2026-07-01).** M1 (texture-upload cap aligned to
   8192), M2 + M3 (VA reclaim on all native buffer/texture create error paths,
   mirroring `_native_shader_compile_spirv`), and the L1/L2 doc-staleness
   comments are all applied. Each MEDIUM landed with a CPU regression assertion
   (`texture.tcyr` M1 dim-cap cases; `native.tcyr`
   `test_native_create_va_reclaim_on_fail` for M2/M3). Suite: 4901 assertions,
   0 failed; lint/fmt/vet/version-check clean; dist regenerated diff-clean.
2. **Deployment advisory (carried):** run mabda's native AMD path on a patched
   amdgpu kernel (CVE-2026-43237, CVE-2026-46220).
3. **Next sweep:** fold in CVE-2026-53313 / -53135 (drm/amd/display); confirm the
   wgpu-native pin question is moot after the 4.0.1 AMD-wgpu retirement.

All findings are pre-existing (AMD-native / wgpu / core); **none is introduced by
the v4.0 NVIDIA backend or its dist bundling**, which audited clean.
