# Mabda Security Audit — 2026-07-02 (v4.0.1 — AMD wgpu retirement)

**Scope.** Targeted audit of the v4.0.1 diff, which is small and surgical: the
AMD-wgpu retirement guard (a runtime `WGPUAdapterInfo.vendorID` read + reject in
`gpu_context_from_preinit`) plus its supporting FFI decode, error code, and CPU
test. The paired samvada/libsystemd retirement was deferred (escape hatch — zero
code). This is **not** a full P(-1) sweep; the comprehensive audit is
`docs/audit/2026-07-01-audit.md` (v4.0.0), whose findings all remain fixed
(no code touched here overlaps them).

**Method.** Direct review of the diff against the CLAUDE.md security checklist,
with emphasis on **FFI descriptor-offset review** (the one checklist item this
change actually exercises) and the integer/pointer-safety of the new read.

## Verdict

**0 CRITICAL / 0 HIGH / 0 MEDIUM.** The change adds one bounded, null-safe u32
read whose only ABI-sensitive value (the `vendorID` offset) was derived from the
vendored header by the compiler, not assumed. No new external-call surface.

## FFI descriptor-offset review (checklist item 7)

The one new FFI struct decode is `WGPUAdapterInfo` in `src/wgpu_descriptors.cyr`.
Offsets were **not hand-assumed** — an `offsetof()`/`sizeof()` probe compiled
against the vendored v29 header (`deps/wgpu-native/include/webgpu/webgpu.h`)
returned:

```
sizeof(WGPUAdapterInfo)   = 96
offsetof(vendorID)        = 80
offsetof(backendType)     = 72   offsetof(deviceID) = 84
sizeof(WGPUStringView)    = 16
```

These are pinned as `WGPU_ADAPTER_INFO_SIZE = 96` and
`WGPU_ADAPTER_INFO_VENDOR_ID_OFFSET = 80`, and asserted in
`tests/tcyr/backend.tcyr::test_amd_wgpu_retirement_guard_v401` so a future
header/layout drift trips a CPU test rather than silently mis-rejecting a vendor.
A wrong offset was the single top risk (reject NVIDIA/Intel, or miss AMD) and is
now closed by derivation + assertion.

## Memory / pointer / integer safety

- **Buffer safety:** `wgpu_adapter_vendor_id` uses a stack-local `var info[96]`
  (matches `WGPU_ADAPTER_INFO_SIZE`), `memset` to `WGPU_ADAPTER_INFO_SIZE`, and
  reads a u32 at +80 (max offset 83 < 96). No overflow.
- **Pointer validation:** `wgpu_adapter_info_vendor_id(0)` and
  `wgpu_adapter_vendor_id(0)` are null-guarded → return 0 (not a real PCI
  vendor), so a null adapter is treated as "not AMD" and defers to wgpu-native's
  own null handling. The guard call site in `gpu_context_from_preinit` is
  reached only after the existing `adapter != 0` check, so the live path always
  passes a valid adapter.
- **Integer:** `vendorID` is a 16-bit PCI id (`0x1002`/`0x10DE`/`0x8086`); the
  `load32` read cannot sign-extend into a false compare. Compared by exact
  equality to `PCI_VENDOR_AMD`; no arithmetic.
- **Syscall/FFI return handling:** `wgpu_adapter_get_info` is a void-fill call
  already bound (`_fp(36)`), invoked via the existing `fncall2` (no new
  `fncall6`/6+-arg-into-wgpu risk). The scratch is zeroed before the call, so a
  no-op fill leaves `vendorID = 0` → "not AMD" (fail-open to the *pre-existing*
  behavior, not a crash).

## CVE surface

No new external dependency and no new wgpu-native entrypoint (the bound
`wgpuAdapterGetInfo` is a read-only info query). The v4.0.0 CVE sweep window is
unchanged; nothing here alters mabda's ioctl/FFI attack surface.

## Note on enforcement coverage

The **live** AMD reject cannot be exercised by the CPU tcyr suite (no real
adapter). Its behavioral proof is a GPU-integration run on AMD hardware
(`make test-gpu`/phase0 → expect `GPU_ERR_AMD_WGPU_RETIRED`), plus an
NVIDIA/Intel wgpu regression confirming they still create contexts. The CPU test
covers everything short of the live `wgpu_adapter_get_info` fill: constants,
offset, decode, and the AMD-vs-NVIDIA branch logic.

## Adversarial verification (6 independent skeptics) — outcomes

A post-implementation adversarial pass (offset re-derivation, false-reject,
memory-safety, test-integrity, doc-consistency, wiring-integrity) confirmed the
offset (independent `offsetof` recompile), the no-false-reject contract, and the
wiring integrity, and surfaced three items — all now addressed:

- **Test coverage (was: the guard *mechanism* wasn't exercised, only its
  condition re-derived).** Fixed two ways: the rejection decision is factored
  into `_wgpu_vendor_retired(vendor_id)` (unit-tested for AMD-reject +
  NVIDIA/Intel/zero-pass — inverting it now fails a CPU test), and a new
  `test_amd_wgpu_guard_mechanism_e2e` drives the **real**
  `gpu_context_from_preinit` through a mock wgpu fn-table (slot 36 =
  `wgpuAdapterGetInfo`): a mock AMD adapter must return
  `Err(GPU_ERR_AMD_WGPU_RETIRED)`, a mock NVIDIA adapter must return `Ok`.
  Deleting, inverting, misplacing, or mis-coding the guard now fails CI.

- **LOW — accepted one-shot memory leak.** `wgpuAdapterGetInfo` returns the
  adapter-name `WGPUStringView` members "with ownership"; the only reclaim is
  `wgpuAdapterInfoFreeMembers(WGPUAdapterInfo)` — a **by-value** call needing a
  struct-packing C shim + a **new consumer-launcher fn-table slot**
  (`deps/wgpu_main.c`). That launcher/lib contract bump rides the HW-only wgpu
  path (untestable in CI); disproportionate to a ~4-tiny-string leak that
  happens **once per context** and is reclaimed by the OS at process exit.
  **Decision: accept + defer** the free to the next launcher fn-table revision
  (e.g. the v5.x wgpu work), documented at `src/wgpu_ffi.cyr`
  `wgpu_adapter_vendor_id`. Not per-frame, not unbounded, no UAF/OOB.

- **Doc stragglers.** The two HIGH contradictions were fixed
  (`docs/architecture/overview.md` diagram reconciled to three backends;
  `docs/guides/native-migration.md` libsystemd-deferral corrected). The
  remaining LOW items are dated ADR update-trails
  (`docs/adr/005`, `docs/adr/006`) and a v3-era proposal
  (`docs/proposals/v3-wgsl-frontend-choice.md`) that carry correction banners or
  are point-in-time history — left as-is as defensible record, not live guidance.
