# Proposal: v3.3 Asset Loading (KTX2 / DDS / PNG)

**Status:** Proposed (v3.3 design, 2026-06-19). `33x` branch.
**Arc:** v3.3 "Asset Loading" — see [`roadmap.md` § v3.3](../development/roadmap.md#v33--asset-loading)
and the [`3-3-punchlist.md`](../punchlists/3-3-punchlist.md).
**Companion proposal:** [`v3.3-chitra-png-decoder-package.md`](v3.3-chitra-png-decoder-package.md)
(the new sibling decode package).
**Consumers:** soorat (textures), kiran (asset pipeline), rasa/ranga (image I/O).

## Summary

mabda can *create* and *sample* textures (RGBA8 + the BC/ETC2/ASTC compressed
families, since v3.2.x) but it cannot yet *load* one from a file or byte
buffer. v3.3 closes that gap with three loaders, behind one architectural
split:

> **Decode is CPU and lives in a package; container-parse + GPU upload lives
> in mabda.**

- **KTX2 + DDS** — GPU-texture *container* formats. They carry already-encoded,
  GPU-ready data (mip chains, and usually block-compressed BC payloads). mabda
  parses the container and places each mip level's bytes via a new per-level
  upload path. **No external decoder** — this rides the 3.2.x compressed-texture
  stack directly.
- **PNG** — a CPU raster format. mabda does **not** decode it; a new pure-Cyrius
  sibling package, **`chitra`**, decodes PNG bytes → canonical RGBA8, and mabda
  uploads the result through its existing texture API. See the companion proposal.

The public surface is explicit per-format entrypoints plus a magic-byte
sniffer:

```cyrius
fn gpu_texture_load_ktx2(ctx, bytes, len): i64   # @public — handle | 0
fn gpu_texture_load_dds(ctx, bytes, len): i64    # @public
fn gpu_texture_load_png(ctx, bytes, len): i64    # @public — routes through chitra
fn gpu_texture_load(ctx, bytes, len): i64        # @public — sniff magic, dispatch
# + _result variants returning Ok(handle)/Err(gpu_err) for each.
```

## Correction to the original roadmap framing

The v3.2-era roadmap said v3.3 image loading was **blocked** ("adopted only
once a pure-Cyrius decoder exists in the AGNOS ecosystem… no C image library
will be vendored"). That premise was **wrong**:

- The Cyrius **stdlib already ships `sankoch`** — `zlib_decompress(src, src_len,
  dst, dst_cap)` (RFC 1950/1951 inflate) + `crc32` + `adler32`. DEFLATE is free.
- **`kii`** (a terminal image→ASCII viewer, v1.0.1) already has an 813-line,
  W3C-compliant, fuzz-hardened PNG decoder (`kii/src/png.cyr`) built on sankoch.

So the gate is effectively met. The maintainer decision (2026-06-19) is to
**stand up a reusable decode package (`chitra`)** by *forking + adapting* kii's
proven PNG core — rather than coupling mabda to an app, or rebuilding inflate.
What `chitra` genuinely adds over kii is covered in the companion proposal
(byte-buffer I/O instead of file paths; a canonical-RGBA8 normalization pass;
tRNS) — it is a fork with real new code, not a rename.

## What v3.3 adds to mabda (the upload side)

mabda's current texture API is 2D-only with whole-texture upload
(`gpu_texture_create_2d(ctx,w,h,fmt)`, `gpu_texture_write(ctx,tex,src,n)`).
Container loading needs three additions:

1. **Format mapping** (`src/asset_format.cyr`) — `mabda_texfmt_from_vk_format`
   (KTX2) and `mabda_texfmt_from_dxgi_format` (DDS) → `MABDA_TEXFMT_*`. Every
   number is **pinned against the canonical Vulkan `VkFormat` / D3D `DXGI_FORMAT`
   enum** and cited in the header (the gfx9.json-register discipline — a wrong
   number is a silent-wrong load). Unmapped → 0 (fail loud at the loader).
2. **Per-mip-level upload** — `gpu_texture_write_level(ctx, tex, level, src, n)`
   + a new `BACKEND_SLOT_TEXTURE_WRITE_LEVEL` (280; `BACKEND_SIZE` 280→288).
   Containers carry per-level data; whole-texture write can't place it.
3. **Generalized mipped create** — `gpu_texture_create_2d_fmt_mipped(ctx, w, h,
   fmt, mip_count)` + a new `BACKEND_SLOT_TEXTURE_CREATE_2D_FMT_MIPPED` (288;
   `BACKEND_SIZE` 288→296). The existing mipped create is RGBA8-only; a fixed-
   arity fnptr slot can't grow a `fmt`/`mip_count` arg, so it's a new slot.

The PNG path reuses the *existing* `gpu_texture_create_2d(RGBA8)` +
`gpu_texture_write` (chitra gives whole-image RGBA8), so it does not need the
per-level slot.

## The caps gate (prerequisite, not a detail)

The ETC2/ASTC/BC6H safety story depends on a capabilities check **before**
texture create — otherwise an ETC2/ASTC `.ktx2` loaded on native AMD (Cezanne)
would create a texture it cannot sample (a black sample, not an error). The
loaders take `(ctx, bytes, len)` and have no `caps` in hand, so v3.3 adds
caps access off the context (`gpu_ctx_supports_format(ctx, fmt)`, resolving the
`GpuCapabilities` stashed at device-create). Every loader runs this gate before
`create`; an unsupported format fails loud with `GPU_ERR_FORMAT_UNSUPPORTED`.

## Container format handling (the ungated subset)

### DDS (simplest — ships first)
`'DDS '` magic + 124-byte `DDS_HEADER` (+ optional 20-byte `DDS_HEADER_DXT10`).
Two format paths: legacy **FourCC** (`DXT1`→BC1, `DXT5`→BC3; `DXT3`/BC2 →
fail-loud, no mabda id) and the **DX10/DXGI_FORMAT** extension. No
supercompression — the simplest ungated path. Mip levels are a sequential
byte walk sized by `mabda_texfmt_data_size` per level.

### KTX2-uncompressed
12-byte identifier + header (`vkFormat`, dims, `levelCount`, `layerCount`,
`faceCount`, `supercompressionScheme`) + a level-index table (per level:
byteOffset / byteLength / byteLengthUncompressed). v3.3 handles
`supercompressionScheme == 0` only; `!= 0` (BasisLZ/Zstd/ZLIB) **fails loud**
(the second decoder gate — see Gates). Mip/level data placed via the per-level
upload path.

### Format map (illustrative — pin at impl)
`R8G8B8A8_UNORM`→RGBA8, `BC1/BC3/BC4/BC5/BC6H/BC7`→the matching `MABDA_TEXFMT_*`,
`ETC2_*`/`ASTC_{4x4,6x6,8x8}`→their ids (KTX2). The map is **N:1** (BC1_RGB,
BC1_RGBA, and their sRGB peers all collapse to one `MABDA_TEXFMT_BC1`) — see the
sRGB decision below.

## Error model

Two-tier, matching mabda's convention: a thin `gpu_texture_load_*(…) → handle|0`
plus a `_result` variant returning `Ok(handle)/Err(gpu_err)`. New codes:
`GPU_ERR_CONTAINER_PARSE = 21` (malformed/truncated/unsupported container) and
`GPU_ERR_IMAGE_DECODE = 22` (chitra decode failure). Existing
`GPU_ERR_FORMAT_UNSUPPORTED = 19` covers the caps/gate rejections. Every header
read is bounds-checked against `len` before use (untrusted-input discipline).

## Deferred — tracked, never silently dropped

Per the project's "never silently defer" rule, each of these is recorded here
(and in the punchlist Gates) with its reject behavior + future home:

- **Array layers / cubemap faces → v3.4 (Phase AL-ARRAY).** mabda is 2D-only.
  The v3.3 parsers *read* `layerCount`/`faceCount`/`arraySize` and the cubemap
  caps/misc bits specifically so they **reject precisely** (`GPU_ERR_FORMAT_
  UNSUPPORTED`) rather than mis-upload. v3.4 adds `gpu_texture_create_2d_array`
  / `_cube` + a `(level, layer)` write slot.
- **KTX2 supercompression (BasisLZ / Zstandard / ZLIB) → post-v3.3.** Needs a
  pure-Cyrius Zstd/Basis decoder that does not exist. `supercompressionScheme
  != 0` fails loud. (The ZLIB scheme could ride `sankoch` — a candidate cheap
  follow-up if a consumer needs it.)
- **JPEG → chitra v0.2+ / a later arc.** Out of v3.3 scope; tracked in the
  companion proposal.
- **sRGB formats.** mabda has no `_SRGB` ids today (the #1 silent-wrong risk —
  loading sRGB data as UNORM mis-colors it). v3.3 must pick a policy in AL.0:
  carry an `is_srgb` flag the loader surfaces, or add `MABDA_TEXFMT_*_SRGB` ids.
  Decision recorded at impl.

## HW-verification

KTX2/DDS BC loading + sampling is HW-verifiable on the Cezanne (gfx90c) dev box
(BC sampling is HW-proven since 3.2.3). **ETC2/ASTC remain HW-blocked on this
APU** (final) — those load+store but cannot sample on native, which the caps
gate catches at load time; wgpu handles all families. PNG → RGBA8 → sample is
fully verifiable on Cezanne.

## Risks

See the punchlist **Gates & risks** for the full register. The load-bearing
ones: the **caps-threading prerequisite** (the gate is uncodeable without it),
**format-number pinning** (silent-wrong if off), **sRGB collapse**, the **wgpu
256-byte `bytesPerRow` alignment** for uploads, and the **chitra cross-repo
cut-before-wire** edge. Inflate is **not** a risk — `sankoch` owns it.
