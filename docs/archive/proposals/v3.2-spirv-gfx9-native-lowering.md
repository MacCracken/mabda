# Proposal: v3.2 SPIR-V → GFX9 ISA Native Lowering (the in-mabda compiler backend)

**Status:** Proposed (v3.2.2+ design). The single largest, highest-risk
piece of engineering in mabda's history.
**Date:** 2026-06-15.
**Arc:** Third feature of the v3.2.x line ("Texture & Shader Breadth"),
landing *after* compressed textures (3.2.0) and the SPIR-V *frontend
plumbing* (3.2.1). See
[`roadmap.md` § v3.2](../development/roadmap.md#v32--texture--shader-breadth).
**Companions:** the (separate) `v3.2-compressed-textures.md` and
`v3.2-spirv-shader-support.md` proposals. This document covers **only**
the native AMD compiler back end: turning a SPIR-V compute module into
GFX9 ISA bytes that the existing native dispatch path can run.
**Anchors it builds on:** `docs/proposals/v3-wgsl-frontend-choice.md`
(the deferred-frontend rationale — SPIR-V→GFX9 is the same class of
problem and a shared GFX9 back end serves both), the hand-authored ISA
in `src/backend_native_shaders.cyr`, the dispatch ABI in
`src/backend_native_pm4.cyr`, and the byte-polymorphic
`shader_module_create` slot in `src/backend.cyr`.

## Why this is the riskiest mabda work to date — stated up front

Everything mabda has shipped so far is **fixed, hand-verified byte
streams**. The downsample shader (`native_gfx9_shader_downsample_2x2`,
`src/backend_native_shaders.cyr:135`) is 79 instructions a human wrote,
ran through `llvm-mc`, and pinned with CPU asserts. The PM4 composers are
the same: every dword is a constant a person checked against Mesa
`gfx9.json` and a RADV IB capture. When something was wrong (the
`0xF8`-vs-`0xC4` EXP opcode, the `0xE`-vs-`0x9` COL_FORMAT field, the
`TC_NC` ACQUIRE_MEM bit), the fix was a *one-dword edit* and a re-run of
the oracle.

A compiler is the opposite. It emits bytes that **no human checked**, for
inputs **no human saw**, from a SPIR-V module a consumer's toolchain
produced. The failure modes are unbounded:

- **A register-allocation bug** writes a VGPR the shader later reads as
  garbage — no decoder error, just a wrong pixel or a hang, on *some*
  inputs.
- **An RSRC1 mis-encoding** (VGPRS/SGPRS field one off) under-allocates;
  the wave clobbers another wave's registers. Intermittent, input-shaped.
- **A control-flow lowering bug** (EXEC mask / `s_cbranch` target wrong)
  diverges silently and corrupts results only when lanes actually
  diverge.
- **An address-calculation bug** in a `global_store` writes out of the
  BO and either faults (best case) or corrupts an adjacent allocation
  (worst case, and a *security* concern — see Risks).

There is no `llvm-mc` oracle for arbitrary generated code the way there is
for one fixed shader. The mitigation strategy (below) is built entirely
around **manufacturing oracles**: differential testing against the bytes
we already trust, and against `llvm-mc` round-trips of every instruction
*form* we emit. This is why the MVP's exit criterion is not "compile a new
shader" but "**recompile the downsample shader we already trust, from its
SPIR-V, and match the hand-authored bytes** (or prove the divergence is a
legal alternative encoding that runs identically on Cezanne)." That fixed
shader is the bring-up oracle the whole effort pivots on.

## Why from-SPIR-V, not from-WGSL, is the right first compiler

`docs/proposals/v3-wgsl-frontend-choice.md` deferred the WGSL→GFX9
frontend and recorded that, when a compiler is built, it should be
"compute subset first." This proposal makes the concrete call the maintainer
has opted into: **the first compiler mabda builds takes SPIR-V as input,
not WGSL.** Reasons, in priority order:

1. **SPIR-V is already a parsed, typed, SSA-adjacent binary IR.** WGSL is
   surface syntax — a WGSL frontend must do lexing, parsing, name
   resolution, type inference, and de-sugaring *before* it has anything an
   instruction selector can chew on. The
   `v3-wgsl-frontend-choice.md` LoC estimate put ~2k lines on the WGSL
   parser alone. SPIR-V hands us SSA values, explicit types, explicit
   control-flow blocks, and decoration-based binding info in a
   word-stream that is **trivial to parse** (a 5-word header + uniform
   `(opcode, wordcount)` instructions). Starting from SPIR-V deletes the
   entire front half of the WGSL project and lets the first compiler
   focus its risk budget where the danger actually is — **the back end**
   (instruction selection, register allocation, encoding).

2. **The back end is the shared, reusable, vendor-spanning asset.** Both a
   future WGSL frontend *and* this SPIR-V path want the *same* GFX9 code
   generator. The roadmap's v4.0 NVIDIA section
   (`roadmap.md:374`) already says "the WGSL → ISA lowering path from v3.0
   informs the architecture but the back end is fully replaced" — i.e.
   the architecture explicitly anticipates **frontend/back-end
   separation**. Building the SPIR-V→GFX9 back end first establishes that
   IR boundary cleanly; a later WGSL frontend becomes a *second producer*
   of the same IR (`tarjuma`/`karkati`, the to-be-named frontend package),
   not a parallel reimplementation.

3. **It is the path the f64 consumer actually needs.** The roadmap
   (`roadmap.md:317-331`) names **attn11** as the f64-compute consumer and
   states the hard fact: **WGSL has no f64** (gpuweb #2805, deferred), so
   the f32-only WGSL path *cannot* carry attn11's f64 oracle. SPIR-V +
   Vulkan `shaderFloat64` *can*. f64 is therefore reachable **only**
   through a SPIR-V path. A WGSL-first compiler would have to be thrown
   away or bypassed the moment f64 mattered. SPIR-V-first means f64 is an
   *extension* of the same compiler (Phase F), not a new project.

4. **SPIR-V has industrial producers we don't have to write.** Consumers
   can emit SPIR-V from `glslangValidator`, `clang -target ...
   -emit-spirv`, `slang`, or Rust's `rust-gpu` — at *their* build time,
   exactly as they already pre-compile GFX9 ISA bundles in v3.0/v3.1. We
   own the back end (the sovereign part); we don't own a shading-language
   parser (the part with the least leverage). This matches every
   "own the stack" call mabda has made.

**The frontend is still deferred.** WGSL→SPIR-V (or WGSL→IR) remains
out of scope here and is a separate, later package. This proposal does
not relitigate that; it builds the back end the frontend will eventually
feed.

## Relationship to the rest of v3.2

```
3.2.0  Compressed textures (BC/ETC2/ASTC)      — separate proposal
3.2.1  SPIR-V frontend plumbing                — separate proposal:
         - kind-tagged shader_module_create (SHADER_KIND_WGSL / _SPIRV / _GFX9_ISA)
         - wgpu backend: SPIR-V passthrough (wgpuShaderSourceSPIRV — wgpu-native
           accepts SPIR-V directly; this is a thin FFI add, NOT a compiler)
         - shader_cache keyed on (kind, hash)
         - native backend: SPIR-V kind returns GPU_ERR_NOT_IMPLEMENTED (honest)
3.2.2+ Phase N — NATIVE SPIR-V → GFX9 compiler  — THIS proposal
```

3.2.1 is the cheap, low-risk win: wgpu-native already consumes SPIR-V
(`WGPUShaderSourceSPIRV` in webgpu.h v29), so the *wgpu* SPIR-V story is
an FFI passthrough, not a compiler. That ships first and unblocks every
wgpu consumer who has SPIR-V. The **native** SPIR-V story is this
document — and it is where all the risk lives. Keeping 3.2.1 (plumbing)
separate from Phase N (compiler) means the SPIR-V *feature* can ship on
wgpu while the native compiler is still in bring-up, exactly as 3.1.0
shipped native mipmaps while the wgpu generate path stayed
`NOT_IMPLEMENTED`.

## Current state — what exists, and what the compiler must produce

The compiler does not start from nothing. mabda already owns every
*downstream* stage; the compiler fills the gap between "SPIR-V bytes" and
"a BO of GFX9 ISA at a canonical-high VA":

- **The byte-polymorphic slot exists but is a native stub.**
  `BACKEND_SLOT_SHADER_MODULE_CREATE` (`src/backend.cyr:112`, offset 48)
  is wired on both backends. On native,
  `_backend_native_shader_module_create(ctx, bytes_ptr, n)`
  (`src/backend_native.cyr:461`) currently `return 0` — a documented
  stub, because v3.0/v3.1 native shaders come from the in-tree
  `native_gfx9_shader_*` helpers, not this API. **This stub is exactly
  where the compiler plugs in:** native `shader_module_create` will
  (when kind == SPIRV) run the Phase N pipeline and publish the resulting
  ISA bytes into a BO, returning a `(handle, va)` module pair — the same
  shape `_backend_native_compute_dispatch` already consumes
  (`src/backend_native.cyr:492-493` reads `load64(shmod+0)` /
  `load64(shmod+8)`).

- **The ISA encoders exist** and are the compiler's output stage.
  `src/backend_native_shaders.cyr` already encodes VOP1
  (`v_mov_b32`), VOP2 (`v_lshlrev_b32`, `v_and_b32`, `v_add_u32`), VOP3
  (`v_add3_u32`, `v_bfe_u32`, `v_or3_b32`), SOP2 (`s_mul_i32`,
  `s_lshl_b32`, `s_add_i32/u32`, `s_addc_u32`), SOPP (`s_waitcnt`,
  `s_endpgm`, `s_nop`), and FLAT/global (`global_load_dwordx2`,
  `global_store_dword`) — *every instruction class the f32 MVP needs is
  already hand-encoded somewhere in this file.* The compiler's encoder
  stage **generalizes these from fixed-operand constants into
  operand-parameterized emitters** (e.g. a general
  `gfx9_enc_vop2(op, vdst, src0, vsrc1)` whose fixed-operand uses
  reproduce the existing `0x24040081`-style constants). The existing
  constants become the encoder's first unit tests.

- **The RSRC1/RSRC2 + USER_DATA ABI is fully specified and HW-proven.**
  `native_pm4_build_compute_downsample` (`src/backend_native_pm4.cyr:594`)
  documents the exact contract: RSRC1 `0x2C0083` (VGPRS field for 16
  VGPRs, SGPRS field for 24 SGPRs, FLOAT_MODE=0xC0, DX10_CLAMP), RSRC2
  `0x18C` (USER_SGPR=6 | TGID_X_EN | TGID_Y_EN), USER_DATA_0/1 = src VA,
  _2/3 = dst VA, _4 = dst_w, workgroup id in s6/s7. The compiler's
  **RSRC + ABI stage** computes these *from the register-allocation
  result and the SPIR-V binding decorations* instead of hardcoding them.
  This is the "USER_DATA-VA ABI mabda already uses" the MVP targets.

- **The dispatch + BO + VA + syncobj path is done.**
  `native_compute_dispatch_cached` (`src/backend_native.cyr:63`),
  `native_bo_create_gtt`, `native_gem_va_map`, the texture VA
  sub-allocator (`native_ctx_alloc_texture_va`,
  `src/backend_native.cyr:1312`), and the shader-BO publish pattern in
  `_backend_native_texture_generate_mipmaps`
  (`src/backend_native.cyr:707-719`, including the `_native_align_up(...,
  4096)` GEM_VA page-alignment fix) are all HW-verified on Cezanne. The
  compiler reuses every one of these verbatim; it only changes *what
  bytes go in the shader BO*.

- **Verification tooling exists.** `scripts/disasm-shaders.sh` already
  round-trips the downsample shader through
  `llvm-mc --disassemble --arch=amdgcn --mcpu=gfx90c`. Per project memory
  (`feedback_verify_gfx9_shader_bytes_with_llvm_mc`), llvm-mc is the
  encoding oracle and Mesa `gfx9.json` is the register-address authority
  (`feedback_gfx9_register_authoritative_source`). The compiler bring-up
  leans on both as automated differential oracles (Phase N.0).

So the compiler is a **middle insert**: SPIR-V in, ISA bytes out, with the
encoders, ABI, dispatch, BO, VA, and verification harness all already
present. That is what makes a from-SPIR-V compiler *tractable* in mabda's
manual-memory, no-external-deps world — but "tractable" still means a
multi-minor, highest-risk effort.

## The pipeline (six stages)

```
SPIR-V binary
   │  N.1  parse: header + (opcode,wordcount) stream → typed instruction list
   ▼
SPIR-V module model (types, constants, globals/bindings, functions, blocks)
   │  N.2  lower to mabda-IR (MIR): linear SSA, GFX9-flavored value classes
   ▼                              (scalar-uniform vs vector-divergent)
MIR (SSA, basic blocks, explicit types, uniformity-classified values)
   │  N.3  instruction selection: MIR op → GFX9 instruction(s)
   ▼
GFX9 instruction list (virtual registers, not yet allocated)
   │  N.4  register allocation: virtual regs → physical VGPR / SGPR
   ▼                            (+ s_waitcnt insertion for memory ops)
GFX9 instruction list (physical registers)
   │  N.5  encode: each instruction → dword(s) via the generalized encoders
   ▼       (reuses/generalizes src/backend_native_shaders.cyr emitters)
ISA byte stream
   │  N.6  ABI wiring: compute RSRC1 (from VGPR/SGPR high-water marks),
   ▼       RSRC2 (USER_SGPR from binding count, TGID_* from builtin use),
           USER_DATA layout (binding VAs), prefetch NOP padding
(ISA bytes, RSRC1, RSRC2, USER_DATA descriptor) → publish to BO → dispatch
```

Each stage is small, independently CPU-testable, and ordered so the
*output* of the previous stage is the *fixture* for the next. The whole
thing lives in new `src/` modules under the existing flat layout
(no transitive includes; `src/lib.cyr` owns the chain):

```
src/spirv_parse.cyr     — @internal: SPIR-V word-stream parser → module model
src/mir.cyr             — @internal: mabda-IR types + SSA value/block model
src/spirv_lower.cyr     — @internal: SPIR-V module → MIR
src/gfx9_isel.cyr       — @internal: MIR → GFX9 virtual-reg instruction list
src/gfx9_regalloc.cyr   — @internal: VGPR/SGPR allocation + s_waitcnt
src/gfx9_encode.cyr     — @internal: generalized GFX9 instruction encoders
                          (lifts the fixed emitters out of backend_native_shaders.cyr)
src/gfx9_compile.cyr    — @internal: top-level driver: spirv_bytes → (isa, rsrc1, rsrc2, abi)
```

`backend_native_shaders.cyr`'s existing hand-authored shaders **stay** —
they remain the fallback/oracle library and the bring-up ground truth.
`gfx9_encode.cyr` factors out *reusable* operand-parameterized encoders;
the existing fixed shaders can be re-expressed in terms of them as a
regression check (each fixed shader must round-trip to its known bytes
through the new encoders).

### Stage N.1 — SPIR-V parse

SPIR-V is a word stream: a 5-word header (magic `0x07230203`, version,
generator, id-bound, schema) followed by instructions, each
`word[0] = (wordCount << 16) | opcode`. The parser:

- Validates magic + endianness + id-bound (reject malformed/oversize up
  front — input validation is the first audit gate; a compiler ingests
  fully untrusted bytes).
- Walks instructions into a module model: `OpType*` (the type table),
  `OpConstant*`, `OpVariable` with `StorageClass` + `Binding`/`DescriptorSet`
  decorations (the buffer bindings), `OpFunction`/`OpLabel`/`OpBranch*`
  (control-flow structure), and the executable instruction stream per
  block.
- Records `OpEntryPoint` (`GLCompute` execution model) + `OpExecutionMode`
  (`LocalSize` = workgroup dims) — these feed the dispatch's NUM_THREAD.

Pure byte walking, no syscalls. Every field validated against the SPIR-V
spec section cited in the module header. **This is the lowest-risk stage**
and lands first (N.1).

### Stage N.2 — lower to MIR

MIR is a deliberately small SSA IR shaped for GFX9, not a general
optimizer IR:

- **Value classes carry GFX9 uniformity.** The single most important
  GFX9 fact: *uniform* values (same across the wave) live in **SGPRs** and
  use **SALU**; *divergent* values (per-lane) live in **VGPRs** and use
  **VALU**. The existing downsample shader is the proof — its address math
  is all SALU (`s_mul_i32`/`s_lshl_b32`/`s_add_u32`) precisely because
  "every input is uniform (single thread)"
  (`backend_native_shaders.cyr:124`). MIR classifies each value as
  `UNIFORM` or `DIVERGENT` (a simple forward propagation from
  uniform sources — constants, push-constant/user-data loads, workgroup
  id — vs divergent sources — local invocation id, divergent loads). This
  classification *is* the scalar-vs-vector instruction-selection decision.
- Types: i32, u32, f32 for the MVP; i64/f64 added in Phase F; vectors
  (vec2/3/4) as register tuples.
- Memory: `OpLoad`/`OpStore` through `OpAccessChain` on a
  `StorageBuffer`-class variable → a (binding, byte-offset-expression)
  pair the isel stage turns into a flat global address.

### Stage N.3 — GFX9 instruction selection

A switch from MIR op + operand uniformity to GFX9 instruction(s):

- f32 ALU: `OpFAdd`→`v_add_f32`, `OpFMul`→`v_mul_f32`,
  `OpFma`→`v_fma_f32`, etc. (VALU when any operand divergent).
- i32/u32 ALU: `OpIAdd`/`OpIMul`/`OpShiftLeft`/`OpBitwiseAnd`… → the VOP2/
  VOP3 *or* SOP2 form depending on uniformity (the existing
  `v_and_b32`/`s_add_i32` encoders are the templates).
- Memory: `OpLoad`/`OpStore` on a buffer → address-calc instructions
  (`s_add_u32`/`s_addc_u32` for uniform base+offset, exactly the
  downsample pattern) + `global_load_dword{,x2,x4}` / `global_store_dword`
  with the `off`/`saddr` form the existing FLAT encoders use.
- Builtins: `LocalInvocationId`/`WorkgroupId`/`GlobalInvocationId` →
  the system-VGPR / TGID-SGPR sources the ABI provides (TGID in s6/s7 per
  RSRC2 `TGID_X|Y`, exactly as downsample reads them).
- Constants → inline-constant operands where the VOP src table allows
  (the `0.0`=128, `1.0`=242, `-1`=193 inline encodings the existing
  shaders use), else a literal dword following the instruction (the
  `src0=255 → literal follows` pattern at
  `backend_native_shaders.cyr:99`).

Output is a list of GFX9 instructions over **virtual** registers.

### Stage N.4 — register allocation (VGPR/SGPR)

The classic-hard stage, scoped down hard for the MVP:

- **Two separate register files** (VGPR, SGPR) allocated independently —
  GFX9's fundamental split.
- **MVP allocator = linear-scan over live intervals**, no spilling. If the
  shader needs more than the file size (104 VGPRs / ~102 SGPRs usable),
  the MVP **fails the compile with a clear error** rather than spilling to
  scratch — spilling (scratch ring + `SPI_TMPRING_SIZE`/RSRC scratch bits)
  is a later bite (N.4-spill), and the compute consumers in scope
  (downsample, attn11 elementwise/matmul tiles) are register-light by
  design. Failing loud beats a subtly wrong spill (ADR 006 spirit).
- Reserves the ABI-fixed registers first: user-data SGPRs (s0..sN per
  binding count), TGID SGPRs, system VGPRs (v0 = local id), matching the
  dispatch ABI exactly so the allocator never hands out a physical
  register the CP is going to overwrite at launch.
- **`s_waitcnt` insertion** is folded in here: after every memory op,
  before the first use of its result, insert the right
  `vmcnt`/`lgkmcnt` wait (the `0xBF8C0070` / `0xBF8C0F70` the downsample
  shader places by hand). Getting this wrong = reading stale/garbage
  memory results — a top-tier correctness risk, so it gets its own dense
  test suite (a use-before-wait must be impossible by construction).
- The **VGPR/SGPR high-water marks** are the inputs to RSRC1 (N.6).

### Stage N.5 — ISA encoding

Generalized, operand-parameterized encoders in `gfx9_encode.cyr`, one per
GFX9 instruction format the MVP touches: VOP1, VOP2, VOP3a/b, SOP1, SOP2,
SOPK, SOPP, and FLAT(global). Each is the lift of an existing fixed
emitter:

- The existing `0x24040081` (`v_lshlrev_b32_e32 v2, 1, v0`) becomes
  `gfx9_enc_vop2(OP_LSHLREV_B32, vdst=2, src0=inline(1), vsrc1=0)`.
- The existing `0xDC548000 / 0x047F0000` two-dword
  `global_load_dwordx2 v[4:5], v[0:1], off` becomes
  `gfx9_enc_global_load(OP_LOAD_DWORDX2, vdata=4, vaddr=0, saddr=OFF, off=0, glc=0, slc=0)`.

**Critical regression gate:** re-encoding the *exact operands* of every
hand-authored shader through these general encoders must reproduce the
byte-for-byte constants already pinned in `backend_native_shaders.cyr`.
That is a free, powerful oracle: it proves the encoders correct against
~100 known-good dwords *before any generated code runs on hardware*. Plus
every encoder form is round-tripped through `llvm-mc` in CI-adjacent dev
tests (extending `scripts/disasm-shaders.sh`).

### Stage N.6 — RSRC1/RSRC2 + USER_DATA ABI wiring

The output-shaping stage, computed *from the compile result* rather than
hardcoded:

- **RSRC1** = `FLOAT_MODE(0xC0) | DX10_CLAMP | encode_vgprs(vgpr_hw) |
  encode_sgprs(sgpr_hw)`. The VGPRS field is `ceil(vgprs/4)-1`, SGPRS is
  the GFX9 step encoding — *exactly the math the comments at
  `backend_native_shaders.cyr:34-46` and the `0x2C0083` downsample value
  document*, now computed instead of written.
- **RSRC2** = `USER_SGPR(binding_count_rounded) | TGID_X_EN/Y_EN/Z_EN`
  (set per which workgroup-id components the shader actually reads) |
  `TRAP_PRESENT` if the shader touches memory (the mandatory bit at
  `backend_native_shaders.cyr:225-232`).
- **USER_DATA descriptor**: an ordered list of (user-data-slot → binding
  VA) the dispatcher writes into `R_COMPUTE_USER_DATA_*` before dispatch.
  The compiler *emits the layout*; the dispatcher (a generalized
  `native_pm4_build_compute_generic`, sibling of
  `native_pm4_build_compute_downsample`) consumes it. This is the seam
  between the compiler and the existing PM4 path.
- **Prefetch NOP padding**: append the 16× `s_nop 0` tail every shader
  needs (`backend_native_shaders.cyr:105-109`).

The result `(isa_bytes, isa_len, rsrc1, rsrc2, user_data_layout)` is what
native `shader_module_create` publishes into a BO (reusing the
`_backend_native_texture_generate_mipmaps` publish pattern) and stashes on
the module, ready for dispatch.

## The bring-up oracle: recompile downsample_2x2 from SPIR-V

The MVP is **not** "compile an arbitrary shader." It is:

> Hand-write (or `clang -emit-spirv` / `glslang`) the SPIR-V for the
> *exact same* 2×2 box-filter downsample that
> `native_gfx9_shader_downsample_2x2` implements, run it through Phase N,
> and assert the output ISA either (a) byte-matches the hand-authored
> shader, or (b) differs only in ways proven equivalent (alternate
> legal encodings, different-but-correct register choices) **and** the
> recompiled shader passes `native_mipmap_e2e` on Cezanne with
> byte-identical mip results.

This is the perfect oracle because:

- The hand-authored bytes are **already trusted and HW-verified**
  (M.7 passed on Cezanne, `3-1-punchlist.md`).
- The ABI is already fixed and known (the `0x2C0083` / `0x18C` / USER_DATA
  contract).
- `native_mipmap_e2e` already exists as the end-to-end check — swap the
  shader source from "hand-authored helper" to "compiler output" and the
  *whole rest of the stack is unchanged*. A green run = the compiler
  produced runnable, correct GFX9 from SPIR-V.

Hitting (a) byte-equality is the strong win; (b) equivalence-up-to-encoding
is the realistic win and is itself a real milestone. Either way the oracle
is concrete, automated, and grounded in code that already runs.

## Phase N — staged delivery across the 3.2.x line

Each bite is independently verifiable and ends green
(build / lint / fmt / vet / distlib / version-check clean; every new path
adds a CPU assertion — the house rule). HW gates run on Cezanne via new
`programs/native_spirv_*` programs. The phasing front-loads the *oracle
infrastructure* so generated code is never trusted without a check.

- **N.0 — Oracle harness + encoder lift (3.2.2).** Lift the fixed emitters
  in `backend_native_shaders.cyr` into operand-parameterized
  `gfx9_encode.cyr` encoders; prove every existing hand-authored dword
  re-encodes byte-identically (the ~100-dword regression oracle). Extend
  `scripts/disasm-shaders.sh` into a per-form `llvm-mc` round-trip
  driver. No SPIR-V yet. **Pure CPU; the safety net before any generated
  code exists.**
- **N.1 — SPIR-V parser (3.2.2).** `spirv_parse.cyr`: header + instruction
  stream + type/constant/decoration tables + entry-point/exec-mode.
  Fuzz-style malformed-input rejection tests. Fixture: the downsample
  SPIR-V module. Pure CPU.
- **N.2 — MIR + lowering skeleton (3.2.3).** `mir.cyr` + `spirv_lower.cyr`:
  SPIR-V module → SSA MIR for a *straight-line* (no control flow) compute
  function; uniformity classification. Assert MIR shape on the downsample
  fixture. Pure CPU.
- **N.3 — Instruction selection, straight-line f32/i32 (3.2.3).**
  `gfx9_isel.cyr`: MIR → virtual-register GFX9 list for ALU + global
  load/store + builtins, matching the downsample op set. Assert the
  selected op sequence. Pure CPU.
- **N.4 — Register allocation + s_waitcnt (3.2.4).** Linear-scan VGPR/SGPR,
  ABI-register reservation, waitcnt insertion, no-spill fail-loud.
  Dense waitcnt-correctness tests. Pure CPU.
- **N.5 — Encode + ABI wiring + the BRING-UP ORACLE (3.2.4).**
  `gfx9_encode.cyr` end-to-end + `gfx9_compile.cyr` driver + RSRC/USER_DATA
  computation. **Recompile downsample from SPIR-V; assert byte-match or
  proven-equivalent vs the hand-authored shader.** Then native
  `shader_module_create` (SPIRV kind) publishes the compiler output, and
  `programs/native_spirv_downsample_e2e.cyr` runs it on Cezanne and
  verifies mip results match the hand-authored path byte-for-byte.
  **This is the MVP exit criterion** — the smallest end-to-end SPIR-V→GFX9
  compute that runs on hardware.
- **N.6 — A second, independent compute kernel (3.2.5).** A kernel the
  compiler has *never seen as hand-authored bytes* — e.g. a SAXPY /
  elementwise `y = a*x + y` over storage buffers (attn11's simplest op
  shape). Differential oracle: a CPU reference computes the expected
  output; the GPU result must match. This is the first time generated code
  has no byte-level twin — the test moves from byte-equality to
  *numerical* equality. New `programs/native_spirv_saxpy_e2e.cyr`.
- **N.7 — Control flow (3.2.5/3.2.6).** Structured `if`/`else`/`loop`
  (SPIR-V `OpSelectionMerge`/`OpLoopMerge` + `OpBranchConditional`) lowered
  with EXEC-mask manipulation (`s_and_saveexec_b64` /`s_cbranch_execz`/
  `s_or_b64` restore — the standard GFX9 divergent-CF idiom) for divergent
  branches, and `s_cbranch_scc*` for uniform branches. **The single
  hairiest correctness area** (divergence bugs are silent and
  input-shaped); gets a dedicated divergent-vs-uniform test matrix and CPU
  reference oracles. May span two bites (uniform CF first, then divergent).
- **N.8 — Op breadth + vectors + the generic dispatcher (3.2.6).** Fill out
  the f32/i32/u32 op set attn11 and the other compute consumers need
  (transcendentals via `v_exp_f32`/`v_log_f32`/`v_rcp_f32` macro-sequences,
  min/max/clamp, integer mul-hi, vec2/3/4 as register tuples,
  multi-binding USER_DATA). Generalize the PM4 dispatcher
  (`native_pm4_build_compute_generic`) so arbitrary binding counts +
  workgroup dims dispatch. Each op: CPU-reference differential test.
- **N.F (feeds Phase F) — native f64 emit (3.2.11, this arc).** The native
  f64 opcode coverage Phase F's F.7 routes consumer SPIR-V through. The
  roadmap-named attn11 enabler. f64 is a SPIR-V-only capability (WGSL has
  none). Scope:
  - **Types/regs:** f64 is a VGPR *pair* (or SGPR pair when uniform); the
    register allocator gets 64-bit value support (aligned pairs).
  - **ALU:** `v_add_f64`/`v_mul_f64`/`v_fma_f64`/`v_rcp_f64` (VOP3, 64-bit
    operands) — encode + llvm-mc-verify each form.
  - **Memory:** `global_load_dwordx2`/`global_store_dwordx2` for f64
    scalars (the dwordx2 form already exists in the encoders).
  - **RSRC/throughput honesty:** document loudly that f64 is ~1:16–1:32
    rate on Cezanne/consumer-RDNA; correctness, not speed, is the
    deliverable here. The full-rate CDNA `V_MFMA_F64` route needs CDNA
    silicon (absent from the dev box) — the correctness path ships in this
    arc; MFMA full-rate is a **flagged HW-verification gap** in the
    punchlist (not deferred work, a hardware-availability item).
  - **Oracle:** attn11's CPU f64 reference is the differential oracle by
    construction (its whole reason for needing f64). A
    `programs/native_spirv_f64_e2e.cyr` runs a small f64 kernel and matches
    a CPU f64 computation to ULP.
  - **Sequencing (no escape hatch):** f64 (Phase F) is sequenced after
    Phase N at **3.2.10–3.2.11**, a committed part of this arc. If N.7/N.8
    run long, the f64 minors move later **within 3.2.x** — never to v3.3 or
    a separate line.

**Slot/struct impact.** No new Backend slot is required: the compiler is
the *implementation* behind the existing `BACKEND_SLOT_SHADER_MODULE_CREATE`
(offset 48) for the SPIRV kind. `BACKEND_SIZE` stays 248
(`src/backend.cyr:202`). The native shader-module struct grows from the
`(handle, va)` pair to also carry `(rsrc1, rsrc2, user_data_layout_ptr,
local_size_xyz)` so the generic dispatcher can program them — an additive
struct change behind `@internal`, public API unchanged (ADR 005: same
public surface both backends; the wgpu side already routes SPIR-V through
3.2.1's passthrough).

## What this does NOT do (honest scope boundaries)

- **No WGSL frontend.** Still deferred (`v3-wgsl-frontend-choice.md`). This
  builds the back end a future WGSL→IR frontend will feed; it does not
  build that frontend.
- **No graphics shaders (VS/FS).** Compute-only, as the
  v3-wgsl-frontend-choice.md staging dictated ("compute subset first").
  Vertex/fragment SPIR-V lowering (interpolants, exports,
  `SPI_PS_INPUT_*`, the EXP-encoding minefield) is a *later* phase, scoped
  against a real graphics consumer hitting the wall.
- **No texture sampling (image ops).** The native mipmap pivot already
  proved linear textures + flat addressing avoid descriptor tables for the
  box-filter case (`3-1-punchlist.md` PIVOT); general `image_sample` needs
  the T#/V# descriptor infra that pivot deliberately deleted. Out of scope;
  later phase, real-consumer-gated.
- **No optimizer.** Linear-scan regalloc, no spilling (fail-loud over
  cap), no instruction scheduling beyond waitcnt correctness, no constant
  folding beyond what SPIR-V already provides. Correctness first; the
  v3-wgsl-frontend-choice.md "best ISA backend is Mesa ACO" reckoning
  stands — mabda is not out-competing ACO, it is owning a *correct,
  minimal, sovereign* compute back end for the consumers it has.
- **No multi-vendor.** GFX9-only (Cezanne/gfx90c). The IR boundary is
  designed to *inform* the v4 NVIDIA back end (`roadmap.md:374`) but does
  not abstract for it yet — premature vendor abstraction with one vendor is
  speculative.

## Open questions for the maintainer

- **Hand-write the bring-up SPIR-V, or generate it from
  `clang`/`glslang`?** Hand-writing the downsample SPIR-V gives a minimal,
  fully-understood fixture (no compiler-emitted bloat to lower); generating
  it tests the realistic consumer path. Recommendation: **both** — a
  hand-written minimal fixture for N.1–N.5 bring-up, then a
  `glslang`-generated module as a second N.5 fixture before declaring the
  MVP done.
- **Frontend package name** when WGSL→IR eventually lands —
  `tarjuma` (Arabic, "translation") / `karkati` (Sanskrit) per
  `v3-wgsl-frontend-choice.md`'s reviewer prompt. Not decided here; the IR
  boundary this proposal establishes is what makes that package possible.
- **Does Phase F (f64) gate 3.2 close, or graduate?** Recommendation: keep
  it the *last* Phase N bite with explicit permission to slip to its own
  minor / 3.3, so the f32 compute MVP + control flow + op breadth can ship
  as the 3.2 deliverable even if f64 needs more bring-up time on real
  attn11 kernels.

## Exit criteria

**MVP (N.5, ~3.2.4):**
- Native `shader_module_create` compiles the downsample SPIR-V to GFX9 ISA
  and `programs/native_spirv_downsample_e2e.cyr` produces a mip chain on
  Cezanne **byte-identical** to the hand-authored path's
  `native_mipmap_e2e`.
- Every generalized encoder reproduces the existing hand-authored dwords
  byte-for-byte (the ~100-dword regression oracle) and round-trips through
  `llvm-mc`.
- CPU suite: parser validation, MIR shape, isel sequence, regalloc +
  waitcnt correctness, RSRC/ABI computation — every stage byte/shape-pinned
  (house rule). Audit re-run (a compiler ingests untrusted input — input
  validation, address-calc overflow, BO-bounds on every generated store).
- lint / fmt / vet / distlib / version-check clean; CHANGELOG `[3.2.x]`.

**Phase N close (f32 + control flow + op breadth, ~3.2.6):**
- A SPIR-V compute kernel the compiler never saw as hand-authored bytes
  (SAXPY + a control-flow kernel) runs on Cezanne and matches a CPU
  reference numerically.
- Control flow (uniform + divergent) verified against a divergence test
  matrix.

**Phase F (f64, 3.2.7 or graduated):**
- An f64 compute kernel matches a CPU f64 reference to ULP on Cezanne;
  attn11 can carry its f64 oracle on the native path. Throughput caveats
  documented per `roadmap.md`.
