# Proposal: v3.1 Multi-Queue Coordination (logical ordering abstraction)

**Status:** Proposed (v3.1.1+ design).
**Date:** 2026-06-15.
**Arc:** Second feature of the v3.1.x arc — ships *after* mipmaps (3.1.0).
See [`docs/development/3-1-punchlist.md`](../development/3-1-punchlist.md).
**Roadmap:** [`roadmap.md` § v3.1](../development/roadmap.md#v31--mipmaps--multi-queue-consumer-catch-up).
**Companion:** [`v3.1-mipmap-generation.md`](v3.1-mipmap-generation.md).

## Summary

Add multi-queue coordination: consumers submit work to named logical
queues (GRAPHICS / COMPUTE / TRANSFER) and express ordering between them,
so a compute pass can overlap a graphics pass (rasa: compute+present
overlap; bijli: large transfer + compute). The public API is identical on
both backends, but **the abstraction is *ordering*, not *parallelism*** —
see the hard truth below.

## Hard truth up front: wgpu has exactly one queue

WebGPU defines exactly **one default queue per device**
(`wgpuDeviceGetQueue` returns the single queue; wgpu-native v29 exposes no
way to create another — confirmed against `src/wgpu_ffi.cyr` and the
spec). There is no `queue_create` and no `queue_submit_multiple` in the
FFI. **Real cross-queue parallelism is physically impossible on the wgpu
backend.** Native AMD, by contrast, has independent hardware rings
(`AMDGPU_HW_IP_GFX`, `_COMPUTE`, and `_DMA` once wired) that the kernel
scheduler runs concurrently.

The chosen resolution (see the 3.1 planning decision, 2026-06-15) is to
define multi-queue as a **logical ordering/dependency abstraction**:

- The public API exposes named queues and explicit cross-queue
  dependencies (signal/wait), not a parallelism guarantee.
- **wgpu**: all logical queues fold onto the one underlying `WGPUQueue`;
  cross-queue dependencies are satisfied by submit ordering. Behavior is
  **correct and complete** (the consumer's declared ordering is honored)
  — just serialized, no overlap. This is a real, complete implementation,
  not a stub, so it satisfies ADR 006's no-fail-silent rule and ADR 005's
  same-API-both-backends rule.
- **native AMD**: each logical queue maps to a hardware ring; cross-queue
  dependencies become timeline-syncobj wait/signal across rings — real
  concurrency.

This is exactly the v3.0 "same public API, backend-specific performance"
story: consumer code is byte-identical; native gets the win, wgpu stays
correct. Consumers that *need* the overlap are on the native path anyway
(and at v4.0 native becomes the sole AMD path).

## Current state

- **One queue, both backends.** wgpu: a single `WGPUQueue` at
  `GpuContext+24`, fetched once at preinit (`src/context.cyr:24,61`,
  `src/backend_wgpu.cyr`). native: `ip_type` (GFX or COMPUTE) is chosen
  at each call site — `native_compute_dispatch_cached` (GFX_IP_COMPUTE)
  and `native_render_dispatch_simple` (GFX_IP_GFX), both routing through
  `native_cs_submit_4chunk(..., ip_type, ...)`
  (`src/backend_native_amdgpu.cyr:733`).
- **Ephemeral per-dispatch sync.** native creates a syncobj, submits with
  `SYNCOBJ_OUT`, waits to a `CLOCK_MONOTONIC + 15s` deadline, then
  destroys it — per dispatch (`src/backend_native.cyr` compute/render
  slots). There is no persistent, cross-dispatch sync object today.
- **`AMDGPU_HW_IP_DMA` (=2) is not wired.** Transfers currently ride the
  GFX ring; a true TRANSFER queue needs an SDMA PM4 path
  (`src/backend_native_pm4.cyr` has no SDMA builders).
- **Render graph is single-queue.** The v2.5 graph
  (`src/render_graph.cyr`) is built around single-encoder/single-submit
  (roadmap notes this); it has no notion of per-node queue affinity or
  cross-queue edges.
- **uapi note.** `drm_amdgpu_cs` carries no `queue_id` field; `ip_type`
  selects the ring (stable uapi since ~5.10). Timeline syncobjs require
  kernel ≥ 5.2 (Cezanne's 6.x has them). The design rides `ip_type` +
  timeline syncobjs, not a hypothetical queue-id extension.

## Public API (identical on both backends — ADR 005)

```cyrius
# Queue kinds.
QUEUE_GRAPHICS = 0;  QUEUE_COMPUTE = 1;  QUEUE_TRANSFER = 2;

# Acquire a logical queue handle. On wgpu all kinds alias the one
# underlying queue; on native each maps to a hardware ring.
fn gpu_queue_get(ctx, kind): i64               # -> queue_ptr

# Cross-queue dependency: work submitted to `waiter` after this call will
# not start until work submitted to `signaler` before this call completes.
# wgpu: enforced by submit ordering on the single queue. native: a
# timeline-syncobj signal on `signaler`'s ring + wait on `waiter`'s ring.
fn gpu_queue_barrier(ctx, signaler, waiter): i64   # -> 0|err

# Block the CPU until all work on `queue` completes.
fn gpu_queue_wait_idle(ctx, queue): i64            # -> 0|err
```

Existing `gpu_compute_dispatch` / `gpu_render_pass_*` submit to the
"default" queue (GRAPHICS for render, COMPUTE for compute) to preserve
v3.0 behavior. A queue-targeted variant routes work to a chosen queue via
the **ctx-stash pattern** (a "current queue" stash on the ctx, set before
the dispatch), *not* by adding a queue param to the dispatch slots —
`render_pass_draw` is already at the 5-arg `(ctx, pass, pipe, vc, ic)`
ceiling, and stash-on-ctx is the established precedent
(`surface_configure` stashes the card fd / surface handle at
`GpuContext+96/+104`).

## Backend interface changes

Append after the mipmap slots (3.1.0 ends at `BACKEND_SIZE = 224`). New
slots:

| Slot | Signature |
|------|-----------|
| `BACKEND_SLOT_QUEUE_GET` | `(ctx, kind) -> queue_ptr` |
| `BACKEND_SLOT_QUEUE_BARRIER` | `(ctx, signaler, waiter) -> 0\|err` |
| `BACKEND_SLOT_QUEUE_WAIT_IDLE` | `(ctx, queue) -> 0\|err` |

`BACKEND_SIZE` 224 → 248; add `BACKEND_QUEUE_SLOTS_BEGIN/END` (224/248)
and extend `backend_is_complete`. Both backends fill all three.

**Queue state placement.** A logical Queue is a small struct (kind +
backend-specific handle/ring-id + persistent timeline syncobj handle +
current timeline point). It does **not** live in `GpuContext+0..+24`
(that dual wgpu/native region is full and load-bearing). Queue objects
are allocated behind the backend (a small ctx-side queue table, like the
mipmap metadata table), keeping the 120-byte dual region untouched.

## wgpu backend impl

- `queue_get(kind)` returns a thin Queue wrapping the single
  `gpu_ctx_queue(ctx)` handle, tagged with `kind`. All kinds alias it.
- `queue_barrier(signaler, waiter)` is a no-op beyond enforcing that the
  signaler's submitted command buffers are submitted before the waiter's
  (the single queue already serializes; the barrier just pins ordering).
- `queue_wait_idle` = `wgpu_device_poll(device, wait=1)`.
- Documented limitation: no overlap; correct ordering only.

## native AMD backend impl

- `queue_get(kind)` allocates a Queue bound to a ring
  (`QUEUE_GRAPHICS→HW_IP_GFX`, `QUEUE_COMPUTE→HW_IP_COMPUTE`,
  `QUEUE_TRANSFER→HW_IP_DMA`) and creates a **persistent timeline
  syncobj** for it (replacing the ephemeral per-dispatch syncobj model on
  the queue-targeted path).
- Each submit on a queue signals its timeline to an incrementing point;
  `queue_barrier` adds a timeline `WAIT` (on the signaler's point) IN-chunk
  to the waiter's next submit and a `SIGNAL` OUT-chunk on the signaler —
  real cross-ring ordering with no CPU stall.
- `queue_wait_idle` waits the queue's timeline to its latest point.
- **TRANSFER ring** needs SDMA PM4 (copy packets) — a new
  `src/backend_native_pm4.cyr` path. If SDMA bring-up is heavy, TRANSFER
  initially falls back to the COMPUTE ring (documented; SDMA is a
  follow-up bite), so GRAPHICS+COMPUTE overlap ships first.

## The render-graph refactor (the big risk)

The v2.5 render graph assumes single-encoder/single-submit. Multi-queue
needs: per-node **queue affinity**, **cross-queue fence edges** emitted at
graph edges that cross queues, and **per-queue submit batching**. There is
no prototype. Estimate: a **2–3 week design spike + implementation**, and
it is the single largest risk in the arc.

**This is why multi-queue is 3.1.1+, not folded into 3.1.0**, and why the
punchlist keeps the door open to multi-queue **graduating to its own
minor** if the render-graph work balloons. The minimum-viable 3.1.1 is
the queue abstraction + GRAPHICS/COMPUTE overlap for *direct* dispatch
(no render-graph integration); render-graph multi-queue scheduling can be
a later bite (3.1.2) or its own design doc.

## Phasing (sub-bites)

1. Queue abstraction + 3 slots + ctx-side queue table (both backends).
2. wgpu serialized impl (single-queue-backed logical queues).
3. native persistent per-queue timeline syncobjs; queue-targeted
   dispatch via ctx-stash; GRAPHICS+COMPUTE overlap.
4. `gpu_queue_barrier` cross-ring timeline wait/signal (native) /
   ordering pin (wgpu).
5. TRANSFER ring: SDMA PM4 copy path (or documented COMPUTE fallback).
6. Render-graph multi-queue scheduling — **design spike first**, then
   per-node affinity + cross-queue edges. May split to 3.1.2 / own minor.
7. e2e: `programs/native_multiqueue_e2e.cyr` (compute+graphics overlap,
   timeline-ordered, CPU-verified result) + wgpu serialized-equivalent.

## Exit criteria (3.1.1 — direct-dispatch multi-queue)

- `gpu_queue_get` / `_barrier` / `_wait_idle` on both backends; all three
  slots filled (`backend_is_complete` = 1).
- native: GRAPHICS+COMPUTE submit to distinct rings; `queue_barrier`
  enforces a verified cross-ring ordering (a compute write consumed by a
  graphics pass produces the correct pixel on Cezanne).
- wgpu: same API, serialized; ordering correctness verified; documented
  as no-overlap.
- CPU suite: queue table, slot wiring, timeline-point accounting,
  barrier-chunk layout — each new path adds an assertion.
- Render-graph multi-queue scheduling is explicitly **scoped separately**
  (3.1.2 / own design doc) and not a 3.1.1 blocker.
- lint / fmt / vet / distlib / version-check clean; CHANGELOG `[3.1.1]`;
  audit re-run on any CS-submit / syncobj / FFI change.
