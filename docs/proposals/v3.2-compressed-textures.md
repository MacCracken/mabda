# Proposal: v3.2 Compressed Textures (BC / ETC2 / ASTC)

**Status:** Proposed (v3.2.0 design).
**Date:** 2026-06-15.
**Arc:** First feature of the v3.2.x "texture & shader breadth" arc — see
[`roadmap.md` § v3.2](../development/roadmap.md#v32--texture--shader-breadth).
The arc's fixed sequence (maintainer decision): **compressed textures
(3.2.0) → SPIR-V (3.2.1+) → f64 compute (3.2.2+)**.
**Companions (later in the arc):** `v3.2-spirv-ingestion-wgpu.md`, `v3.2-spirv-gfx9-native-lowering.md`, `v3.2-f64-compute.md`
(to be written when those bites open).

## Summary

Add block-compressed 2D textures — BC1–BC7 (desktop/AMD), the ETC2 set,
and ASTC block variants (both mobile) — to mabda's public texture API.
The work is four concrete pieces:

1. **Format enums + WGPUTextureFormat mapping** — a `MABDA_TEXFMT_*`
   space covering the BC/ETC2/ASTC families, each mapped to its v29
   `WGPUTextureFormat` value (verified against the in-tree
   `deps/wgpu-native/include/webgpu/webgpu.h`), plus per-format block
   geometry (block width/height in texels, bytes-per-block).
2. **Block-based validation + size math** — the upload byte count is
   `ceil(w/bw) * ceil(h/bh) * blockBytes`, not `w*h*bpp`; dimension and
   overflow guards are block-aware. Pure Cyrius math, no FFI, fully
   CPU-testable.
3. **A format-parameterized create + upload path** — texture create and
   write take a format, the upload threads `bytesPerRow` in **blocks**
   (rows-per-image in block-rows), and there is **no per-texel mmap
   write** — compressed data is opaque blocks, copied verbatim.
4. **Capability gating** — `gpu_caps_*` exposes which families the active
   adapter/backend supports, and create rejects an unsupported format up
   front (`GPU_ERR_TEXTURE` / a new `GPU_ERR_FORMAT_UNSUPPORTED`).

The public API is the same shape on both backends (ADR 005). The
**backends differ in what they can do with the bytes** (ADR 006
fail-loud), and that difference — driven by a hard hardware constraint
on the native path — is reckoned with up front below.

## Hard truth up front: native AMD has no compressed-texture sampling path in 3.2.0

This is the constraint that shapes the whole design, exactly as
"wgpu has one queue" shaped multi-queue.

**wgpu** has first-class compressed-texture support. The formats are real
`WGPUTextureFormat` enum values (`webgpu.h` v29 lines 1075–1126);
`wgpuQueueWriteTexture` already accepts block-compressed data when
`bytesPerRow` is given in blocks; the adapter advertises
`WGPUFeatureName_TextureCompressionBC/ETC2/ASTC` (lines 645–648) and the
TA (texture-addressing) unit decodes blocks at sample time. On wgpu,
compressed textures **create, upload, bind, and sample** — complete.

**Native AMD** cannot sample a compressed texture in 3.2.0, for a
structural reason, not a missing-feature reason:

- Native textures are **LINEAR GTT BOs** with **no tiling, no DCC, no
  swizzle** (`backend_native.cyr` header; `COLOR_SW_MODE = 0` "linear
  surface, no swizzle", `DCC_ENABLE = 0` in
  `backend_native_pm4.cyr:988,1110`). The whole native texture story is
  "the BO's bytes *are* the pixels, write/read collapse to `memcpy`"
  (`_backend_native_texture_write/_read`).
- There is **no image-descriptor (T#/V#) infrastructure and no
  `image_sample` path anywhere in the native backend.** The v3.1 mipmap
  PIVOT *deleted* the descriptor-table design precisely because linear
  layout let the downsample shader use flat `global_load`/`global_store`
  (`v3.1-mipmap-generation.md` § PIVOT; `native_texture_level_va`). The
  native render path samples nothing — the FS hardcodes solid red
  (`native_gfx9_shader_solid_red`).
- GFX9 hardware decode of BC/ETC2/ASTC requires a **T# image descriptor
  with the compressed format field set, a tiled surface, and the TA unit
  in the shader's `image_sample`/`image_load` path.** That is the entire
  T#/V# + tiling + sampler infrastructure the project has deliberately
  avoided shipping (it's the ~200-line, ABI-risky, 2–4-HW-iteration body
  of work the mipmap PIVOT was relieved to skip). Standing it up is a
  multi-bite native sub-project on its own — out of scope for a 3.2.0
  that is fundamentally about *format/validation/upload breadth*, not a
  new native sampling engine.

**Resolution (the v3.0/v3.1 pattern):** in 3.2.0 the public compressed
API is **identical on both backends and complete on both for what it
promises** — but what it promises on native is **storage + readback, not
sampling**:

- **wgpu**: full — create, upload, **bind + sample** a compressed texture.
- **native AMD**: create a compressed BO (linear, sized in blocks),
  `gpu_texture_write` the opaque block data in, `gpu_texture_read` it back
  byte-identical. **Binding a compressed texture for sampling returns
  `GPU_ERR_NOT_IMPLEMENTED` (fail-loud, ADR 006)** — the GFX9 sampler
  decode path is explicitly deferred. This is a *complete* implementation
  of the storage contract, not a stub: a native consumer can hold,
  transfer, and round-trip compressed assets (the asset-pipeline / staging
  use case kiran and aethersafta actually have today), and gets a loud,
  documented error the moment it tries to sample one — never a silent
  wrong pixel.

This is the same shape as wgpu's serialized multi-queue (correct +
complete for what it claims, the backend-specific capability is the
documented delta) and as wgpu's mipmap `generate` returning
`NOT_IMPLEMENTED` until wgpu compute lands. Native compressed *sampling*
lands in **Phase TS (3.2.2–3.2.3), this same arc** — the GFX9
T#/tiling/sampler path designed in
[`v3.2-native-compressed-sampling.md`](v3.2-native-compressed-sampling.md).
It is split out of 3.2.0 only so this minor stays a tight
format/validation/upload slice — **not deferred out of v3.2**.

## Current state (what exists today)

- **Texture formats are a tiny hardcoded set.** `wgpu_types.cyr`
  enumerates only RGBA8/BGRA8 (±srgb) + the depth formats; every
  create path hardcodes `WGPU_TEXTURE_FORMAT_RGBA8_UNORM`
  (`texture.cyr`, `backend_wgpu.cyr`, `backend_native.cyr`). There is no
  format parameter on `gpu_texture_create_2d_rgba8` or its slot.
- **Size math is `w*h*4` everywhere.** `texture_upload_rgba8` computes
  `bytes_per_row = width*4`, `data_size = width*height*4`;
  `_backend_wgpu_texture_write` and `_backend_native_texture_write` both
  assert `n == width*height*4` (`backend_wgpu.cyr:326`,
  `backend_native.cyr` `n != size`). None of this is block-aware.
- **The upload FFI is already block-capable.** `wgpu_queue_write_texture`
  + `wgpu_texel_copy_buffer_layout(offset, bytesPerRow, rowsPerImage)`
  (`wgpu_descriptors.cyr:518`) is exactly the WebGPU block-copy shape —
  for compressed formats `bytesPerRow` is "bytes per *block row*" and
  `rowsPerImage` is "block rows". No new FFI is needed for the wgpu
  upload; only the *values* fed in change.
- **Feature query FFI exists and is unused for this.**
  `wgpu_device_has_feature(device, feature)` and
  `wgpu_adapter_has_feature(adapter, feature)` are already wired
  (`wgpu_ffi.cyr:216,220`). The `WGPUFeatureName_TextureCompression*`
  values (`webgpu.h:645-648`) feed straight into them — that is the
  capability gate, no new FFI slot required.
- **Capabilities struct has no compression fields.** `GpuCapabilities`
  (`capabilities.cyr`, 120 bytes, +0..+112) has no
  texture-compression bits. Appending them is the same append-after-end
  move the backend slots use.
- **Native texture create takes the VA from the sub-allocator and
  va-maps a linear BO** (`native_texture_create_2d_rgba8`,
  `native_ctx_alloc_texture_va`). A compressed BO is the same allocation
  with a **block-computed size** instead of `w*h*4` — the linear-BO
  machinery is unchanged.
- **Native max-dim cap and overflow guard are RGBA8-shaped.**
  `MABDA_MAX_TEXTURE_DIM_2D = 8192`, and the audit note on
  `gpu_texture_create_2d_rgba8` reasons "8192*8192*4 = 268 MiB, no
  overflow" (`texture.cyr:244`). The block-size multiply needs its own
  overflow reasoning (compressed is *smaller* per texel, so the bound
  holds, but the math must be re-derived, not assumed).

## Format model

A compact, table-driven format descriptor — the single source of truth
for every per-format constant — so validation, size math, the wgpu
mapping, and capability gating all read from one place.

```cyrius
# mabda compressed-format ids (stable, backend-independent). Grouped by
# family; values are mabda-internal, NOT the wgpu enum (mapped below).
MABDA_TEXFMT_RGBA8_UNORM      = 0;   # the existing uncompressed default
# BC family (desktop / AMD) — 4x4 blocks
MABDA_TEXFMT_BC1_RGBA_UNORM   = 10;  # 8  bytes/block (DXT1)
MABDA_TEXFMT_BC3_RGBA_UNORM   = 11;  # 16 bytes/block (DXT5)
MABDA_TEXFMT_BC4_R_UNORM      = 12;  # 8  bytes/block
MABDA_TEXFMT_BC5_RG_UNORM     = 13;  # 16 bytes/block
MABDA_TEXFMT_BC6H_RGB_UFLOAT  = 14;  # 16 bytes/block (HDR)
MABDA_TEXFMT_BC7_RGBA_UNORM   = 15;  # 16 bytes/block
# ETC2 family (mobile) — 4x4 blocks
MABDA_TEXFMT_ETC2_RGB8_UNORM  = 20;  # 8  bytes/block
MABDA_TEXFMT_ETC2_RGBA8_UNORM = 21;  # 16 bytes/block
# ASTC family (mobile) — variable block, always 16 bytes/block
MABDA_TEXFMT_ASTC_4X4_UNORM   = 30;  # 4x4  block, 16 bytes/block
MABDA_TEXFMT_ASTC_6X6_UNORM   = 31;  # 6x6  block, 16 bytes/block
MABDA_TEXFMT_ASTC_8X8_UNORM   = 32;  # 8x8  block, 16 bytes/block
# (sRGB variants of each get the same block geometry; add as a parallel
#  id range — e.g. +1 per format — once a consumer needs sRGB sampling.)
```

Three pure-Cyrius accessors driven by the descriptor table — every new
format is one table row:

```cyrius
fn mabda_texfmt_block_width(fmt): i64     # 1 (uncompressed) | 4 | 6 | 8 ...
fn mabda_texfmt_block_height(fmt): i64    # 1 | 4 | 6 | 8 ...
fn mabda_texfmt_block_bytes(fmt): i64     # 4 (RGBA8) | 8 | 16
fn mabda_texfmt_is_compressed(fmt): i64   # 0 | 1
```

### WGPUTextureFormat mapping (v29, verified in tree)

Every value below is read directly from
`deps/wgpu-native/include/webgpu/webgpu.h` (v29.0.0.0). These extend the
`WGPUTextureFormat` enum in `wgpu_types.cyr` (which today stops at the
depth formats); the comment block cites the header line.

| mabda id | WGPUTextureFormat | v29 value | block | bytes |
|---|---|---|---|---|
| `BC1_RGBA_UNORM` | `BC1RGBAUnorm` | `0x32` | 4×4 | 8 |
| `BC3_RGBA_UNORM` | `BC3RGBAUnorm` | `0x36` | 4×4 | 16 |
| `BC4_R_UNORM` | `BC4RUnorm` | `0x38` | 4×4 | 8 |
| `BC5_RG_UNORM` | `BC5RGUnorm` | `0x3A` | 4×4 | 16 |
| `BC6H_RGB_UFLOAT` | `BC6HRGBUfloat` | `0x3C` | 4×4 | 16 |
| `BC7_RGBA_UNORM` | `BC7RGBAUnorm` | `0x3E` | 4×4 | 16 |
| `ETC2_RGB8_UNORM` | `ETC2RGB8Unorm` | `0x40` | 4×4 | 8 |
| `ETC2_RGBA8_UNORM` | `ETC2RGBA8Unorm` | `0x44` | 4×4 | 16 |
| `ASTC_4X4_UNORM` | `ASTC4x4Unorm` | `0x4A` | 4×4 | 16 |
| `ASTC_6X6_UNORM` | `ASTC6x6Unorm` | `0x52` | 6×6 | 16 |
| `ASTC_8X8_UNORM` | `ASTC8x8Unorm` | `0x58` | 8×8 | 16 |

`fn mabda_texfmt_to_wgpu(fmt): i64` returns the v29 value (or `0` for an
unknown id, which create rejects). A CPU test pins every row against
these header constants — the audit checklist's "FFI descriptor offset
review" applied to enum values.

## Block-based validation + size math (pure, no FFI)

```cyrius
# Blocks needed to cover `dim` texels at block size `b`: ceil(dim/b).
fn mabda_texfmt_blocks_for_dim(dim, b): i64 { return (dim + b - 1) / b; }

# Total compressed byte size: blocks_x * blocks_y * block_bytes.
fn mabda_texfmt_data_size(fmt, width, height): i64
```

Validation rules (all CPU-testable; every rule adds an assertion):

- **Dimensions**: positive, `<= MABDA_MAX_TEXTURE_DIM_2D` (reuse the
  existing `validate_dimensions`). WebGPU does **not** require compressed
  texture dimensions to be block-multiples at the texture level (the last
  partial block is allowed); but a **`writeTexture` of a full mip level**
  copies whole block rows. We follow WebGPU: allow non-multiple
  dimensions, size the copy in `ceil` blocks.
- **Overflow guard, re-derived for compressed.** Worst case is ASTC4×4 /
  BC3/BC7 at 16 bytes/block: `ceil(8192/4)*ceil(8192/4)*16 =
  2048*2048*16 = 64 MiB` — comfortably inside i64 and *smaller* than the
  RGBA8 268 MiB bound. The guard is still written explicitly (per the
  security checklist's "any `a*b` on dimensions gets an overflow guard"),
  not assumed from the RGBA8 note.
- **Upload byte count must equal `mabda_texfmt_data_size(fmt, w, h)`** —
  the compressed analog of the existing `n == w*h*4` check in both write
  slots.

## Upload path (block layout, no per-texel write)

The WebGPU `writeTexture` block contract:

- `bytesPerRow` = bytes per **block row** =
  `blocks_x * block_bytes` (must satisfy the 256-byte
  `COPY_BYTES_PER_ROW_ALIGNMENT` for `copyB2T`, but `queueWriteTexture`
  is looser — documented per-format).
- `rowsPerImage` = number of **block rows** = `blocks_y`.
- the `WGPUExtent3D` write size stays in **texels** (`w, h, 1`); wgpu
  derives blocks internally from the format.

So `wgpu_texel_copy_buffer_layout(0, bytesPerRow, rowsPerImage)` —
already in tree — is fed block-derived values instead of `w*4, h`. The
extent is still `wgpu_extent_3d(w, h, 1)`. **No new descriptor builder,
no per-texel loop** — compressed data is opaque; the upload is one
`memcpy`-shaped FFI copy of `data_size` bytes.

**Native upload** is even simpler and is the same `memcpy` the existing
linear path already does — the BO is sized to `data_size`, the bytes are
copied verbatim, `read` returns them byte-identical. The compressed BO is
just a linear blob to native; nothing decodes it (that's the sampling gap
above).

## How it threads the Backend slots

**Decision: parameterize the existing texture slots with a format, do
NOT add a parallel "compressed_*" slot family.** A compressed texture is
a texture; the create/write/read/release lifecycle is identical, only the
size math and the (wgpu) format field differ. A separate slot family
would duplicate four slots and the dispatcher logic for no behavioral
gain, and it would fight the "same call-site shape both backends" design.

The minimal slot change is **one new create slot** carrying a format
(the existing `texture_create_2d_rgba8` slot keeps its RGBA8 ABI for
back-compat, exactly as the single-level create survived the mipped
create being added in v3.1):

```
BACKEND_SLOT_TEXTURE_CREATE_2D_FMT   (ctx, w, h, fmt) -> tex_ptr
```

`write` / `read` / `release` are **unchanged** — they already take
`(ctx, tex, ptr, n)` and validate `n` against the BO size, which the
create slot stored. The native `tex` struct already carries `size`
(`NATIVE_TEX_FIELD_SIZE`); for a compressed BO it's `data_size`, and the
existing `n != size` guard works as-is. The wgpu `tex` struct's
`width|height` fields are kept; the write slot derives blocks from a
**format stashed in the tex struct** (one new u32 field in the 32-byte
wgpu tex struct's currently-unused tail, or — cleaner — bump the format
into the spare slot at +16 which is the unused `sampler` field on the
write/read path).

For **sampling on native**, the bind path (the consumer's bind-group /
texture-view creation) is where `GPU_ERR_NOT_IMPLEMENTED` surfaces. v3.2.0
ships no native compressed *view/sample* slot — there is nothing to call,
so there is no stub slot (ADR 006 honored: the slot exists only when both
backends do it for real). The public `gpu_texture_create_2d` accepts a
compressed format on native; a future native-sampling bite adds the
view/sample path when the T#/tiling sub-project lands.

### Slot layout bookkeeping

Append `BACKEND_SLOT_TEXTURE_CREATE_2D_FMT` after the queue slots
(3.1.1 ended at `BACKEND_SIZE = 248`; offsets 0..240 are load-bearing,
append-after-KIND policy holds):

| Slot | Offset | Signature |
|------|--------|-----------|
| `BACKEND_SLOT_TEXTURE_CREATE_2D_FMT` | 248 | `(ctx, w, h, fmt) -> tex_ptr` |

`BACKEND_SIZE` 248 → 256. Add a `BACKEND_TEXFMT_SLOTS_BEGIN/END`
(248/256) range marker pair and extend `backend_is_complete`'s walk over
it **once both backends fill the slot** (the M.2/Q.1 deferral discipline:
layout in tree first, completeness walk when there's a real impl on both
sides — and both *create* impls are real in 3.2.0, so the walk activates
in this minor). 4 args is within the fncall ceiling.

## Public API (identical on both backends — ADR 005)

```cyrius
# Create a 2D texture of an explicit format. fmt == MABDA_TEXFMT_RGBA8_UNORM
# is the existing uncompressed behavior (gpu_texture_create_2d_rgba8
# forwards to this). Compressed fmts allocate a block-sized BO. Returns an
# opaque backend tex_ptr, or 0 on invalid dims / unsupported format (see
# gpu_caps gating below). # @public
fn gpu_texture_create_2d(ctx, width, height, fmt): i64

# write / read are the existing dispatchers, unchanged — they validate n
# against the BO's stored size, which is block-derived for compressed.
fn gpu_texture_write(ctx, tex, src, n): i64    # @public (existing)
fn gpu_texture_read(ctx, tex, dst, n): i64     # @public (existing)
fn gpu_texture_release(ctx, tex): i64          # @public (existing)
```

`gpu_texture_create_2d_rgba8(ctx, w, h)` stays as the convenience entry
(forwards `fmt = MABDA_TEXFMT_RGBA8_UNORM`). All existing validation
guards (positivity, `MABDA_MAX_TEXTURE_DIM_2D`, overflow) apply, plus the
format-supported check.

## Capability gating

Extend `GpuCapabilities` with a compression-support bitset (append after
+112, the same move every prior cap addition used):

```cyrius
# +120: texture_compression  (i64 bitset: bit0=BC, bit1=ETC2, bit2=ASTC)
fn gpu_caps_texture_compression(c): i64
fn gpu_caps_supports_format(c, fmt): i64    # maps fmt -> family bit
```

- **wgpu**: populated from `wgpu_adapter_has_feature(adapter,
  WGPUFeatureName_TextureCompressionBC/ETC2/ASTC)` at context/caps build.
  On a desktop AMD adapter, BC is present, ETC2/ASTC usually absent —
  so the gate correctly rejects an ASTC create on that adapter.
- **native AMD**: the *storage* contract supports any format (it's a
  linear blob), but the cap bitset reflects what can be **sampled** —
  which in 3.2.0 is **nothing compressed** (sampling deferred). So
  `gpu_caps_supports_format` for a compressed fmt returns 0 on native,
  and `gpu_texture_create_2d` of a compressed fmt on native succeeds for
  storage but the (future) sample/bind path is what's gated. The
  distinction "create-for-storage succeeds vs sample-supported" is
  documented on the cap accessor.

`gpu_texture_create_2d` consults the cap gate and returns 0 (with a
`GPU_ERR_FORMAT_UNSUPPORTED` available via the Result-returning variant)
when the active backend/adapter can't honor the requested use. A new
`GPU_ERR_FORMAT_UNSUPPORTED` error code (next free value after
`GPU_ERR_NOT_IMPLEMENTED = 18`) distinguishes "this adapter lacks the
feature" from "not implemented on this backend."

## Why not ship native compressed sampling in 3.2.0

Stated plainly so it isn't relitigated mid-arc: GFX9 sampling of
BC/ETC2/ASTC needs (a) a **tiled** surface layout (the TA unit's block
addressing assumes a non-linear tile mode), (b) a **T# image descriptor**
encoding the compressed format + tiling + extent, and (c) an
**`image_sample`/`image_load` shader path** with a sampler (S#). None of
the three exist — the project deliberately runs linear/no-DCC/no-T#, and
the v3.1 mipmap PIVOT *removed* the only descriptor-table design that was
ever drafted. Building all three is a native sub-project comparable in
size to the original render bring-up — so it gets its own dedicated
**Phase TS (3.2.2–3.2.3, this arc)** rather than being bolted onto this
format-breadth minor. Shipping native *storage + readback* now is the
honest, complete, useful slice (asset staging/transfer round-trips work
today); native *sampling* follows in Phase TS, with a real prerequisite
(the T#/tiling/sampler path).

## Phasing

See **Phase T** in the punchlist. The shape: format table + mapping →
block math + validation → capability gating → create slot + dispatcher →
wgpu upload/sample wiring → native storage path → e2e on both backends.

## Exit criteria (3.2.0)

- `gpu_texture_create_2d(ctx, w, h, fmt)` on both backends; the
  `BACKEND_SLOT_TEXTURE_CREATE_2D_FMT` slot filled on both
  (`backend_is_complete` walk extended over 248..256, active this minor).
- Format table, block math (`blocks_for_dim`, `data_size`), v29 enum
  mapping, validation, and capability gating each carry CPU assertions —
  every new path adds one (house rule). Worst-case overflow bound
  re-derived and asserted.
- **wgpu**: `programs/compressed_texture_e2e.cyr` creates a BC1 (and a BC7)
  texture, uploads block data, **binds + samples** it in a render pass,
  CPU-reads the rendered RT, and verifies decoded pixels against a CPU
  reference decode of the same blocks (HW-gated; AMD desktop / any
  BC-capable adapter).
- **native AMD**: `programs/native_compressed_store_e2e.cyr` creates a BC1
  texture (linear, block-sized BO), `gpu_texture_write`s known block
  bytes, `gpu_texture_read`s them back **byte-identical** on Cezanne;
  asserts that a sample/bind attempt returns `GPU_ERR_NOT_IMPLEMENTED`
  (fail-loud verified, not silent).
- Capability gating verified: requesting an unsupported format
  (e.g. ASTC on a BC-only adapter) returns 0 / `GPU_ERR_FORMAT_UNSUPPORTED`
  rather than reaching the FFI.
- lint / fmt / vet / distlib / version-check clean; `dist/mabda.cyr`
  regenerated; CHANGELOG `[3.2.0]` section; roadmap v3.2 entry updated to
  the shipped shape (wgpu full sampling; native storage-only this minor;
  native sampling = Phase TS, this arc). Audit re-run on the texture-size /
  `writeTexture` / enum-mapping deltas (P(-1) work-loop step 5).

## Risks

- **Native sampling expectation mismatch.** A consumer may assume
  "create a compressed texture on native" means it can be sampled.
  Mitigation: `gpu_caps_supports_format` returns 0 for compressed on
  native, the bind/sample path fails loud with `GPU_ERR_NOT_IMPLEMENTED`,
  and the limitation is in the CHANGELOG, the proposal, and the cap
  accessor's doc comment. (Same posture as wgpu mipmap-generate
  `NOT_IMPLEMENTED`.)
- **wgpu adapter feature variance.** ETC2/ASTC are usually absent on
  desktop AMD; tests must gate on `has_feature` so CI/dev boxes don't
  fail on a missing optional feature. The e2e program picks BC (present
  on the AMD dev box) for the sampling check; ETC2/ASTC sampling is
  exercised only where the adapter advertises it.
- **`bytesPerRow` alignment.** `queueWriteTexture` is lenient but
  `copyBufferToTexture` requires 256-byte block-row alignment. The 3.2.0
  upload uses `queueWriteTexture` (the existing texture-write path), so
  this is documented but not yet a blocker; the readback path on wgpu
  (copy-texture-to-buffer) for the sample-verify program must pad block
  rows to 256 — call out in the e2e program.
- **Format-table drift vs webgpu.h.** Enum values are pinned by CPU test
  against the in-tree header; a wgpu-native bump that renumbers formats is
  caught by that test (the audit "enum value review" gate).
