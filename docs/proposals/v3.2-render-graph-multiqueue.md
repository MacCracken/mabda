# Proposal: v3.2 Render-Graph Multi-Queue Scheduling

**Status:** Proposed (v3.2.x design).
**Date:** 2026-06-15.
**Arc:** Folded into the v3.2.x arc as **Phase R** — the v3.1.2 deferral
(was "Phase Q.7") pulled forward. See
[`roadmap.md` § v3.2](../development/roadmap.md#v32--texture--shader-breadth)
and the punchlist's **Phase R**.
**Predecessor:** [`v3.1-multiqueue.md`](v3.1-multiqueue.md) — which shipped
the queue primitives this proposal *composes* and explicitly scoped
render-graph multi-queue as "the big risk" deferred out of 3.1.1.
**Consumers:** rasa (compute+present overlap), bijli (large transfer +
compute), aethersafta (compositor: clear/compute + present passes).

## Summary

The v2.5 render graph (`src/render_graph.cyr`) topo-sorts a DAG of
compute / render / copy nodes and executes them **single-submit**: one
wgpu command encoder, every node encoded sequentially, one
`wgpu_queue_submit_one` at the end. That is correct but leaves the native
backend's independent hardware rings idle — a compute node that feeds a
render node runs on the same ring, in series, even though the v3.1.1 queue
abstraction can run GFX and COMPUTE concurrently with a no-CPU-stall
cross-ring fence.

This proposal makes the render graph **multi-queue aware** on native and
**serialized-equivalent** on wgpu:

1. **Per-node queue affinity** — a node declares `GRAPHICS` / `COMPUTE` /
   `TRANSFER`; the scheduler honors it (native routes to the matching HW
   ring; wgpu folds all onto the one `WGPUQueue`).
2. **Cross-queue dependency edges lowered to `gpu_queue_barrier`** — the
   existing toposort already infers writer→reader edges from
   reads/writes declarations. An edge whose endpoints sit on *different*
   queues becomes an in-CS `SYNCOBJ_TIMELINE_WAIT` (the v3.1.1 Q.4
   primitive), not a CPU stall.
3. **Per-queue submit batching** — instead of one encoder for the whole
   graph, the scheduler groups each queue's nodes and submits them as a
   per-queue stream, so the GFX and COMPUTE rings overlap under the
   kernel scheduler.
4. **A real scheduler** that topologically orders nodes *per queue* and
   inserts the cross-queue fence edges at exactly the points where the
   DAG crosses a queue boundary.

The public builder API (`rg_add_compute` / `rg_add_render` /
`rg_add_copy_*` / `rg_node_reads` / `rg_node_writes` / `rg_build` /
`rg_execute`) stays byte-compatible. One new builder call —
`rg_node_queue(g, node_id, kind)` — declares affinity; omitting it keeps
the v2.5 default (the legacy single-queue behavior, unchanged).

## Hard truth up front: this is a real refactor of the single-submit executor, and wgpu can never overlap

Two structural constraints shape the whole design, the same way "wgpu has
one queue" shaped 3.1.1 and "native has no compressed sampling" shaped
3.2.0.

**(1) The v2.5 executor is single-encoder/single-submit by construction.**
`rg_execute` (`render_graph.cyr:666`) builds *one*
`wgpu_device_create_command_encoder`, walks the sorted nodes encoding each
into it, finishes *one* command buffer, and calls `wgpu_queue_submit_one`
*once* (`render_graph.cyr:680,707,709`). There is no per-queue grouping,
no fence insertion, no notion of which ring a node runs on. Multi-queue is
not a flag flip — the executor is rewritten into a **per-queue batched
submitter with a fence-edge pass between batches**. That rewrite is the
body of work; everything else (affinity field, edge classification) feeds
it. This is honestly a medium refactor of the one module, not a
one-liner, and it is staged across three minors so each step lands green.

**(2) wgpu physically cannot overlap — and that is fine.** WebGPU exposes
exactly one device queue (`v3.1-multiqueue.md` § "Hard truth"; confirmed
against `src/wgpu_ffi.cyr` — no `queue_create`). On wgpu, *all* queue
affinities fold onto the single `WGPUQueue`, and the multi-queue scheduler
degrades to **exactly today's behavior**: one encoder, submit in the
topo-sorted order the cross-queue edges imply. The declared ordering is
honored; there is no overlap. This is **correct and complete** (ADR 006
no-fail-silent, ADR 005 same-API), not a stub — the wgpu render graph is
byte-for-byte the v2.5 path, re-expressed through the new scheduler so the
*output command stream is identical*. Consumers that need the overlap are
on the native path anyway (and native is the sole AMD path at v4.0).

Native AMD, by contrast, gets the real win: GFX and COMPUTE nodes submit
to distinct rings (`AMDGPU_HW_IP_GFX` / `_COMPUTE`), cross-queue edges
become in-CS timeline waits, and the kernel scheduler runs the rings
concurrently — exactly the 3-ring overlap
`programs/native_multiqueue_e2e.cyr` already proves for direct dispatch.

## Current state (what exists today)

- **Render graph is single-submit.** `rg_execute(g, device, queue)`
  (`render_graph.cyr:666`) — one encoder, sequential `_rg_encode_*` per
  node, one submit. Node struct (72 B, `render_graph.cyr:36`) has **no
  queue field**, but carries a **`+56: reserved (16)`** tail — room for a
  queue-affinity field and a scheduler scratch field **without growing
  the struct** (the same append-into-reserved move the queue table used).
- **The toposort already builds the edges we need.** `rg_build`
  (`render_graph.cyr:259`) runs Kahn's algorithm over writer→reader edges
  inferred from `reads`/`writes` declarations and stamps each node's
  `sort_idx` (+48). The cross-queue edge set is a *subset* of these edges
  — exactly the ones whose writer and reader sit on different queues. No
  new dependency model is needed; the classification is a post-sort scan.
- **The queue primitives are shipped and HW-verified (3.1.1).**
  `src/queue.cyr`: `gpu_queue_get` / `_barrier` / `_wait_idle`,
  `queue_set_pending_wait` / `queue_bump_point` / `queue_point`, the
  ctx-side queue table (`CTX_OFF_QUEUE_*`), and the "current queue" stash
  (`gpu_ctx_set_current_queue`) that routes a dispatch onto a chosen ring.
- **Native has a queue-targeted *async* dispatch path — for compute.**
  `native_compute_dispatch_cached_timeline` (`backend_native.cyr:134`)
  submits on a queue's ring via `native_cs_submit_timeline`, signals the
  queue's persistent timeline, consumes a pending cross-ring wait as an
  in-CS `TIMELINE_WAIT`, and does **not** block. `gpu_compute_dispatch`
  already routes through it when a current queue is stashed
  (`backend_native.cyr:508`).
- **Native render dispatch is still synchronous — the gap.**
  `_backend_native_render_pass_draw` (`backend_native.cyr:869`) composes
  the GFX PM4 and calls `native_render_dispatch_simple`
  (`backend_native.cyr:247`), which creates an **ephemeral** syncobj,
  submits via `native_cs_submit_4chunk`, **waits 15 s**, and destroys the
  syncobj. There is no timeline/async render variant. A render *node* on a
  GRAPHICS queue can't participate in cross-ring overlap until render gets
  the same timeline treatment compute already has.
- **`native_cs_submit_timeline` already supports the GFX ring.** It takes
  `ip_type` as a parameter (`backend_native_amdgpu.cyr:900`) — passing
  `AMDGPU_HW_IP_GFX` is valid — and its `WAIT_FOR_SUBMIT` flag comment
  *explicitly* anticipates "future render-graph cross-queue scheduling"
  (`backend_native_amdgpu.cyr:940`). The submit machinery is ready; what's
  missing is a render-side caller analogous to the compute one.
- **No Backend slots are needed.** Multi-queue scheduling composes the
  *existing* queue slots (`BACKEND_SLOT_QUEUE_GET/_BARRIER/_WAIT_IDLE`,
  +224/+232/+240) and dispatch slots. `BACKEND_SIZE` stays **256** (Phase
  T's `BACKEND_SLOT_TEXTURE_CREATE_2D_FMT` at +248 is the last slot). The
  one *new* native primitive is a render-timeline dispatch fn — an
  internal `backend_native.cyr` function, **not** a Backend slot, exactly
  as `native_compute_dispatch_cached_timeline` is internal.

## Data model changes (render_graph.cyr, append-only)

The Node struct's `+56: reserved (16)` tail absorbs both new fields — **no
struct growth**, matching the header's reserved budget:

```
# Node (72 bytes) — reserved tail now used:
#   +56: queue_kind  (i64) — QUEUE_KIND_* affinity; default
#                            QUEUE_KIND_GRAPHICS for render/copy nodes,
#                            QUEUE_KIND_COMPUTE for compute nodes (matches
#                            the v3.0 "default queue per op kind" rule).
#   +64: batch_idx   (i64) — scheduler scratch: which per-queue batch this
#                            node lands in (-1 before rg_schedule).
```

Wait — the header lists Node as 72 bytes ending at +56 (16 reserved). +64
exceeds 72. **Correction baked into the bite plan:** R.1 grows Node from
72 → 80 bytes (append-only: `queue_kind` at +56 reusing 8 of the reserved
16, `batch_idx` at +64 as the new 8), and updates the header comment's
byte count + every `alloc(72)` / `memset(_, _, 72)` in `_rg_node_new`
(`render_graph.cyr:743`). This is the standard append-after-end growth;
the existing fields keep their offsets, so all current tests pass
unchanged. (Stating the off-by-one here rather than papering over it — the
reserved tail covers `queue_kind` for free; `batch_idx` is the one new
word.)

New builder call (public, additive):

```cyrius
# Declare the queue a node runs on. kind ∈ {QUEUE_KIND_GRAPHICS,
# _COMPUTE, _TRANSFER}. Omitting the call keeps the per-kind default
# (compute→COMPUTE, render/copy→GRAPHICS), which reproduces v2.5 ordering.
# Must be called before rg_build. # @public
fn rg_node_queue(g, node_id, kind): i64
```

A per-graph scheduler-output table, allocated at `rg_schedule` time:

```
# RenderGraph (40 → 48 bytes): append a schedule ptr at +40 (the label
# moves? No — label stays at +32; the schedule ptr is the new +40 word,
# growing the struct 40→48, append-only).
#   +40: schedule (ptr, 8) — a Schedule* (per-queue batch lists +
#                            cross-queue fence-edge list), 0 before
#                            rg_schedule.
```

## The scheduler (rg_schedule — the new pass between build and execute)

`rg_build` keeps doing toposort + transient allocation. A **new
`rg_schedule(g)` pass** runs after build and produces a `Schedule`:

1. **Assign batches per queue.** Walk nodes in `sort_idx` order; bucket
   each into its `queue_kind`'s batch list, preserving sorted order within
   a queue. Result: up to three ordered node lists (GRAPHICS / COMPUTE /
   TRANSFER), each internally in dependency order.

2. **Classify cross-queue edges.** Re-scan the inferred writer→reader
   edges (same logic `rg_build` already runs at `render_graph.cyr:282`).
   For each edge `(w, r)`: if `queue_kind(w) == queue_kind(r)` it is an
   *intra-queue* edge — already satisfied by submit order within the
   batch. If they differ, record a **fence edge** `(producer_queue,
   producer_node, consumer_queue, consumer_node)` in the Schedule's
   fence-edge list.

3. **Determine submit order across queues** so every fence edge's
   producer batch is submitted (and its timeline point reserved) before
   the consumer batch records its in-CS wait. Because the per-node
   `sort_idx` is a global topological order, submitting **batches in
   ascending min-sort_idx, and within a batch in sort_idx order**, plus
   recording each cross-queue edge as a pending-wait on the consumer
   queue *before* the consumer's submit, is sufficient — the consumer's
   `TIMELINE_WAIT` references a point the producer's submit has already
   reserved via `queue_bump_point`. (This is the exact pattern the
   direct-dispatch e2e uses: barrier records the pending wait, the next
   queue-targeted submit folds it in.)

CPU-testable in full: batch assignment, edge classification
(intra vs cross), and the submit-order computation are pure graph math
over the in-memory model — **no FFI, no HW**. Each gets assertions
(house rule).

## The executor split (rg_execute — backend-divergent)

`rg_execute` becomes a thin dispatcher that runs `rg_schedule` (if not
already scheduled) then routes to a backend executor. The **public
signature is unchanged** — but to schedule onto real queues it needs the
`ctx` (for `gpu_queue_get` / `gpu_queue_barrier`), which `rg_execute`
already receives indirectly: today it takes `(g, device, queue)`. We add a
**ctx-taking variant** and keep the old one forwarding:

```cyrius
# Existing — wgpu single-queue path, unchanged ABI. Forwards to the
# multi-queue executor with a NULL ctx (→ wgpu serialized path).
fn rg_execute(g, device, queue): i64            # @public (existing)

# New — multi-queue aware. ctx supplies the queue table + barrier path.
# On native, schedules per-queue batches with cross-ring fence edges;
# on wgpu, identical command stream to rg_execute. # @public
fn rg_execute_mq(g, ctx): i64
```

### wgpu executor (serialized-equivalent)

`_rg_execute_wgpu_mq` ignores affinity for *submission* (one queue
exists) and produces **the same single encoder + single submit** as v2.5,
walking nodes in `sort_idx` order. Cross-queue fence edges are no-ops (the
single queue already serializes). The output command stream is identical
to today's `rg_execute` — verified by keeping `render_graph_e2e.cyr`
passing unchanged plus a new assertion that the wgpu MQ path emits nodes
in the same order.

### native executor (real overlap)

`_rg_execute_native_mq` walks the Schedule:

- For each queue with a non-empty batch: `gpu_queue_get(ctx, kind)` to
  acquire/create the logical Queue (idempotent, cached on ctx).
- Submit each batch's nodes in sort_idx order via the **queue-targeted
  async path**: compute nodes through the existing
  `native_compute_dispatch_cached_timeline`; render nodes through the
  **new `native_render_dispatch_timeline`** (R.4 — the missing render
  analog); copy nodes through the SDMA timeline submit
  (`native_cs_submit_timeline` on `AMDGPU_HW_IP_DMA`, the
  multiqueue_e2e leg-3 pattern).
- Before a consumer node's submit, for each incoming cross-queue fence
  edge, `gpu_queue_barrier(ctx, producer_queue, consumer_queue)` — which
  records the pending wait the consumer's next submit folds into an in-CS
  `TIMELINE_WAIT`. No CPU stall between rings.
- At graph end, `gpu_queue_wait_idle(ctx, q)` on each used queue to retire
  all work before `rg_execute_mq` returns (the graph's completion
  contract — callers expect results readable on return, as v2.5 does).

**The single MVP caveat carried from 3.1.1:** the cached IB BO is shared
per context (`native_compute_dispatch_cached_timeline` header,
`backend_native.cyr:129`). Multiple in-flight queue-targeted submits
sharing one IB would clobber it mid-flight. R.5 lifts this with **per-node
IB staging** (each scheduled node gets its own slice of a ring of IB BOs,
sized to the batch count) so genuine cross-ring overlap is safe — this is
the concrete realization of the "per-submit IB ring buffers (a later
3.1.x concern)" note. Until R.5, the native executor is correct but
serializes at the IB boundary (still uses the timeline path, so it is the
overlap-ready code path — R.5 removes the last serialization point).

## Backend split summary

| Aspect | wgpu | native AMD |
|---|---|---|
| Queue affinity | folded onto the one `WGPUQueue` | routed to `HW_IP_GFX` / `_COMPUTE` / `_DMA` |
| Cross-queue edge | no-op (single queue serializes) | in-CS `SYNCOBJ_TIMELINE_WAIT` via `gpu_queue_barrier` |
| Submit shape | one encoder, one submit (= v2.5) | per-queue batch, per-node timeline submit |
| Overlap | none (correct ordering only) | real GFX/COMPUTE/DMA concurrency |
| Render dispatch | encoder draw (existing) | **new** `native_render_dispatch_timeline` (R.4) |
| IB safety | wgpu owns command buffers | per-node IB staging (R.5) |

This is the v3.0/v3.1 posture exactly: same public API, wgpu correct +
complete, native gets the performance win, the delta is a documented
capability.

## Phasing

See **Phase R** in the punchlist. Shape: node affinity field + builder →
scheduler (pure CPU) → wgpu serialized executor → native render-timeline
dispatch → native MQ executor + IB staging → e2e on both backends → cut.

## Exit criteria (Phase R, across 3.2.8–3.2.10)

- `rg_node_queue` + per-node affinity (default-preserving); Node struct
  grown append-only; all existing render-graph tests pass unchanged.
- `rg_schedule` produces correct per-queue batches + cross-queue fence
  edges + submit order — each as a CPU assertion over hand-built graphs
  (diamond compute→render, cross-queue producer/consumer, intra-queue
  chains).
- **wgpu**: `rg_execute_mq` emits the identical command stream to v2.5
  `rg_execute`; `render_graph_e2e.cyr` passes unchanged; documented as
  serialized (no overlap).
- **native**: `native_render_dispatch_timeline` lands (render's timeline
  analog of the compute path); `programs/native_render_graph_mq_e2e.cyr`
  on Cezanne runs a compute→render cross-queue graph where the render node
  consumes the compute node's buffer, ordered by an in-CS timeline wait,
  with the rings on distinct HW rings — result CPU-verified, no wrong
  pixel, no CPU stall between the rings.
- Per-node IB staging removes the shared-IB serialization point; a graph
  with two independent compute batches on COMPUTE + GFX shows genuine
  overlap (verified by timeline-point progression, not just correctness).
- BACKEND_SIZE stays 256; no new Backend slots; `backend_is_complete`
  unchanged. lint / fmt (128 KiB cap) / vet / distlib diff-clean /
  version-check green per bite; CHANGELOG `[3.2.8]`..`[3.2.10]`; audit
  re-run on the new render-timeline CS-submit path (untrusted-input check
  on the IB-staging offset math).

## Risks

- **Executor rewrite regresses the single-submit wgpu path.** Mitigation:
  the wgpu MQ executor is required to emit the *identical* command stream;
  `render_graph_e2e.cyr` is the unchanged regression gate, plus a CPU
  assertion that the MQ scheduler's wgpu node order equals the v2.5
  sort_idx order.
- **Native render had no timeline path — new CS-submit surface.** R.4
  adds `native_render_dispatch_timeline`; it reuses the proven
  `native_cs_submit_timeline` (already GFX-ring-capable, with the
  WAIT_FOR_SUBMIT flag the comment reserved for exactly this). Risk is the
  GFX-ring cache-flush ordering vs the timeline signal — mitigated by
  keeping the existing render PM4 preamble/postamble (the cache-flush
  events `_backend_native_render_pass_draw` already emits) and signalling
  the timeline only on completion, identical to the synchronous path's
  syncobj-on-completion contract.
- **Shared-IB clobber under overlap.** This is the known 3.1.1 MVP caveat;
  R.5's per-node IB staging is the planned fix, called out as a bite (not
  a silent serialization). Until R.5 the native executor is correct
  (timeline path, serialized at IB) — overlap is the R.5 deliverable.
- **Deadlock from a mis-declared cross-queue cycle.** The toposort already
  rejects cycles (`rg_build` returns 1 on `sorted < n`,
  `render_graph.cyr:372`); cross-queue edges are a subset of those edges,
  so a cycle is caught at build, before scheduling. Assertion: a forced
  cross-queue cycle fails `rg_build`.
- **Consumer expectation: "multi-queue = faster on wgpu."** Mitigation:
  same as 3.1.1 — wgpu is documented as serialized-correct, the overlap is
  a native capability, and the cap is stated on `rg_execute_mq`'s doc
  comment, the CHANGELOG, and the roadmap.

## Hardware-verification note

All overlap verification (R.6 e2e, R.5 timeline-progression check) runs on
the **Cezanne (gfx90c)** dev box — the same silicon that HW-verified
3.1.1's 3-ring multiqueue e2e. No absent-hardware gap: GFX + COMPUTE +
DMA rings all exist on Cezanne, the timeline-syncobj path is proven there,
and the render-timeline dispatch is the same GFX ring the synchronous
render e2e (`native_render_e2e.cyr`) already drives. There is **no
CDNA/RDNA-specific dependency** in this work — it is pure scheduling over
primitives already proven on the dev box.
