# Proposal: v3.2 f64 (Double-Precision) Compute (both backends)

**Status:** **SHIPPED in 3.2.12** (2026-06-19) — see the CORRECTION + OUTCOME
banner below; the body is the original 2026-06-15 design, kept as history.
**Date:** 2026-06-15 (proposed); 2026-06-19 (shipped).
**Arc:** Ships **after** compressed textures (Phase T) and SPIR-V
(Phase S). f64 is **hard-gated on SPIR-V** on both backends — see the
hard truth below.
**Roadmap:** [`roadmap.md` § v3.2](../development/roadmap.md#v32--texture--shader-breadth).
**Companions:** `v3.2-compressed-textures.md` (Phase T),
`v3.2-spirv-ingestion-wgpu.md` (Phase S), `v3.2-spirv-gfx9-native-lowering.md` (Phase N, the
native compiler that Phase F's native half rides).
**Consumer:** **attn11** — the f64, hand-derived, grad-checked
transformer. Its GPU compute backend must match a CPU f64 oracle every
op is validated against; the f32-only WGSL path cannot carry it. attn11
is the only reason f64 is on the 3.2 roadmap, and the only adopter at
ship.

> Cezanne).** The **native** half is the live route: the Phase N SPIR-V→GFX9
> compiler emits `V_*_F64` (64-bit register pairs threaded as `MIR_T_F64`), and
> `MABDA_NATIVE_F64` is flipped to **1** — `gpu_caps_native_shader_f64()` returns
> 1. The shipped deliverable is the conformant f64 **arithmetic** toolkit:
> add/sub/mul/**div** (correctly-rounded reciprocal-Newton macro)/**sqrt**
> (correctly-rounded, full-range incl. subnormals)/fma, i32↔f64 + f32↔f64 convert,
> OpConstant, Ldexp, ordered compares, and OpSelect (`v_bfi_b32` on a 0/-1 mask).
> A consumer kernel compiles + dispatches entirely through
> `gpu_shader_module_create_spirv` → `gpu_compute_dispatch` (the F.9 layernorm
> smoke). **Transcendentals are out of scope as intrinsics**: GLSL.std.450

> caveat:** Cezanne's FP64 ALU is throttled (~1:16–1:32) — f64 is for
> correctness-critical consumer math, not throughput. See
> `[[project_f64_transcendentals_arithmetic_only]]` and the 3.2.12 CHANGELOG
> (Phase F.7/F.9/F.10) for the per-bite story.

## Summary

Let consumers run **double-precision (f64) compute** through the same
`gpu_compute_dispatch` surface they already use for f32, on both
backends, when the device and shader path support it. f64 is **not a new
backend slot, not a new dispatch path, and not a new struct** — it is
(1) a **device capability** consumers query before they rely on it, and
(2) **shader content** that arrives through the SPIR-V path Phase S
builds. The public API addition is small: a capability getter and a
dispatch-time guard. The work is in (a) correctly *detecting* f64
support per backend, (b) *requesting* the underlying feature at device
creation, and (c) on native, *emitting* f64 GFX9 ISA (which is Phase N's
SPIR-V→GFX9 compiler, not Phase F).

This is the smallest of the three 3.2 features in surface area but the
one with the most honest caveats to land, because **f64 support is a lie
if you read the roadmap literally** (see next section).

## Hard truth up front: there is no `WGPUFeatureName_ShaderF64`

> **⚠ This section's conclusion was wrong — see the CORRECTION banner above.**
> The base `WGPUFeatureName` enum indeed lacks ShaderF64, but the *native*
> `WGPUNativeFeature_ShaderF64 = 0x0003001D` exists and is what f64 uses (with
> naga accepting f64 SPIR-V on the standard path). Read the rest as historical.

The roadmap (§ v3.2) says "wgpu surfaces it as the `SHADER_F64`
feature." **That is not true at the FFI level in wgpu-native v29.** The
`WGPUFeatureName` enum in `deps/wgpu-native/include/webgpu/webgpu.h`
(v29) runs:

```
WGPUFeatureName_ShaderF16            = 0x0000000B   // f16 exists
WGPUFeatureName_Float32Filterable    = 0x0000000E
... (no F64 entry anywhere; enum ends at TextureComponentSwizzle = 0x16)
```

There is **`ShaderF16`, but no `ShaderF64`.** WGSL itself has no `f64`
type (gpuweb #2805, deferred Milestone 4+), so WebGPU never standardized
an `f64` feature name. f64 on the wgpu backend is therefore reachable
**only** through wgpu-native's SPIR-V passthrough:

- `WGPUNativeFeature_SpirvShaderPassthrough = 0x00030017`
  (`deps/wgpu-native/include/webgpu/wgpu.h`) — "Shader code isn't parsed
  or interpreted in any way. It is the caller's responsibility to ensure
  the code is correct. Supported platforms: Vulkan, DX12, Metal."
- `wgpuDeviceCreateShaderModuleSpirV(device, descriptor)` +
  `WGPUShaderModuleDescriptorSpirV { WGPUStringView label; uint32_t
  sourceSize; uint32_t const* source; }`.
- The SPIR-V binary uses the `Float64` capability; Vulkan validates it
  against the device's `VkPhysicalDeviceFeatures.shaderFloat64`. So the
  *real* gate is the Vulkan device feature, surfaced through wgpu-native
  only via "did the SPIR-V module compile + did the device advertise
  shaderFloat64", **not** a clean WebGPU boolean.

**Consequence for sequencing:** f64 on wgpu is impossible without the
SPIR-V passthrough path. That path is exactly what **Phase S** builds
(`wgpuDeviceCreateShaderModuleSpirV` FFI + the `SpirvShaderPassthrough`
device-feature request + a SPIR-V shader-source kind). So "f64 gates on
SPIR-V" is not a soft ordering preference — it is a literal API
dependency. Phase F's wgpu half is a thin layer on top of Phase S:
capability detection + a passthrough-time f64 guard. **This is why f64 is
last in the arc.** naga never enters the picture for f64 (it can't
validate `f64`), which is *fine* because passthrough bypasses naga
entirely — the roadmap's "naga may not validate f64, so a raw SPIR-V
passthrough may be required" is correct and, in fact, **passthrough is
the only option, not a fallback.**

## Hard truth #2: native f64 is the SPIR-V→GFX9 compiler, deferred to Phase N

The native AMD backend has **no shader compiler** — every shader in tree
(`native_gfx9_shader_store_deadbeef`, `_downsample_2x2`, `_solid_red`,
`_fullscreen_triangle_vs` in `src/backend_native_shaders.cyr`) is
**hand-authored GFX9 ISA**, byte-pinned and `llvm-mc`-verified. f64
compute kernels are not hand-authorable at consumer scale: attn11's GPU
backend is dozens of distinct kernels, not one box-filter. So native f64
arrives **only** when a SPIR-V→GFX9 lowering path exists that can emit
`V_ADD_F64` / `V_MUL_F64` / `V_FMA_F64` (and the SALU/VALU scaffolding,
register allocation, and 64-bit VGPR-pair handling f64 demands). **That
compiler is Phase N**, the native half of the SPIR-V work — the large
(compiler-scale) piece, in this same 3.2.x arc. Phase F's native half is:
capability detection (Cezanne *does* run f64, throttled) + routing f64
SPIR-V through Phase N's compiler + the throughput caveats. **Phase F
adds no GFX9 ISA itself** — it consumes Phase N's emitter.

To prove the dispatch *plumbing* before Phase N's general compiler is
mature, Phase F includes one **hand-authored f64 GFX9 reference kernel**
(`native_gfx9_shader_fma_f64` — a scalar `d = a*b + c` over an f64
buffer, the deadbeef-ABI user-SGPR VA convention). This is the f64
analogue of the deadbeef shader: it HW-validates `V_FMA_F64` encoding,
64-bit VGPR-pair load/store, and the f64 RSRC1 register budget on
Cezanne, decoupled from compiler maturity. attn11's real kernels still
wait on Phase N.

## Current state (what exists today)

- **No f64 anywhere.** mabda is f32-at-the-boundary by constraint
  (`f64 internally, f32 at the GPU boundary` — CLAUDE.md). Buffers are
  byte-blobs (`gpu_buffer_*`), so an f64 *buffer* already works (it's
  just 8-byte elements); what's missing is **f64 in a shader**.
- **Capabilities struct is 120 bytes** (`src/capabilities.cyr`), offsets
  +0..+112, with no spare field. f64 needs a new field; +120 (a 121st
  i64) is the next slot — grow to 128 bytes, mirroring the
  `gpu_timestamps`/`compute_shaders` boolean fields. Setters/getters
  follow the file's existing pattern (`gpu_caps_timestamp_query` at +16).
- **Feature detection precedent exists.** `gpu_timestamps_supported`
  (`src/gpu_timestamps.cyr:38`) calls `wgpu_device_has_feature(device,
  WGPU_FEATURE_TIMESTAMP_QUERY)` — the canonical "check the device, not
  the adapter; the feature must be *requested* at device creation"
  pattern. f64 detection is the same shape, but the *requested* feature
  is the native `SpirvShaderPassthrough`, and the *effective* gate is
  whether a tiny f64 SPIR-V probe module compiles.
- **Device features are NOT requested today.** The C launcher
  (`deps/wgpu_main.c:47`) builds the device with bare
  `WGPU_DEVICE_DESCRIPTOR_INIT` and **no `requiredFeatures`**. SPIR-V
  passthrough (and hence f64) needs `SpirvShaderPassthrough` added to
  `requiredFeatures` at `wgpu_shim_request_device` — this is **Phase S's
  C-shim work**, which Phase F depends on, not duplicates.
- **The shader path is byte-polymorphic but WGSL-only in practice.**
  `gpu_shader_module_create(ctx, bytes, n)` (`src/compute.cyr:197`)
  routes through `BACKEND_SLOT_SHADER_MODULE_CREATE` (+48). wgpu's
  filler (`_backend_wgpu_shader_module_create`,
  `src/backend_wgpu.cyr:192`) hardcodes `wgpu_shader_source_wgsl_len` /
  `WGPU_STYPE_SHADER_SOURCE_WGSL = 0x00000002`. There is no SPIR-V
  source kind (`WGPUSType_ShaderSourceSPIRV = 0x00000001` and
  `wgpuDeviceCreateShaderModuleSpirV` are unwired — the FFI table is 65
  fns / `_fp(0..64)`, no SpirV entry). **Phase S adds the source-kind
  discriminator**; Phase F reuses it (f64 shaders are SPIR-V shaders).
- **wgpu compute is a v3.0 stub.** `_backend_wgpu_compute_dispatch`
  (`src/backend_wgpu.cyr:425`) returns `GPU_ERR_OTHER` unconditionally —
  wgpu compute was never built (this is also why wgpu mipmap *generation*
  is `GPU_ERR_NOT_IMPLEMENTED`, per the 3.1.0 punchlist M.6b). **f64 on
  wgpu therefore additionally depends on real wgpu compute landing.**
  This is a second prerequisite for the wgpu half and must be tracked: if
  wgpu compute is still a stub when Phase F opens, wgpu f64 is
  `GPU_ERR_NOT_IMPLEMENTED` (fail-loud, ADR 006) and only native f64
  ships — exactly the posture 3.1.0 took for mipmaps.
- **Native compute dispatch is real.** `_backend_native_compute_dispatch`
  (`src/backend_native.cyr:477`) is HW-proven on Cezanne; `shmod`/`bp`
  are 16-byte `(handle, va)` pairs; the PM4 composer
  (`native_pm4_build_compute_*`) sets RSRC1/RSRC2 + USER_DATA SGPRs. An
  f64 kernel rides this verbatim — only the shader bytes and the RSRC1
  VGPR budget change (f64 doubles VGPR pressure).
- **Error code exists.** `GPU_ERR_NOT_IMPLEMENTED = 18`
  (`src/error.cyr:36`) is the fail-loud return for an f64 dispatch on a
  device/backend that can't carry it.

## The capability surface consumers query (the heart of Phase F)

attn11's correctness contract is "GPU result == CPU f64 oracle." It must
**refuse to run** on a device that can't do real f64 rather than
silently fall back to f32 (which would pass shape checks but fail the
oracle). So the public capability query is load-bearing:

```cyrius
# @public — does this context's backend + device support f64 compute?
# Returns 1 if a SPIR-V (wgpu) / GFX9 (native) f64 compute kernel will
# run with IEEE-754 double precision; 0 otherwise. Consumers that
# require f64 (attn11) MUST check this and hard-fail rather than fall
# back to f32. Detection is backend-specific (see below) — this is NOT
# a simple feature bit on wgpu.
fn gpu_caps_shader_f64(ctx): i64

# @public — populated by gpu_caps_from_context; readable on a caps struct.
fn gpu_caps_f64_supported(caps): i64          # field at GpuCapabilities+120
```

**New `GpuCapabilities` field** (`src/capabilities.cyr`, struct grows
120 → 128):

```
+120: shader_f64   (i64 bool)   # f64 compute available on this device
```

with `gpu_caps_f64_supported(c)` / `gpu_caps_set_f64(c, v)` following the
file's getter/setter convention, and the `gpu_caps_new` memset already
zero-initializing it.

### wgpu f64 detection (the subtle one)

There is no boolean to read. The detection sequence is:

1. Device must have been created with `SpirvShaderPassthrough` in
   `requiredFeatures` (Phase S's C-shim change). If the C launcher didn't
   request it (older consumer launcher), f64 is unavailable — report 0.
2. `wgpu_device_has_feature(device, 0x00030017)` (SpirvShaderPassthrough)
   — wire it as `WGPU_NATIVE_FEATURE_SPIRV_SHADER_PASSTHROUGH` alongside
   the existing `WGPU_FEATURE_TIMESTAMP_QUERY = 9` precedent.
3. **Probe.** Build a minimal f64 SPIR-V compute module (a 1-element
   `OpFMul` on `OpTypeFloat 64`, `OpCapability Float64`), call
   `wgpuDeviceCreateShaderModuleSpirV`, and check for a non-null module.
   On a device whose Vulkan `shaderFloat64 = VK_FALSE`, the passthrough
   module creation fails (the driver rejects the Float64 capability) —
   that failure *is* the f64 capability signal, since wgpu-native exposes
   no `shaderFloat64` query. Cache the probe result on the caps struct so
   it runs once. (This probe is the honest substitute for the
   nonexistent `SHADER_F64` feature bit; document it as such.)

### native f64 detection

Native talks to the Vulkan-less DRM/AMDGPU path, so there is no
`shaderFloat64` Vulkan query either — but there is ground truth:
**all GFX9+ AMD GPUs implement f64 in hardware** (the FP64 ALU path
exists on Vega/RDNA/CDNA; it is *throttled*, not *absent*). So native
f64 capability is:

1. Backend kind is `BACKEND_KIND_AMD` (GFX9+), AND
2. Phase N's SPIR-V→GFX9 emitter is present and supports the f64 opcodes
   (a compile-time/feature constant `MABDA_NATIVE_F64 = 1` set when Phase
   N lands the f64 emitter — until then `gpu_caps_shader_f64` reports 0
   on native even though the *hardware* can do it, because mabda can't
   *emit* it yet).

So `gpu_caps_shader_f64` is honest on both sides: it reports "can mabda
actually run an f64 kernel here end-to-end," not "does silicon have an
FP64 ALU."

## Public API (identical shape on both backends — ADR 005)

No new dispatch fn. f64 rides the existing surface:

```cyrius
# Existing — unchanged. bytes are now allowed to be a SPIR-V f64 module
# (wgpu: via Phase S passthrough; native: via Phase N GFX9 emit).
fn gpu_shader_module_create(ctx, bytes_ptr, n): i64    # + source-kind (Phase S)
fn gpu_compute_dispatch(ctx, shmod, x, y, z, bp): i64  # unchanged

# New — capability gate (above).
fn gpu_caps_shader_f64(ctx): i64
fn gpu_caps_f64_supported(caps): i64
```

The dispatch-time guard: `gpu_compute_dispatch` gains a check that, if
the module was created as an f64 module on a context where
`gpu_caps_shader_f64(ctx) == 0`, it returns `GPU_ERR_NOT_IMPLEMENTED`
(fail-loud) rather than dispatching a kernel the device will fault on.
This requires the shader module to **carry its source kind / f64 flag**
— a 1-word tag added to the module wrapper (wgpu: the 8-byte handle
becomes a small `(handle, flags)` struct; native: the existing 16-byte
`(handle, va)` pair extends to 24 with a flags word). Both are
append-only struct growth, the established pattern (NativeTexture grew
32→48 for mip metadata in M.1b).

## Backend interface changes

**None.** This is the key simplification and worth stating plainly: f64
adds **zero `Backend` slots**. `BACKEND_SIZE` stays at 248
(`src/backend.cyr:202`). f64 is:

- a capability field (`src/capabilities.cyr`, +120),
- shader *content* flowing through the existing
  `BACKEND_SLOT_SHADER_MODULE_CREATE` (+48) and
  `BACKEND_SLOT_COMPUTE_DISPATCH` (+64) slots (whose source-kind
  plumbing Phase S already added), and
- on native, an emitter behind Phase N.

The byte-polymorphic `shader_module_create` boundary (CLAUDE.md) is
exactly why no new slot is needed — the slot already "reads bytes
however the backend wants." Phase S taught it to read SPIR-V; Phase F
adds no new reading, only f64 *content* inside that SPIR-V. Avoiding a
slot also avoids the `backend_is_complete` walk extension and the
layout-assert churn (`src/backend.cyr:290`), so the FFI-descriptor-offset
audit surface (P(-1) security step 7) is untouched.

## wgpu backend impl

Thin, sits entirely on Phase S:

1. **Reuse Phase S's `wgpuDeviceCreateShaderModuleSpirV` filler.** An f64
   module is just a SPIR-V module whose `Float64` capability the
   passthrough doesn't inspect — no new code path; the module's f64-ness
   is the consumer's SPIR-V, validated by Vulkan at module creation.
2. **f64 detection + probe** (`gpu_caps_shader_f64`, above) populated in
   `gpu_caps_from_context`.
3. **Device-feature request** — confirm Phase S added
   `SpirvShaderPassthrough` to `requiredFeatures` in
   `wgpu_shim_request_device` (`deps/wgpu_main.c`). If not, that is a
   Phase F dependency to file against Phase S, not re-implement.
4. **Gated by real wgpu compute.** If `_backend_wgpu_compute_dispatch` is
   still a stub when Phase F lands, wgpu f64 dispatch returns
   `GPU_ERR_NOT_IMPLEMENTED` — wgpu f64 *module creation* can succeed
   (proving the passthrough path), but *dispatch* waits on wgpu compute.
   Document exactly like 3.1.0's wgpu mipmap-generate gap (M.6b).

## native AMD backend impl — gated on Phase N

1. **Capability** = `BACKEND_KIND_AMD` + `MABDA_NATIVE_F64` (set when
   Phase N's f64 emitter lands).
2. **The hand-authored reference kernel** `native_gfx9_shader_fma_f64`
   (`src/backend_native_shaders.cyr`) — scalar `dst[i] = a[i]*b[i]+c[i]`
   over f64 buffers, deadbeef user-SGPR ABI (s0:1 = a VA, s2:3 = b VA,
   etc.), using:
   - `global_load_dwordx2` for each f64 operand (64-bit = a VGPR pair),
   - `v_fma_f64 v[lo:hi], v[a:a+1], v[b:b+1], v[c:c+1]`,
   - `global_store_dwordx2` for the f64 result,
   - **RSRC1 with a doubled VGPR budget** — f64 ops consume VGPR pairs;
     where the downsample kernel reserved 16 VGPRs (RSRC1 `0x2C0083`,
     `src/backend_native_pm4.cyr:583`), the f64 kernel needs ~16 VGPR
     *pairs*; the RSRC1 VGPRS field and a new PM4 composer
     (`native_pm4_build_compute_fma_f64`) account for it. **FLOAT_MODE =
     0xC0 already covers f64 round-to-nearest-even** — the existing
     `GFX9_COMPUTE_PGM_RSRC1_MIN` comment already notes FLOAT_MODE applies
     to f64 (`src/backend_native_shaders.cyr:39`), so no new float-mode
     work.
   - Every dword byte-pinned + `llvm-mc`-verified via
     `scripts/disasm-shaders.sh` (the deadbeef/downsample method;
     `feedback_verify_gfx9_shader_bytes_with_llvm_mc`). This is the
     single new GFX9 ISA artifact in Phase F.
3. **General f64 kernels** route consumer SPIR-V through Phase N's
   SPIR-V→GFX9 emitter (which must support `OpFMul`/`OpFAdd`/`OpFma` on
   `OpTypeFloat 64` → `V_MUL_F64`/`V_ADD_F64`/`V_FMA_F64`). Phase F does
   not build the emitter; it consumes it and adds the f64 conformance
   tests. If Phase N's f64 opcode coverage is incomplete, native f64
   ships only for the kernels Phase N supports, documented per-op.
4. **Cezanne (gfx90c) runs f64 throttled** — the reference kernel proves
   correctness, not speed (see caveats).

## Throughput caveats to document (consumer-facing)

These go in the f64 consumer guide and the `gpu_caps_shader_f64` doc
comment, verbatim-honest (per `feedback_honest_perf_framing`):

- **f64 is ~16–64× slower than f32 on consumer RDNA/Vega** (FP64 rate is
  ~1:16 to 1:32 of FP32 on consumer parts; Cezanne/gfx90c is in this
  band). attn11 should expect f64 GPU compute to be *correct* and
  *faster than CPU f64* for large tensors, but **far** below f32 GPU
  throughput. Choose f64 only where the f64 oracle demands it.
- **Full-rate f64 (1:1, even 1:2 matrix) is CDNA/Instinct only**, via
  `V_MFMA_F64` (the matrix-FMA path). Cezanne has no MFMA; the reference
  kernel uses scalar `V_FMA_F64`. The roadmap's "full-rate only on CDNA"
  is correct; mabda does not pretend Cezanne is full-rate.
- **The fully-sovereign full-rate route** (native f64 + CDNA
  `V_MFMA_F64`) is explicitly **out of Phase F scope** — it is a Phase N
  follow-on (the emitter would need MFMA codegen) and needs CDNA
  hardware mabda's dev box (Cezanne) doesn't have. Documented, not built.
- **wgpu f64 inherits the Vulkan driver's f64 rate** — same silicon, same
  ~1:16–1:32 on consumer parts; passthrough adds no overhead but no
  speedup.

## Phasing — Phase F (sub-bites, mirroring the 3.1 punchlist granularity)

Each bite ends build / lint (per-file) / fmt (128 KiB-guarded) / vet /
distlib diff-clean / version-check clean; every new path adds a CPU
assertion (house rule). HW bites are Cezanne-gated.

- **F.1** — `GpuCapabilities` f64 field (+120, struct 120→128) +
  `gpu_caps_f64_supported` / `_set_f64` + zero-init verify. Layout
  asserts. Pure CPU.
- **F.2** — `gpu_caps_shader_f64(ctx)` dispatcher + the wgpu detection
  sequence (SpirvShaderPassthrough has-feature check wired as
  `WGPU_NATIVE_FEATURE_SPIRV_SHADER_PASSTHROUGH = 0x00030017`; probe-
  module hook stubbed behind Phase S). Native detection (kind +
  `MABDA_NATIVE_F64`). Mock-fnptr + value asserts.
- **F.3** — shader-module f64 flag: extend the module wrapper (wgpu
  `(handle, flags)`; native `(handle, va, flags)`), set the f64 bit at
  create time when the source kind is SPIR-V-f64. `gpu_compute_dispatch`
  fail-loud guard (`GPU_ERR_NOT_IMPLEMENTED` when f64 module on
  non-f64-capable ctx). Struct-layout + guard asserts.
- **F.4 (native)** — `native_gfx9_shader_fma_f64` hand-authored GFX9 ISA,
  every dword `llvm-mc`-round-tripped; `scripts/disasm-shaders.sh`
  extended. RSRC1 f64 VGPR budget documented. CPU byte-pin (size +
  checksum + spot checks). Pure CPU until F.6.
- **F.5 (native)** — `native_pm4_build_compute_fma_f64` PM4 composer
  (f64 RSRC1/RSRC2 + USER_DATA VA SGPRs for a/b/c/dst). Structural CPU
  test (scan for wired RSRC/VA/dim values), mirroring M.5.
- **F.6 (native, HW)** — `programs/native_f64_fma_e2e.cyr`: write known
  f64 a/b/c buffers, dispatch, CPU-read dst, verify `a*b+c` bit-exact
  against a CPU f64 computation on Cezanne. The f64-on-HW proof, decoupled
  from Phase N. Gated on amdgpu render node (no master).
