# Proposal: v3.2 SPIR-V Shader Ingestion — wgpu path

**Status:** Proposed (v3.2.1 design).
**Date:** 2026-06-15.
**Arc:** Second feature of the v3.2.x "Texture & Shader Breadth" arc —
ships *after* compressed textures (3.2.0) and *before* f64 compute (a
later 3.2.x). See the v3.2 punchlist (Phase S).
**Roadmap:** [`roadmap.md` § v3.2](../development/roadmap.md) —
"SPIR-V shader support — alternative path to WGSL. Shader cache keyed on
source kind. Reuses `shader_cache.cyr`."
**Companion (this arc):** native SPIR-V→GFX9 lowering (Phase N, later
3.2.x minors — the large compiler piece, staged honestly across
3.2.5–3.2.9).

## Summary

Let a consumer hand mabda a **pre-assembled SPIR-V binary** (a `u32`
word stream, magic `0x07230203`) and have the wgpu backend create a
shader module from it, exactly as it does WGSL today. This is the
alternative shader frontend the v3.2 roadmap calls for: WGSL stays the
default, SPIR-V becomes a peer input, and the existing byte-polymorphic
`gpu_shader_module_create` boundary carries it.

The wgpu side is genuinely small — wgpu-native v29 has first-class
SPIR-V support (`WGPUShaderSourceSPIRV`, `WGPUSType_ShaderSourceSPIRV =
0x00000001`). The work is (1) a way to *signal* "these bytes are SPIR-V,
not WGSL" across the byte-polymorphic boundary, (2) the SPIRV chained
descriptor builder + FFI plumbing, (3) SPIR-V binary validation, (4) a
source-kind-aware shader cache so a WGSL string and a SPIR-V blob that
happen to hash the same never collide, and (5) **the one non-obvious
constraint reckoned with below — the instance-feature gate in the C
launcher.**

## Hard truth up front: SPIR-V is a v29 *instance feature*, off by default

wgpu-native v29 does **not** accept SPIR-V unless the instance was
created with `WGPUInstanceFeatureName_ShaderSourceSPIRV` (= `0x2`) in
`WGPUInstanceDescriptor.requiredFeatures`. Verified directly against
`deps/wgpu-native/include/webgpu/webgpu.h`:

```c
typedef enum WGPUInstanceFeatureName {
    WGPUInstanceFeatureName_TimedWaitAny       = 0x00000001,
    WGPUInstanceFeatureName_ShaderSourceSPIRV  = 0x00000002,  // <- this
    ...
};
typedef struct WGPUInstanceDescriptor {
    WGPUChainedStruct * nextInChain;          // +0
    size_t requiredFeatureCount;              // +8
    WGPUInstanceFeatureName const * requiredFeatures;  // +16
    WGPU_NULLABLE WGPUInstanceLimits const * requiredLimits;  // +24
};
```

The current launcher (`deps/wgpu_main.c:374-381`) builds the instance
with `requiredFeatureCount = 0 / requiredFeatures = NULL`:

```c
WGPUInstanceExtras extras = {0};
extras.chain.sType = (WGPUSType)WGPUSType_InstanceExtras;
extras.backends = WGPUInstanceBackend_Vulkan;
WGPUInstanceDescriptor desc = {0};
desc.nextInChain = (const WGPUChainedStruct*)&extras;
preinit.instance = wgpuCreateInstance(&desc);
```

So **a SPIR-V `wgpuDeviceCreateShaderModule` call against today's
instance fails** — the feature is not requested. This is the load-bearing
constraint of the whole proposal and it lives in **consumer-owned C**
(`deps/wgpu_main.c` is downloaded/linked by each consumer, like the wgpu
binaries themselves — not a mabda source file). The fix is a 3-line
launcher edit:

```c
static const WGPUInstanceFeatureName k_required[] = {
    (WGPUInstanceFeatureName)WGPUInstanceFeatureName_ShaderSourceSPIRV,
};
WGPUInstanceDescriptor desc = {0};
desc.nextInChain         = (const WGPUChainedStruct*)&extras;
desc.requiredFeatureCount = 1;
desc.requiredFeatures     = k_required;
```

mabda cannot make this edit for the consumer (it does not own the
launcher), so the design must (a) ship the updated `deps/wgpu_main.c`
reference launcher in-tree, (b) document the gate in the consumer
migration note, and (c) **fail loud, not silent**, when a consumer feeds
SPIR-V to an instance that wasn't built with the feature — the module
create returns `0`, and `gpu_shader_module_create_spirv` maps that to a
clean error rather than a mystery null. There is no way for mabda to
detect "instance lacks the feature" before the create call; the
fail-loud null return is the honest contract.

This is the same shape as every other consumer-C coupling in mabda
(wgpu-native binaries, `samvada_main.c`): the Cyrius side is complete and
correct; the consumer's build wires one C constant.

## Current state (what exists today)

- **`gpu_shader_module_create(ctx, bytes_ptr, n)` is byte-polymorphic**
  (`src/compute.cyr:197`). It dispatches through
  `BACKEND_SLOT_SHADER_MODULE_CREATE` (+48) via `fncall3`. wgpu reads the
  bytes as WGSL UTF-8; native reads them as pre-compiled GFX9 ISA. There
  is **no kind tag** — the bytes' meaning is purely a function of which
  backend is bound. SPIR-V breaks this: on wgpu alone, the *same backend*
  must now accept *two* byte formats. So the kind has to travel
  explicitly. (`docs/proposals/v3-wgsl-frontend-choice.md` calls
  byte-polymorphism "the load-bearing API choice"; this proposal extends
  it with a kind tag rather than replacing it — see "Why a kind tag".)
- **wgpu shader create** (`src/backend_wgpu.cyr:192`,
  `_backend_wgpu_shader_module_create`) threads the validated length `n`
  into `wgpu_shader_source_wgsl_len(bytes_ptr, n)` (Audit 2026-06-14
  MED-4 fix), builds `wgpu_shader_module_descriptor(0, src)`, and calls
  `wgpu_device_create_shader_module(device, desc)`.
- **The WGSL source descriptor** is `wgpu_shader_source_wgsl_len`
  (`src/wgpu_descriptors.cyr:200`): a 32-byte struct = `ChainedStruct`
  (16) + `StringView` (16), sType `WGPU_STYPE_SHADER_SOURCE_WGSL = 0x2`
  (`src/wgpu_types.cyr:123`). **There is no SPIRV descriptor builder and
  no SPIRV sType constant** in tree yet.
- **`shader_cache.cyr` is keyed on a u64 FNV-1a hash of the WGSL source
  *bytes*** (`_shader_hash`, NUL-terminated scan). `shader_cache_get`,
  `_set`, `_get_or_compile` all assume a NUL-terminated WGSL C-string and
  call `wgpu_shader_source_wgsl` internally. **A SPIR-V blob has embedded
  NUL bytes** (it is `u32` words; `0x07230203` itself contains no NUL but
  operand words routinely do) — so the current `_shader_hash`'s
  `while (c != 0)` loop would stop at the first zero byte, producing a
  near-useless hash and colliding wildly. The cache is WGSL-only today
  and cannot be pointed at SPIR-V without a length-explicit hash.
- **The FFI create entry exists** —
  `wgpu_device_create_shader_module(device, desc)` (`src/wgpu_ffi.cyr:166`,
  `_fp(16)`). It takes a *descriptor*; the descriptor's `nextInChain`
  selects WGSL vs SPIRV. No new FFI fn-table slot is needed — only a new
  *descriptor builder*.
- **The instance is built without the SPIR-V feature** (see the hard
  truth above).

## The byte-polymorphic boundary, extended: a shader-source KIND

SPIR-V and WGSL are not distinguishable by content alone in a way mabda
should rely on (a SPIR-V binary *does* start with a fixed magic, but
sniffing magic bytes to choose a code path is exactly the kind of "magic"
the project bans — and it would silently misroute a WGSL file that
happened to begin with those bytes). The consumer must **declare** the
kind. Two options were considered:

**Option A — a separate public entry per kind (CHOSEN).** Keep
`gpu_shader_module_create(ctx, bytes_ptr, n)` as the WGSL/native
byte-polymorphic entry it is today (zero churn, zero risk to the v3.0/3.1
contract), and add a sibling:

```cyrius
fn gpu_shader_module_create_spirv(ctx, words_ptr, word_count): i64
```

The kind is encoded *in the function the consumer calls*. No enum
parameter, no `fncall` arity change, no new struct field. Internally both
funnel to a single kind-carrying backend slot (below).

**Option B — add a `kind` parameter to `gpu_shader_module_create`.**
Rejected: it changes a stable v3.0 public signature (every consumer's
call site churns), and `gpu_shader_module_create` already documents its
bytes as "backend-specific" — overloading it with an orthogonal
source-kind axis muddies two concepts. A second named entry is clearer
and the established mabda idiom (`gpu_texture_create_2d_rgba8` vs
`_mipped`, `gpu_surface_configure_wgpu` vs `_native_kiosk`).

### Shader-source kind constants

A small public enum, parallel to `BackendKind`, so the cache and any
future native path can pattern-match:

```cyrius
enum ShaderSourceKind {
    SHADER_SRC_WGSL  = 0;   # UTF-8 text (default; today's path)
    SHADER_SRC_SPIRV = 1;   # u32-word binary, magic 0x07230203
    SHADER_SRC_GFX9  = 2;   # pre-compiled GFX9 ISA (native today)
}
```

`SHADER_SRC_GFX9` is reserved up front (the v4.0/NVIDIA-style "name every
vendor now" precedent in `backend.cyr`) so the native byte-polymorphic
input has a name when Phase N gives native a real choice between ISA and
SPIR-V.

## The kind across the backend slot

`gpu_shader_module_create_spirv` cannot reuse `fncall3` against the
existing `BACKEND_SLOT_SHADER_MODULE_CREATE` slot unchanged, because that
slot's wgpu filler (`_backend_wgpu_shader_module_create`) is hardwired to
WGSL. Two sub-options, **kept deliberately minimal**:

**S-Option 1 (CHOSEN): widen the slot signature to carry kind.** Change
the shader-create slot from `(ctx, bytes_ptr, n)` to
`(ctx, bytes_ptr, n, kind)` — a 4-arg `fncall4`, comfortably within the
fncall ceiling and the same arity as `create_mipped`. Both backends'
fillers gain a `kind` param; wgpu branches WGSL/SPIRV on it, native
ignores it for v3.2 (always GFX9; asserts `kind == SHADER_SRC_GFX9` is
the only valid native input and returns `0` otherwise — fail-loud).
`gpu_shader_module_create` forwards `SHADER_SRC_WGSL` (wgpu) or
`SHADER_SRC_GFX9` (native) per the bound backend's current meaning;
`gpu_shader_module_create_spirv` forwards `SHADER_SRC_SPIRV`. **No new
slot offset** — the slot *type* widens but its `BACKEND_SLOT_*` constant
and position are untouched, so the append-after-KIND invariant and every
layout test hold. This is the lowest-churn path and matches how the
public API stayed call-site-stable across the backend swap.

**S-Option 2 (rejected): a brand-new `BACKEND_SLOT_SHADER_MODULE_CREATE_SPIRV`
slot.** Rejected as over-built for v3.2: it would grow `BACKEND_SIZE`,
demand a native filler that can only fail-loud, and split one logical
operation (create-a-shader-module) across two slots for no benefit. The
kind param is the right axis.

> **`backend_is_complete` note:** widening an *existing* slot's signature
> does not change the completeness walk — the fnptr at +48 is still
> non-null on both backends. No range-marker churn.

## wgpu backend impl

Three pieces, all small, all cited against v29 `webgpu.h`.

1. **SPIRV sType constant + descriptor builder** (`src/wgpu_types.cyr` +
   `src/wgpu_descriptors.cyr`):

   ```cyrius
   # src/wgpu_types.cyr — alongside WGPU_STYPE_SHADER_SOURCE_WGSL = 0x2
   WGPU_STYPE_SHADER_SOURCE_SPIRV = 0x00000001;   # webgpu.h:949
   ```

   ```cyrius
   # src/wgpu_descriptors.cyr — WGPUShaderSourceSPIRV (32 bytes, v29):
   #   +0:  chain (ChainedStruct = 16; next@0, sType@8)
   #   +16: codeSize (u32)  -- COUNT OF u32 WORDS, not bytes
   #   +20: padding (4)     -- code ptr is 8-byte aligned
   #   +24: code (const uint32_t*, 8)
   # Layout verified vs deps/wgpu-native/include/webgpu/webgpu.h:2800.
   fn wgpu_shader_source_spirv(words_ptr, word_count): i64 {
       var src = alloc(32);
       memset(src, 0, 32);
       wgpu_chained_struct(src, WGPU_STYPE_SHADER_SOURCE_SPIRV);
       store32(src + 16, word_count);   # codeSize in WORDS
       store64(src + 24, words_ptr);    # code ptr
       return src;
   }
   ```

   Note the field-offset contrast with the WGSL builder: WGSL's
   payload is a 16-byte `StringView` (data ptr + byte length) at +16;
   SPIRV's payload is a `u32` count at +16 and a `u32*` at +24 (with 4
   bytes of struct padding between, because the pointer is 8-byte
   aligned). `codeSize` is **words, not bytes** — the single most common
   integration bug for SPIRV-via-WebGPU and the thing to pin with a test.

2. **The create wrapper** (`src/backend_wgpu.cyr`): widen
   `_backend_wgpu_shader_module_create(ctx, bytes_ptr, n, kind)` to branch:

   ```cyrius
   fn _backend_wgpu_shader_module_create(ctx, bytes_ptr, n, kind): i64 {
       if (ctx == 0)       { return 0; }
       if (bytes_ptr == 0) { return 0; }
       if (n <= 0)         { return 0; }
       var device = gpu_ctx_device(ctx);
       var src = 0;
       if (kind == SHADER_SRC_SPIRV) {
           # n is BYTE length here; SPIRV needs WORD count.
           if (_spirv_validate(bytes_ptr, n) != 0) { return 0; }
           src = wgpu_shader_source_spirv(bytes_ptr, n / 4);
       } else {
           src = wgpu_shader_source_wgsl_len(bytes_ptr, n);
       }
       var desc = wgpu_shader_module_descriptor(0, src);
       return wgpu_device_create_shader_module(device, desc);
   }
   ```

   `wgpu_shader_module_descriptor` is reused unchanged — its
   `nextInChain` field carries whichever source struct, since both are
   `ChainedStruct`-prefixed (the whole point of the chained-struct
   mechanism).

3. **The public dispatcher** (`src/compute.cyr`, next to
   `gpu_shader_module_create`):

   ```cyrius
   # @public — create a shader module from a SPIR-V binary (wgpu path).
   # words_ptr → u32 word stream; byte_len = word_count * 4. The wgpu
   # instance MUST have been built with the ShaderSourceSPIRV feature
   # (deps/wgpu_main.c) — otherwise create returns 0. Native backend
   # returns 0 (SPIR-V→GFX9 lowering is Phase N, a later 3.2.x).
   fn gpu_shader_module_create_spirv(ctx, words_ptr, byte_len): i64 {
       if (ctx == 0) { return 0; }
       var slot = backend_get_slot(gpu_ctx_backend(ctx),
       BACKEND_SLOT_SHADER_MODULE_CREATE);
       return fncall4(slot, ctx, words_ptr, byte_len, SHADER_SRC_SPIRV);
   }
   ```

   `gpu_shader_module_create` (the existing WGSL/GFX9 entry) becomes a
   one-line forward that passes the bound backend's default kind:

   ```cyrius
   fn gpu_shader_module_create(ctx, bytes_ptr, n): i64 {
       if (ctx == 0) { return 0; }
       var slot = backend_get_slot(gpu_ctx_backend(ctx),
       BACKEND_SLOT_SHADER_MODULE_CREATE);
       var kind = SHADER_SRC_WGSL;
       if (backend_kind(gpu_ctx_backend(ctx)) == BACKEND_KIND_WGPU) {
           kind = SHADER_SRC_WGSL;
       } else {
           kind = SHADER_SRC_GFX9;
       }
       return fncall4(slot, ctx, bytes_ptr, n, kind);
   }
   ```

   (This preserves byte-for-byte the existing meaning: WGSL on wgpu, GFX9
   on native — no behavioral change for current consumers, the call site
   is unchanged.)

## SPIR-V validation

SPIR-V is a structured binary; full validation is SPIRV-Tools' job and
out of scope (mabda doesn't vendor it). But the bytes cross the FFI
boundary into wgpu-native's parser, so mabda owes the consumer the cheap,
high-value structural checks that catch the common feeds-garbage bugs
*before* they reach the driver (the P(-1) "input validation" + "buffer
safety" rules). `_spirv_validate(ptr, byte_len)` returns `0` ok / nonzero
error and checks, in order:

1. **`byte_len >= 20`** — the SPIR-V header is 5 words (magic, version,
   generator, bound, schema) = 20 bytes. Anything shorter is not SPIR-V.
2. **`byte_len % 4 == 0`** — SPIR-V is a `u32` word stream; a byte length
   not divisible by 4 is malformed (and `n / 4` would silently truncate).
3. **Magic number.** First word must be `0x07230203` (little-endian
   read of the first 4 bytes). If it reads as `0x03022307`, the binary is
   **byte-swapped** (big-endian SPIR-V) — reject with a distinct error;
   mabda does not byte-swap (wgpu-native expects host-endian words on the
   little-endian AGNOS target, and silently swapping would mask a
   consumer build bug).
4. **`bound` sanity (word[3]).** The id-bound must be `>= 1` and
   `<= word_count` is *not* a valid check (bound can legitimately exceed
   word count), but `bound == 0` is always malformed; a loose upper guard
   (`bound < 0x40000000`) catches a wildly corrupt header cheaply. (Kept
   deliberately loose — deep validation is the driver's job.)
5. **Integer-overflow guard on `word_count = byte_len / 4`** — `byte_len`
   is already validated `>= 20` and `% 4 == 0`; the division cannot
   overflow, but the result is asserted `<= MABDA_MAX_SPIRV_WORDS` (a
   generous cap, e.g. 16 Mi words = 64 MiB, mirroring
   `WGPU_SHADER_SOURCE_MAX_BYTES`'s "prevent a runaway" intent) so a
   bogus huge `codeSize` can't be handed to the driver.

Each check has a CPU assertion that would have caught the corresponding
malformed input (house rule). Validation runs in the wgpu slot *before*
building the SPIRV descriptor; a failure returns `0` (no module), which
the public dispatcher surfaces as the fail-loud null.

## Shader cache: keyed on (source-kind, hash)

The roadmap explicitly says "shader cache keyed on source kind. Reuses
`shader_cache.cyr`." The current cache is WGSL-only and NUL-terminated
(see Current State). Two coupled changes:

1. **A length-explicit, kind-folded hash.** Add
   `_shader_hash_n(ptr, byte_len)` — the same FNV-1a but bounded by an
   explicit length instead of a NUL scan (SPIR-V has embedded NULs; WGSL
   can use this too, it just passes its strlen). Fold the kind into the
   seed so a WGSL string and a SPIR-V blob can never alias even on a hash
   collision: `hash = FNV(kind_seed; bytes)`, e.g. mix `kind` into the
   FNV offset basis before the byte loop. The existing `_shader_hash`
   (NUL-terminated) stays for the unchanged
   `shader_cache_get(cache, wgsl_cstr)` callers, implemented as
   `_shader_hash_n(ptr, strlen(ptr))` folded with `SHADER_SRC_WGSL`, so
   existing keys are stable *for WGSL* (no cache-file churn — the cache is
   in-memory per process anyway, so even a key change is harmless, but
   keeping WGSL keys identical avoids surprising the bench numbers).

2. **Kind-aware get/set/get-or-compile.** Add the SPIR-V-shaped peers:

   ```cyrius
   fn shader_cache_get_spirv(cache, words_ptr, byte_len): i64
   fn shader_cache_set_spirv(cache, words_ptr, byte_len, module): i64
   fn shader_cache_get_or_create_spirv(cache, ctx, words_ptr, byte_len, label): i64
   ```

   `get_or_create_spirv` mirrors `shader_cache_get_or_compile` but routes
   through `gpu_shader_module_create_spirv` (ctx-aware, backend-dispatched)
   rather than calling `wgpu_device_create_shader_module` directly — the
   v2-era `get_or_compile` predates the backend abstraction and reaches
   straight into the wgpu FFI; the new SPIR-V peer is written
   ctx-first from the start. (A follow-up bite can migrate the WGSL
   `get_or_compile` to the ctx path too, but that's not required for
   3.2.1 and is noted as deferred.)

The `map_u64` backing store is unchanged — it's a u64→u64 map; only the
key derivation changes. The kind-fold means the *key space* is
partitioned by kind for free, with no second map and no compound key
struct.

## Native consistency (Phase N preview — NOT in 3.2.1)

The native backend still reads `gpu_shader_module_create` bytes as
**pre-compiled GFX9 ISA** (`_backend_native_shader_module_create`
currently returns `0` — native shaders come from the in-tree
`native_gfx9_shader_*` library, not this public path). For 3.2.1:

- The widened slot's native filler accepts `kind` and returns `0` for
  anything other than `SHADER_SRC_GFX9` — i.e. **`gpu_shader_module_create_spirv`
  on the native backend fails loud** (returns 0), it does not silently
  pretend. This is the honest contract: native SPIR-V ingestion does not
  exist yet.
- **Phase N** (later 3.2.x minors, 3.2.5–3.2.9) adds the native
  SPIR-V→GFX9 lowering. That is the large compiler piece the
  maintainer scoped as in-scope for both backends — and it is genuinely
  large: `v3-wgsl-frontend-choice.md` calibrates a *WGSL* compute-only
  frontend at 10–16 weeks; a SPIR-V frontend skips the parser (SPIR-V is
  already a structured IR, ~the "NIR-lite" layer) but still needs the
  ~3–5k LoC ISA-selection backend against GFX9, plus capability gating
  (SPIR-V can encode features GFX90c can't). It ships as its **own AGNOS
  package** (the `v3-wgsl-frontend-choice.md` "separate package, not in
  mabda's tree" anchor holds — mabda consumes it via `[deps.X]`), staged:
  (N.1) header/capability validation + the subset gate; (N.2) compute
  subset codegen → GFX9 ISA bytes feeding the existing native
  shader-module path; (N.3) HW e2e on Cezanne. **3.2.1 explicitly does
  not start Phase N** — it lands the wgpu path and the kind/cache
  scaffolding Phase N will plug into. Calling SPIR-V "done" after 3.2.1
  would be dishonest; 3.2.1 is "SPIR-V on wgpu; native fails loud,
  tracked as Phase N."

## Phase S — sub-bites (each ends green: build/lint/fmt/vet/distlib/version-check)

The granularity mirrors the 3.1 punchlist (Phase letter + numbered bites,
each independently verifiable).

- **S.1** — Constants + SPIRV descriptor builder + validation, CPU-only.
  `SHADER_SRC_*` enum; `WGPU_STYPE_SHADER_SOURCE_SPIRV = 0x1`;
  `wgpu_shader_source_spirv(words_ptr, word_count)` with the 32-byte
  layout pinned by an offset test; `_spirv_validate` + every check's
  assertion (short / unaligned / bad-magic / byte-swapped / bound==0 /
  oversize). No HW.
- **S.2** — Widen the shader-create slot to `(ctx, bytes_ptr, n, kind)`.
  Update both fillers (`_backend_wgpu_shader_module_create` branches;
  `_backend_native_shader_module_create` gains the param, fails loud on
  non-GFX9) and the two public dispatchers
  (`gpu_shader_module_create` forwards default kind;
  `gpu_shader_module_create_spirv` forwards SPIRV). `fncall3 → fncall4`
  at the call site. Mock-slot CPU tests: routing, kind pass-through,
  WGSL path byte-identical to before, native-SPIRV fail-loud. Layout
  test confirms the slot offset (+48) and `backend_is_complete` are
  unchanged.
- **S.3** — Source-kind-aware shader cache. `_shader_hash_n` (length +
  kind fold); `shader_cache_get/set_spirv`;
  `shader_cache_get_or_create_spirv` (ctx-routed). CPU tests: WGSL key
  stability (existing keys unchanged), WGSL/SPIRV non-collision on a
  forced same-hash, SPIRV round-trip, embedded-NUL blob hashes fully.
- **S.4** — Reference launcher + consumer gate. Update the in-tree
  `deps/wgpu_main.c` to request `WGPUInstanceFeatureName_ShaderSourceSPIRV`
  in `WGPUInstanceDescriptor.requiredFeatures`; document the gate in the
  consumer migration note (a consumer who skips the edit gets a clean
  null from create, not a crash). No mabda Cyrius change here — this is
  the C-coupling bite, called out separately so its consumer-facing
  nature is unmistakable.
- **S.5 (wgpu, HW-gated)** — `programs/spirv_e2e.cyr`: take a tiny
  pre-assembled compute SPIR-V blob (assembled offline with
  `spirv-as`/`glslangValidator`, checked into `programs/` as a `.spv`
  loaded at runtime, or embedded as a word array with the assembly source
  in a comment — same posture as the hand-authored GFX9 shaders being
  byte-pinned), create a module via `gpu_shader_module_create_spirv`,
  build a compute pipeline, dispatch, CPU-verify the result equals the
  WGSL-built equivalent (cross-source identity). Gated on a wgpu-native
  box whose instance was built with the SPIRV feature (S.4).
  > **Honest dependency:** S.5 needs a working **wgpu compute pipeline**.
  > Per the 3.1 mipmap punchlist (M.6b) and `backend_wgpu.cyr:425`,
  > `_backend_wgpu_compute_dispatch` is still a v3.0 **stub** (returns
  > `GPU_ERR_OTHER`) — wgpu compute was never wired. So a *compute*
  > SPIR-V e2e is blocked on real wgpu compute (the same v3.x item that
  > blocks wgpu mipmap generation). **Mitigation:** S.5 ships as a
  > **render** SPIR-V e2e instead (a SPIR-V vertex+fragment pair driving
  > the existing, working `_backend_wgpu_render_*` path —

## Exit criteria (3.2.1 — SPIR-V on wgpu)

- Public `gpu_shader_module_create_spirv(ctx, words_ptr, byte_len)` on the
  wgpu backend, end-to-end to a real `WGPUShaderModule`; native returns
  `0` (fail-loud, Phase N tracked).
- `gpu_shader_module_create` (WGSL/GFX9) behavior **byte-identical** to
  3.1.1 — no consumer call-site churn, no WGSL cache-key change.
- SPIR-V validation rejects short/unaligned/bad-magic/byte-swapped/
  bound==0/oversize binaries with a clean null + a distinct posture per
  class; each has a regression assertion.
- Shader cache partitions WGSL vs SPIR-V by kind; an embedded-NUL SPIR-V
  blob hashes over its full length; a forced WGSL/SPIR-V hash collision
  does **not** alias.
- `deps/wgpu_main.c` reference launcher requests the SPIRV instance
  feature; the consumer gate is documented; a feature-less instance
  fails loud (documented, not crashing).
- wgpu HW: `spirv_e2e` (render variant) produces the same pixels as the
  WGSL-built equivalent on a SPIRV-feature instance. Compute-SPIR-V e2e
  deferred with wgpu compute.
- CPU suite: descriptor offsets (incl. `codeSize` = WORDS not bytes),
  validation classes, slot widening + routing, cache kind-partition —
  every new path adds an assertion.
- lint / fmt / vet clean per-file; `dist/mabda.cyr` regenerates
  diff-clean; `version-check.sh` passes; CHANGELOG `[3.2.1]`; audit index
  current.
